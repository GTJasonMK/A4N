# 项目协作与权限合同 BFS 冗余清理记录

日期：2026-08-13

## 搜索起点与覆盖范围

本专项从“项目详情页管理协作者”和“项目列表处理邀请、按访问范围筛选项目”两项生产功能出发，按广度优先顺序追踪完整调用闭包：

```text
ProjectCollaborationPanel / NovelList / ProjectListPanel
→ frontend/src/api/project.ts
→ generated Host TypeScript / command manifest
→ Web command dispatch / Tauri Host dispatch / CLI command endpoint
→ a4n-runtime project_collaboration / project_records
→ a4n-orchestrator CollaborationApplication / OrchestratorContext
→ a4n-db collaboration access / members / invites / queries
→ project_member / project_invite / novel_project / user
```

横向覆盖以下活跃业务路径：

```text
成员列表、邀请、待处理邀请列表
接受、拒绝、撤销邀请
角色调整、成员移除、主动离开
viewer / editor / manager / owner 权限层级
只读账号权限降级
文本根项目与自由视频根项目解析
派生项目权限继承和所有者继承
项目列表 owned / collaborating / all 范围
项目摘要的所有者、当前角色、成员数和待处理邀请数投影
所有 Orchestrator / Runtime 业务侧项目权限调用
```

显式依赖覆盖 Rust/TypeScript 调用、模块导入和 `pub use` 链、SeaORM 查询与事务；隐式依赖覆盖 Serde/JSON Schema、生成 TypeScript、Host command manifest、Web/Tauri/CLI 字符串分发、JWT/Tauri 可信身份、Orchestrator context 注入、项目族根关系、只读角色降级、PostgreSQL 部分唯一索引和前端角色展示条件。

仓库中该功能不存在 XML DI、运行时反射注册、动态代理或 AOP 切面；依赖注入由 `ServerState/AppState → OrchestratorContext → DbHandle` 显式完成，框架入口由 command manifest、Host dispatcher、Server route 和生成合同覆盖。

## 生产数据只读核验

通过运行中的 `a4n-postgres` 容器对开发库执行只读查询：

```text
project_member_total=0
project_member_roles=0
invalid_member_roles=0
project_invite_total=0
project_invite_roles=0
invalid_invite_roles=0
invalid_invite_statuses=0
```

当前没有活跃协作记录要求保留角色首尾空白、未知角色、旧富摘要或历史邀请读取兼容。清理后持久化非法值直接失败，不再 trim、填空或静默跳过。

## 清理后唯一事实标准

```text
访问权限层级与 satisfies
→ a4n_domain::collaboration::ProjectAccessRole

可邀请成员角色及持久化解析
→ a4n_domain::collaboration::ProjectMemberRole

项目访问范围
→ a4n_domain::collaboration::ProjectAccessScope

项目族合法值
→ a4n_domain::project::ProjectKind

Host 成员/邀请输入输出
→ a4n-api-contract 重导出的领域合同

权限、根项目、邀请和成员持久化
→ a4n-db::collaboration
```

DB、Orchestrator 和 Runtime 只保留各自必要的错误边界和薄调用适配，不再复制角色枚举、解析规则或 Host DTO。

## 明确保留的活跃边界

- `ProjectAccessRole` 与 `ProjectMemberRole` 语义不同：owner 是访问角色，但不能作为邀请角色。
- `CollaborationRootProject.user_id` 被派生项目创建用于继承根项目所有者，不是冗余字段。
- `pending_invite_count: Option<u64>` 表示当前角色是否有权查看邀请统计，不是缺失角色 fallback。
- 项目列表请求未提供 `accessScope` 时使用 `all` 是 CLI/Web 的现行业务默认；一旦提供则严格解析，不接受空白或未知值。
- 前端角色判断只负责按钮可见性和交互提示；后端权限校验仍是安全边界，二者职责不同。
- 新邀请前更新过期邀请用于释放数据库部分唯一索引；列表读取不再产生写操作。
- 接受过期邀请时写入 `expired` 是显式 mutation 的终态推进，不属于读取副作用。
- Web/Tauri/CLI 保留各自传输适配；角色、权限和响应结构只有一套业务事实来源。
