# 项目资料归纳确认目标重复解析清理记录

日期：2026-08-15

## BFS 覆盖范围

从项目详情页“确认章节大纲/分部大纲归纳候选”开始，按 BFS 追踪：

```text
ImportsTab
→ confirmReverseEngineeringCandidate
→ confirm_reverse_engineering_candidate Host command
→ Runtime workflow_run 查询与 Editor 授权
→ Orchestrator 候选事务确认
→ workflow_run.current_step_key / checkpoint / fingerprint 校验
→ ReverseEngineeringCandidate
→ 正式资料 RAG 同步警告
```

已覆盖前端唯一确认入口、生成 TypeScript 合同、command manifest、Server/Tauri/CLI 分发、
Runtime 权限边界、Orchestrator 事务、workflow/checkpoint 身份、候选结果和提交后同步。
确认目标已经由 Orchestrator 从锁定后的 workflow 状态解析，并随强类型候选结果返回；Runtime
再次解析未锁定快照中的 `current_step_key` 是第二套目标 owner。仓库不存在相关 XML、DI、反射、
动态代理或 AOP 入口。

## 优化记录

1. 删除 Runtime 对 `current_step_key` 的第二次目标解析。
2. 提交后同步直接使用 Orchestrator 已确认并返回的 `ReverseEngineeringCandidate.target`。
3. 删除目标缺失时合成 `missing_reverse_candidate_step` 占位状态的回退。
4. 删除 Runtime 在 `project_id` 缺失时回退到 `root_project_id` 的伪兼容路径；该路径随后必被 Orchestrator 的候选身份合同拒绝。
5. Runtime 只接受候选工作流正式拥有的正 `project_id`，错误携带真实 workflow/project/root 状态。
6. Orchestrator 缺少 `current_step_key` 时不再返回合成占位词，错误改为携带真实 workflow ID、状态和 business key。

项目权限仍在写入前完成；目标、checkpoint、输入指纹、来源新鲜度和事务写入仍由
Orchestrator 唯一校验。未新增 fallback、兼容、回退、占位或第二套合同。
