# A4N 下一轮进程边界重构计划

日期：2026-07-31

依据：[a4n-进程依赖架构图.html](./a4n-进程依赖架构图.html)
状态：待实施

## 1. 结论

下一轮只做一件事：

> 将当前八个已运行的 Capability sidecar 从聚合的 `a4n-capabilities` 和具体服务感知的 `a4n-service-protocol` 中解耦，形成八组独立的 `*-contract` / `*-client`，并建立可自动失败的 Cargo 编译边界。

本轮结束时：

- 现有八个 Capability binary、端口、HTTP 路径和用户行为不变。
- `a4n-capabilities` 从 workspace 删除。
- `a4n-service-protocol` 不再拥有八个具体服务的名称、能力版本、服务目录或按服务分派的策略表。
- `a4n-orchestrator` 只依赖它实际使用的 `a4n-prompt-client`，不再获得全部 Capability。
- `a4n-runtime` 虽然仍是当前 Host composition root，但只能显式依赖八个独立 client，不能再持有或向下传递全量 `A4nCapabilities` registry。
- 每个 Capability service 只依赖自己的 contract，绝不依赖任何 client crate。
- CLI 继续作为外部操作端调用 `a4n-server` Host API，不直接调用 Capability，也不计入 Final V5 的业务进程数。

这是当前最小且高杠杆的切片。它复用已经完成的八个真实 sidecar、进程测试、安全协议和 release packaging，不先创建一个违反目标约束的临时 Coordinator，也不提前引入尚无真实 owner 的 Domain 进程。

## 2. 为什么本轮不先拆 Coordinator 或 Domain

### 2.1 不先创建 Coordinator

当前仓库没有六个 Domain process，也没有对应的 Domain contract/client。若现在把 Host 改成调用一个新 Coordinator，新进程只能整体链接：

```text
临时 Coordinator
  -> a4n-runtime
       -> a4n-orchestrator
            -> a4n-db / a4n-core / a4n-domain
            -> a4n-capabilities
            -> 当前业务与 Provider crate
       -> a4n-capabilities / a4n-db / Provider adapter
```

这会形成“Host 变薄、Coordinator 变成分布式单体”的临时结构，并直接违反 Final V5 的约束：

- Coordinator 不能链接 Capability client。
- Coordinator 不能拥有业务 aggregate 或业务 schema。
- Coordinator 只能调用六个 Domain process。
- Coordinator 只能持久化 Saga/checkpoint，不应承载当前全部 Runtime 业务。

该路径后续必须再次迁移同一批业务代码，不是最短路径，因此本轮不做。

### 2.2 不先拆单一 Domain

当前 `a4n-core`、`a4n-domain`、`a4n-db` 和 `a4n-orchestrator` 仍是全局聚合 owner；Project、Platform 与四个产品域尚未拥有独立 schema role、projection contract 和 process client。

现在直接拆 Project 或 Platform，会同时触发：

- Host DTO 拆分。
- 身份、ACL 与项目 projection 签名。
- 全局 SeaORM entity 迁移。
- 跨 schema 事务拆分。
- Coordinator command/snapshot 合同。
- Runtime 启动与 migration owner 改造。

这不是一个可独立关闭的小批次。Final V5 自己给出的迁移顺序也是先拆 Contract/Client，再清理 Global Core，之后才建立 Project/Platform owner。

## 3. 当前代码事实

以下结论来自 2026-07-31 的工作区源码、Cargo manifest 和依赖树，不沿用旧计划中的历史数字。

### 3.1 Workspace 与进程现状

- 当前 workspace 有 42 个 crate。
- 已存在八个 Capability binary：

  1. `a4n-prompt-service`
  2. `a4n-llm-gateway`
  3. `a4n-embedding-service`
  4. `a4n-rag-service`
  5. `a4n-image-service`
  6. `a4n-video-service`
  7. `a4n-import-service`
  8. `a4n-export-service`

- Final V5 中的 `a4n-media-service` 尚不存在。
- Final V5 中的 Coordinator 和六个 Domain process 尚不存在。
- 当前发布包和 service catalog 都以八个 sidecar 为事实基线。

### 3.2 Host 仍是进程内业务宿主

`a4n-server` 与 `a4n-tauri` 当前都直接依赖：

```text
a4n-api-contract
a4n-core
a4n-runtime
a4n-service-protocol
```

`a4n-runtime::AppState::new_with_profile` 当前负责：

- 连接 PostgreSQL。
- 检查或执行启动迁移。
- 创建 `ServiceManager`。
- 构造全部 Capability client。
- 创建 `OrchestratorContext`。
- 注入 LLM、Embedding、RAG、Prompt、Image、Video、Import、Export 能力。
- 启动和关闭 managed sidecar。
- 恢复 cleanup、generation 与媒体生命周期任务。

因此 Entry 还没有达到 Final V5 的薄适配器目标，但本轮不通过增加临时 Coordinator 来掩盖这一事实。

### 3.3 `a4n-capabilities` 是当前聚合入口

`a4n-capabilities` 当前约 2,268 行，混合了四类职责：

- 八种 client trait。
- 八种 HTTP client 实现。
- 通用 HTTP/health/event-stream transport。
- 包含全部 client 的 `A4nCapabilities` registry。

生产依赖链为：

```text
a4n-server / a4n-tauri
  -> a4n-runtime
       -> a4n-orchestrator
            -> a4n-capabilities
       -> a4n-capabilities
```

另外 `a4n-runtime` 自身也直接依赖 `a4n-capabilities`，`a4n-test-support` 和 `a4n-llm-gateway` 的测试同样使用它。

`A4nCapabilities` 当前同时暴露：

```text
prompt / llm / embedding / rag / image / video / import / export
```

这使任何拿到 registry 的代码都能在编译期看见全部能力，与 Final V5 的 use-case 最小注入和 Domain capability allowlist 冲突。

### 3.4 `a4n-service-protocol` 仍知道具体服务

`a4n-service-protocol` 当前不仅包含通用 request/response、health、event、artifact 和 error，还直接拥有：

- 八个 service name。
- 八个 capability version。
- `service-catalog.json`。
- `expected_capability_version_for_service` 等全局 registry。
- 按具体服务分派的 secret、egress 与 resource policy。
- release manifest 数据结构。

这意味着新增、删除或改名任一 Capability 时，都必须修改所谓“通用协议”crate。Final V5 要求具体 Domain/Capability wire contract 归对应 owner，`a4n-service-protocol` 只保存真正稳定的跨进程原语，因此该职责需要在本轮开始收窄。

### 3.5 Server DTO 与 Client DTO 还不是同一合同 owner

当前六个 AI/媒体 service 的 wire DTO 位于 binary crate 内：

```text
a4n-prompt-service/src/contracts.rs
a4n-llm-gateway/src/contracts.rs
a4n-embedding-service/src/contracts.rs
a4n-rag-service/src/contracts.rs
a4n-image-service/src/contracts.rs
a4n-video-service/src/contracts.rs
```

Import/Export DTO 位于实现 crate：

```text
a4n-import-core/src/contracts.rs
a4n-export-core/src/contracts.rs
```

调用方多数仍通过 `ServiceRequest<serde_json::Value>` 和 `ServiceResponse<serde_json::Value>` 传输。Server 端的具体 payload 与 Client 端 trait 没有共同的独立 contract crate，因此 process test 能验证当前行为，但 Cargo 依赖无法证明双方使用同一类型 owner。

### 3.6 已完成且本轮不重复的范围

- 八个 sidecar 已有真实 binary、health、认证、资源限制、取消、错误终态和进程测试。
- sidecar profile 缺能力时会显式失败，不会静默回退 embedded。
- RAG 已迁移到 Qdrant；本轮不重做索引后端迁移。
- Host API、前端 Web/Tauri parity 和 CLI Agent 调用面已经存在。
- release package 已包含 Host、CLI、migration 与八个 sidecar。

本轮只改变 crate owner 和编译依赖，不重新设计这些已经工作的运行行为。

## 4. 本轮唯一目标依赖图

### 4.1 调用方

```text
current composition/use-case
  -> a4n-<capability>-client
       -> a4n-<capability>-contract
            -> a4n-service-protocol
       -> a4n-service-client
            -> a4n-service-protocol
```

约束：

- `a4n-<capability>-client` 只导出本服务的 trait 和 HTTP 实现。
- client crate 不 re-export 其他 client。
- client crate 不依赖 Provider、DB、Runtime、Orchestrator 或 service binary。
- `a4n-service-client` 只提供通用 HTTP、health、JSON、event-stream 与错误映射，不知道任何具体服务名称、路径或版本。

### 4.2 服务端

```text
a4n-<capability>-service
  -> a4n-<capability>-contract
       -> a4n-service-protocol
  -> 当前 application/core/provider adapter
  -> a4n-sidecar-bootstrap
  -> a4n-service-protocol
```

约束：

- service binary 不依赖自己的 client。
- service binary 不依赖其他 Capability client。
- HTTP adapter 负责 contract DTO 与当前 application/provider 类型之间的映射。
- 业务实现类型不能反向进入 wire contract。

### 4.3 控制面

```text
a4n-service-manager / a4n-cli / release scripts
  -> a4n-process-catalog
       -> 八个 a4n-*-contract 的 service descriptor
       -> a4n-service-protocol 中的通用版本/健康原语
```

`a4n-process-catalog` 是现有 service catalog 的正确控制面 owner。它组合各 Capability contract 提供的 service descriptor（含资源与安全策略）和 binary、地址、发布元数据；service identity/version/policy 仍由对应 contract 唯一拥有，catalog 不再另写一套常量。它不进入业务调用路径，也不成为 client registry。

## 5. 本轮 crate 变更清单

### 5.1 新增通用基础 crate

| Crate | 职责 | 明确禁止 |

| 现有 crate | 本轮动作 | 本轮结束状态 |

| `a4n-service-protocol` | 移出 catalog、具体 service registry、具体 policy 分派和 release manifest owner | 保留，但只完成“Capability-specific 信息清理”，不宣称全局纯化已结束 |

| `a4n-api-contract` | 不改名、不拆 Domain DTO | 保留 |

### 5.4 Contract 的内容边界

每个 contract 只允许包含：

- service identity 和 capability version。
- 业务 endpoint/path 常量。
- capability compatibility、resource policy、capability label、secret policy、egress data type 等服务特定的 transport/envelope 元数据。
- wire request/response DTO。
- 枚举、分页 cursor、状态与错误中稳定的 wire 值。
- serde/schema 测试 fixture。
- 构造通用协议校验所需的显式 contract descriptor。

每个 contract 禁止依赖：

```text
a4n-core
a4n-domain
a4n-db
a4n-runtime
a4n-orchestrator
a4n-capabilities
任何 Provider implementation
任何 service binary
SeaORM / Axum / Tauri / Reqwest
```

### 5.5 现有业务类型的处理

不能为了少写映射，让 contract 继续依赖当前重实现 crate。

具体规则：

- `a4n-llm-contract` 不依赖 `a4n-llm`；gateway/client adapter 映射 `ChatRequest`、usage 和 stream 事件。
- `a4n-image-contract` 不依赖 `a4n-image`；adapter 映射图片生成请求。
- `a4n-video-contract` 不依赖 `a4n-video`；adapter 映射 provider request、poll、status、delete 结果。
- `a4n-rag-contract` 不依赖 `a4n-rag-core`；稳定的 record/filter/search wire DTO 进入 contract，RAG service 内映射到 core 类型。
- `a4n-prompt-contract` 不依赖 `a4n-prompt`；PromptEntry、version、dependency graph 使用明确 wire projection。
- `a4n-import-contract` / `a4n-export-contract` 只保留 serde 数据；Base64/ZIP 转换和错误类型继续由 core/application adapter 拥有。

DTO 映射是边界适配，不是复制业务规则。校验规则若属于 wire 格式放 contract；若属于业务语义继续留在 application/core，禁止两边各实现一次。

## 6. 本轮必须建立的架构不变量

### 6.1 Contract 单一 owner

- 每个进程边只有一个 contract crate。
- client 与 server HTTP adapter 都使用同一 contract 类型。
- 不允许 binary crate 内继续存在同名公共 wire DTO。
- 不允许 `serde_json::Value` 作为已知业务 payload 的长期合同；只有真正开放结构的字段可以保留 `Value`。

### 6.2 Client 最小可见性

- `a4n-orchestrator` 正常依赖中只允许 `a4n-prompt-client`。
- `a4n-runtime` 当前允许八个 client，因为它仍是过渡期 composition root。
- 任一 Capability service 的正常依赖中不允许出现任何 `*-client`。
- `a4n-test-support` 的多 client 依赖只允许出现在测试边，不得被生产 binary 反向依赖。

### 6.3 禁止全量 registry

最终源码中必须同时满足：

```text
rg 'A4nCapabilities' crates   => 0
rg 'a4n_capabilities' crates => 0
rg 'a4n-capabilities' Cargo.toml crates/*/Cargo.toml => 0
```

不得创建以下替代物：

- `AllClients`
- `CapabilityRegistry`
- `RuntimeClients` 并向 application 公开全部字段
- `HashMap<ServiceName, dyn Client>`
- 兼容 re-export crate

composition root 可以在局部变量中同时构造多个 client，但必须立即注入只需要该 client 的 adapter/application，不能把全量集合存入 `AppState` 或 `OrchestratorContext` 后继续下传。

### 6.4 通用 transport 不知道具体服务

`a4n-service-client` 不得出现：

```text
prompt / llm / embedding / rag / image / video / import / export
```

对应的 service name、version 和业务 endpoint 必须来自具体 contract；health endpoint 属于控制面，由 process catalog 显式传给 health transport。

### 6.5 Protocol 不再按服务分派

本轮完成后，`a4n-service-protocol` 中不得保留：

- 八个 `*_SERVICE_NAME`。
- 八个 `*_CAPABILITY_VERSION`。
- `expected_capability_version_for_service`。
- `service_for_capability_version`。
- `required_secret_policy_for_service`。
- `egress_data_type_for_service`。
- `sidecar_resource_policy(service)` 形式的具体服务 match。
- `service-catalog.json`。

保留的 validation/compatibility 函数必须接收显式 expected version、secret policy、egress policy 或 descriptor，不能再访问隐藏的全局服务表。

### 6.6 安全和失败语义不退化

- `SIDECAR_AUTH_HEADER`、token 校验和非 loopback 约束保持。
- Provider secret policy 保持现有 allow/deny 行为。
- remote artifact 的本地路径拒绝保持。
- health 必须继续校验 service identity、protocol version 和 capability version。
- stream receiver 关闭继续映射为取消。
- timeout、错误码和敏感信息脱敏保持。
- 缺 client 必须显式失败，不能回退到 embedded。

### 6.7 不保留兼容壳

- 不创建继续 re-export 八个 client 的新聚合 crate。
- 不让 `a4n-capabilities` 只剩 deprecated wrapper。
- 不同时维护 typed 与 JSON 两套 endpoint。
- 不在失败时静默改走旧 client。
- 每个 Capability 完成迁移后，旧模块和旧 trait 在同一批删除。

## 7. 分批实施顺序

本轮按风险从低到高迁移。每一批都必须保持 workspace 可编译；可以使用连续提交，但本轮未全部完成前不把混合边界作为正式发布终态。

### 批次 0：建立事实基线与硬门禁

目标：先让本轮要删除的聚合边界和新增 crate 规则可自动检查。

改动范围：

- 新增 `scripts/checks/check-capability-boundaries.sh`。
- 新增 `scripts/checks/capability-client-allowlist.tsv`。
- 将检查接入 `.github/workflows/module-checks.yml` 的 Host/sidecar 边界 job。
- 记录八个现有 process contract 的 canonical request/response/event fixture。

门禁至少检查：

- contract 禁止依赖清单。
- client 只能依赖自己的 contract、`a4n-service-client` 和通用库。
- service binary 不依赖任何 client。
- 正常依赖与 dev-dependency 分开检查。
- `a4n-orchestrator` 的 client allowlist。
- `a4n-runtime` 的 client allowlist。
- 不存在 binary-to-binary Cargo 依赖。
- 不存在新的全量 registry 类型。

迁移期间使用一份只列当前旧边的临时 allowlist：批次 0 允许现存 `a4n-capabilities` 及其已知 consumer，但禁止新增聚合字段、consumer 或等价 registry；每完成一个 Capability 就在同批删除对应 allowlist 项，批次 7 删除这份迁移例外。不得用通配符、基线数量或“只要命中数没增加”掩盖旧边移动。

本批不改变运行行为。

退出条件：

- 门禁能对一个故意加入的非法依赖稳定失败。
- 删除故意违规后，当前基线通过。
- fixture 与现有 process test 使用的 JSON 一致。

### 批次 1：抽出 Process Catalog 与通用 HTTP Transport

目标：为八组 client 提供唯一通用基础，但不复制实现。

改动范围：

- 新建 `a4n-process-catalog`。
- 把 `crates/a4n-service-protocol/service-catalog.json` 移入该 crate。
- 把 `ServiceCatalogEntry`、catalog 读取和 release manifest 数据结构移入该 crate；`SidecarResourcePolicy` 等通用类型继续留在 protocol，按服务分派的具体 policy 随各 contract 迁移。
- catalog 搬迁阶段先保持现有 JSON 内容不变；后续每个 contract 落地时，将对应 Rust catalog entry 改为引用该 contract 的 service descriptor。
- 在同一 crate 内提供最小的 `export-catalog` 构建工具；为 shell/Ruby 脚本保留的 catalog JSON 改为它导出的受检投影，禁止手写第二套 service name/version registry。
- 新建 `a4n-service-client`。
- 把 `a4n-capabilities/src/transport*` 移入 `a4n-service-client`。
- `a4n-service-manager`、`a4n-cli`、Runtime managed sidecar 配置和 release scripts 改读新 catalog owner。
- 更新 `check-sidecar-package-inventory.sh`、`check-release-manifest.sh` 和相关 bundle 配置路径。

约束：

- `a4n-service-client` 暂时只提供通用 transport API。
- `a4n-capabilities` 在本批仍可依赖该 transport，作为后续逐服务迁移的临时调用方；transport 实现只能有一份。
- 不改八个 service 的端口、路径、版本或 package 清单。

退出条件：

- service catalog 仍为八项且 release manifest 校验通过。
- CLI local managed sidecar 构建清单与 catalog 一致。
- 八个现有 sidecar process test 不因 catalog/transport 搬迁发生行为变化。
- `a4n-service-protocol` 已不再拥有 catalog 和 release manifest。

### 批次 2：Import / Export 试点

新增：

- `a4n-import-contract`
- `a4n-import-client`

- `a4n-export-client`

迁移：

- 将 wire DTO 从 `a4n-import-core::contracts` / `a4n-export-core::contracts` 移入对应 contract。

- `a4n-import-service` / `a4n-export-service` 使用自己的 contract。
- Runtime project transfer、settings import/export 和 package IO 只接收具体 Import/Export client。
- 删除 `a4n-capabilities` 中的 package IO trait、HTTP client、builder field 和测试。

退出条件：

- Import/Export contract 不依赖对应 core。
- Import/Export process tests 使用独立 typed client 通过。
- ZIP 字节、checksum、重复 entry、未知字段和损坏 Base64 失败语义不变。

Prompt 的 DTO 风险低，但必须最后迁移：它是 `OrchestratorContext` 对旧 registry 的最后一个真实业务使用。先让旧 registry 随其余 Capability 迁移逐项缩小，最后迁 Prompt 并原子删除聚合 crate；不得把剩余 registry 搬到 `AppState` 或新建临时容器。

### 批次 3：Image / Video Capability

- Runtime image/video host adapter 直接持有对应具体 client。
- cleanup outbox 的 provider cancel/status 查询只注入 Video client，不接收全量 registry。
- 删除 `a4n-capabilities` 中 Image/Video trait/client。

退出条件：

### 批次 6：Prompt 与聚合 crate 原子删除

目标：迁移最后一个 Capability client，同时删除全量 registry 和旧聚合 crate，不留下空壳。

新增：

- `a4n-prompt-contract`
- `a4n-prompt-client`

迁移：

- 将 Prompt render/list/get/version/diff/dependency/override 等 wire DTO 移出 service binary。
- Prompt service HTTP adapter 映射 contract projection 与 `a4n-prompt` engine 类型。
- Prompt record application 只注入 `Arc<dyn PromptClient>` 或无 sidecar 时的明确不可用 port。
- `OrchestratorContext` 删除 `A4nCapabilities`，只保留 Prompt use-case 所需的显式 port。
- 删除已经无调用方的 `AppState::capabilities()` 与 `OrchestratorContext::capabilities()`。
- 删除 `a4n-capabilities` 中最后的 Prompt trait/client 后，立即删除整个 crate、workspace member、Cargo.lock package 和旧 module-check 入口。
- 测试 fake 改为分别实现具体 client trait；禁止创建测试专用全量 registry 再流回生产构造器。

退出条件：

- `cargo tree -p a4n-orchestrator -e normal` 中只出现 `a4n-prompt-client`，不出现其他 Capability client 或 `a4n-capabilities`。
- Prompt service/client 共用同一 DTO owner。
- registry、override、version history、dependency graph 和 unknown field process tests 通过。
- 缺 Prompt sidecar 时仍显式失败，不走 embedded fallback。
- `crates/` 源码、workspace/Cargo manifest、Cargo.lock 和脚本中的 `a4n-capabilities`、`a4n_capabilities`、`A4nCapabilities` 命中为 0；历史架构文档中的名称不计入源码门禁。
- 没有兼容 re-export、空壳 crate 或旧 JSON client 路径。

### 批次 7：收窄 Protocol 并冻结最终边界

目标：删除最后的具体服务全局表，完成 catalog 投影和 Cargo closure 硬门禁。

删除：

- `a4n-service-protocol` 中八服务 registry、具体 policy match 和按 service name 隐式查找 compatibility/validation 的入口。
- 批次 0 为旧聚合边建立的全部迁移例外。
- catalog JSON 中任何不能由 contract descriptor 或 process metadata 导出的手写字段。

替换：

- `a4n-service-protocol` validation 改为接收具体 contract 提供的显式 descriptor。
- `a4n-service-manager` 从 process catalog 获取期望的 service/version/resource 元数据。
- `a4n-process-catalog` 的八个 entry 全部引用对应 contract descriptor，并由 `export-catalog --check` 固定投影。
- module check 增加 contract/client/process-catalog/service-client 目标。

退出条件：

- `a4n-service-protocol` 中不再存在八项 service identity/version 常量、按 service name 分派的 policy/compatibility registry 或 catalog owner。
- catalog、package inventory、release manifest 与八个 contract descriptor 一致。
- 本轮所有 Cargo closure 门禁、八项 process test、Host check 和 release manifest check 通过。

## 8. 每个服务迁移时的固定步骤

为避免八次迁移产生八种风格，每个 Capability 严格使用同一顺序：

1. 从现有 process test 提取请求、响应、错误和 event fixture。
2. 创建 `*-contract`，迁入该服务的 identity/version/compatibility/resource/secret/egress descriptor，并先用 fixture 证明序列化结果完全一致。
3. 让 service HTTP adapter 使用 contract DTO，并删除 binary 内旧 DTO。
4. 创建 `*-client`，复用唯一 `a4n-service-client` transport。
5. 将调用方从聚合 trait 改为具体 trait。
6. 运行该服务的 unit + real process test。
7. 删除 `a4n-capabilities` 中对应模块、trait、field 和测试。
8. 运行 Cargo closure 门禁，确认没有反向依赖。

禁止先复制 DTO、保留旧 DTO 等全部调用方迁完后再清理。每个服务批次必须完成 owner 切换和旧 owner 删除。

## 9. API 与版本迁移策略

### 9.1 默认不改变 wire

本轮是 owner/依赖迁移，不是 API 重设计。以下内容默认保持：

- URL path。
- HTTP method。
- JSON 字段名。
- enum tag/rename。
- unknown field 策略。
- capability version。
- error code。
- event kind 与顺序。
- body limit、timeout 和并发预算。

若迁移过程中发现当前 client 与 server 已经存在真实 wire 不一致：

1. 先用 process test 固定实际行为。
2. 判断哪一侧违反当前公开合同。
3. 若能在不改变 wire 的情况下统一 owner，直接修正内部映射。
4. 若必须破坏 wire，只升级该 Capability 的 major version。
5. 不增加旧版 endpoint、双序列化或自动 fallback。

### 9.2 Typed contract 规则

- 当前 wire 已定义为封闭的结构继续使用 `#[serde(deny_unknown_fields)]`；是否封闭以现有 process fixture 为准，本轮不得借 DTO 搬迁改变 unknown-field 策略。
- request/response 顶层继续使用 `ServiceRequest<T>` / `ServiceResponse<T>`。
- contract DTO 必须 `Serialize + Deserialize`，必要时增加 `schemars`，但不为没有消费者的 schema 提前加依赖。
- `serde_json::Value` 仅用于明确开放结构，例如 Provider options 或自由 metadata。
- 不把数据库 schema version 填入 Capability request；Capability envelope 继续保持 protocol-only。

### 9.3 本轮不扩展通用请求 envelope

Final V5 要求未来请求携带 `caller_service`、`caller_layer`、deadline、idempotency key 和 principal/tenant/project scope。当前尚无真实 L2/L3 process identity，提前加入并强行填入伪造 layer 只会形成临时合同。

因此本轮：

- 保留当前 request/trace/project/secret envelope 行为。
- 不伪造 Coordinator/Domain caller。
- 在建立第一个真实 Domain process 时，再一次性增加 caller identity、deadline、audience 和 runtime edge 校验。

Provider 已有的显式 idempotency key 继续保留在对应 capability contract 中。

## 10. 数据、事务与 Artifact 边界

本轮不改变任何数据库 owner，也不新增 migration。

必须保持：

- Capability process 不写业务 PostgreSQL。
- RAG 业务真相源仍是 PostgreSQL，索引仍由 Qdrant 持有。
- Import/Export 仍只做转换，不持久化项目业务对象。
- Image/Video 仍只返回结果或当前 Artifact/bytes 合同，不接管业务媒体绑定。
- `ArtifactRef` 的校验、checksum、TTL 和 remote local-path 拒绝保持。
- Runtime/Orchestrator 的现有业务事务边界不因 DTO 移动而改变。

若 contract 提取暴露出某 service 正在直接使用业务 DB 类型，本轮只通过 adapter DTO 映射解除编译依赖，不借机迁移数据库 schema。

## 14. 回滚策略

本轮无数据库迁移，因此不需要数据回滚。

代码回滚原则：

- 每个 Capability 作为独立提交单元；若 process test 未通过，回退该服务整个 owner 切换。
- 不通过保留旧 client 并运行时选择来实现回滚。
- 本地发布包继续要求 Host 与八个 sidecar 原子版本一致。
- remote rolling 只有 wire 完全不变或同 capability major 兼容时才允许混合版本。
- 若必须提升 capability major，先单独写兼容/发布计划，不在本轮临时加入多版本 router。

Catalog 搬迁失败时，回滚 catalog owner 的单次提交；不能同时读取新旧两个 catalog 路径。

## 15. 主要风险与控制

### 风险 1：只是把聚合 crate 改了名字

控制：最终门禁禁止任何包含全部 client 的 registry、re-export 或 map；`a4n-capabilities` 必须物理删除。

### 风险 2：Contract 反向依赖重实现

控制：Cargo 门禁禁止 contract 依赖 core/provider/DB/Host；LLM、RAG、Image、Video 必须通过 adapter 映射。

### 风险 3：Typed DTO 改变现有 JSON

控制：每服务先固化 fixture，再迁 server，再迁 client；字段名、tag、默认值和 unknown field 行为逐项比较。

### 风险 4：通用 transport 再次膨胀成聚合层

控制：`a4n-service-client` 禁止具体服务名、endpoint 和 client re-export；只允许 transport 原语。

### 风险 5：Protocol 仍是隐藏的全局 registry

控制：删除全部具体 capability constants/match；generic validation 接收显式 descriptor。

### 风险 6：AppState 换一个名字继续保存全部 client

控制：composition root 构造后立即注入具体 adapter/application；结构检查禁止生产状态对象出现八 client 集合。

### 风险 7：测试全部迁到 `a4n-test-support` 后掩盖生产边界

控制：contract/client 自己拥有 unit/fixture test；service 自己拥有 process test；test-support 只提供 fake 和进程 helper。

### 风险 8：新增 crate 导致编译反馈退化

控制：所有新 contract/client 必须是轻依赖；复用现有 build-feedback 方法和 25% ceiling，不新增 codegen framework 或 schema registry 服务。

### 风险 9：破坏 embedded/full profile

控制：本轮不删除 embedded feature；sidecar 与 full 两条现有构建都要 check。运行时仍禁止 sidecar 缺失后自动回退 embedded。

## 16. 本轮明确不做

以下内容全部延期，不能作为本轮“顺手优化”：

- 不创建 `a4n-app-orchestrator-service`。

- 不拆 Project/Platform schema。
- 不实现 owner-signed Principal/Project/Domain projection。

- 不实现 Saga PG、lease、cursor long polling 或 Broker。
- 不新增 `a4n-media-service`、`a4n-artifact-store` 或共享对象存储。
- 不重命名 `a4n-api-contract` 为 `a4n-host-contract`。
- 不拆 `a4n-server-http-adapter` / `a4n-tauri-ipc-adapter`。
- 不删除 `a4n-runtime`、`a4n-orchestrator`、`a4n-core`、`a4n-domain` 或 `a4n-db`。
- 不把 `a4n-sidecar-bootstrap` 仅为目标命名而改名为 `a4n-process-bootstrap`。
- 不删除 embedded/full 构建路径。
- 不引入 Broker、服务网格、gRPC、Protobuf 或新的配置中心。
- 不重复 RAG/Qdrant 迁移。
- 不让 CLI 绕过 Host 直连 Capability。

## 17. 本轮最终完成定义

只有以下条件全部满足，才能宣布本轮完成：

1. 八个 Capability 都有独立 contract 和 client crate。
2. 八个 service binary 与调用方共用对应 contract DTO。
3. `a4n-capabilities` 已从源码、workspace、Cargo.lock 和脚本删除。
4. `A4nCapabilities` 及任何等价全量 registry 为 0。
5. `a4n-service-protocol` 不再拥有八个具体服务 registry、catalog 或具体 policy match。
