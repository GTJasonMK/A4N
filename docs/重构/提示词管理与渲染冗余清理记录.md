## 搜索起点与覆盖范围

以“用户在设置页查看、编辑、重置、校验、渲染和管理提示词”为功能起点，按广度优先顺序检查：

1. 前端入口：提示词列表、分类导航、编辑器、版本历史、项目覆盖、变量校验、直接渲染、A/B 渲染和依赖关系面板。
2. 前端 API：`frontend/src/api/prompt/` 的查询、变更、版本、覆盖、校验和渲染调用，以及生成的 Host command/type 合同。
3. Host 合同：`a4n-api-contract` command manifest、Rust 到 TypeScript 生成器、Tauri command/registry、Web dispatch/front route 和认证用户注入。
4. Runtime：`actions/prompt_records.rs`、settings-all Prompt host port、RuntimeProfile、当前用户与脱敏 runtime snapshot 传递。
5. Orchestrator：Prompt Host DTO 投影、Sidecar/embedded 选择、项目权限、项目覆盖持久化与回滚、默认模板重载和退役覆盖清理。
6. Capability：typed `PromptClient` trait、HTTP client、typed transport、请求上下文和响应反序列化。
7. Prompt Sidecar：Axum 路由、读写 handler、服务协议校验、认证、body/concurrency policy、进程测试和 Git 数据目录 manifest。
8. Prompt 引擎：`PromptEngine`、`PromptEntry`、`PromptCategory`、Tera 渲染、注册表、变量校验、版本历史、批量更新和项目覆盖。
9. 隐式依赖：prompt registry YAML、模板文件路径、settings-all 导入回滚、结构化输出修复中的 PromptRenderer、Tauri 注册表和 Web 命令路由表。
10. 横向检查：Rust、TypeScript、生成合同、测试、脚本、文档和配置；未发现相关 XML、反射调用、动态代理、AOP 切面或额外生产路由。

## 活跃调用拓扑

```text
提示词列表 / 分类 / 编辑 / 版本 / 校验 / 渲染
  -> settings Prompt UI
  -> typed frontend API
  -> generated strict Host contract
  -> Tauri command or authenticated Web dispatch
  -> Runtime creates PromptExecutionContext
  -> Orchestrator selects exactly one execution path
       -> Sidecar profile: typed PromptClient
            -> typed ServiceRequest<T>
            -> Prompt Sidecar route/handler
            -> TeraPromptEngine
            -> typed ServiceResponse<T>
       -> Embedded profile: the same PromptEngine operations directly

依赖关系面板
  -> already loaded PromptEntrySummary[]
  -> selected.dependencies
  -> reverse projection from entries whose dependencies contain selected.name
  -> no additional Host commands or network requests

项目覆盖
  -> Editor permission check
  -> canonical prompt existence check
  -> runtime override update
  -> DB persistence
  -> persistence failure performs explicit transactional rollback
  -> Host response exposes only prompt_name + updated_at
```

## BFS 关键证据

- `PromptClient`、HTTP transport 和 Prompt Sidecar 已全部使用 route-specific typed request/response；旧 Orchestrator 仍把这些类型降级成 `ServiceRequest<Value>`，再对成功 payload 二次反序列化。
- Prompt Sidecar 没有 dependency-graph route，typed `PromptClient` 也没有 dependency-graph method；旧 Runtime/Orchestrator 图接口没有 Host manifest、Tauri、Web、前端或 CLI 消费者，是不完整的孤立旧实现。
- 前端加载提示词时已取得所有条目的 `dependencies`，正向依赖与反向依赖可从同一列表确定；原实现仍额外发出两个 Host 请求并在后端重复扫描同一数据。
- `a4n-api-contract::prompt` 已是 Host 生成类型的事实来源，但 Orchestrator 又维护一套字段漂移的 Host DTO：额外暴露 `modified_at`、`content_snapshot`、项目覆盖 `project_id/content`，并存在独立 `AbRenderInput`。
- `PromptEngine` 已提供 `categories()`，旧 context 仍直接读取已退役的 `registry()`；`PromptEntry` 已携带依赖数据，旧 `DependencyGraph` API 已从引擎删除。
- Prompt renderer 的异步包装最终只调用同步 Tera `render`，没有 I/O 或不同语义；结构化修复路径是该包装唯一直接调用者。

## 当前事实标准

Host Prompt DTO 只定义在 `a4n-api-contract::prompt`；Sidecar Prompt DTO 只定义在 `a4n-prompt::contracts`；Prompt 执行只走 typed Sidecar 或 embedded PromptEngine 之一。设置页依赖关系只从已加载的 Prompt 列表投影，不再存在独立依赖查询协议。Prompt 分类只由 `PromptEngine::categories()` 提供，版本完整快照与项目覆盖内容只留在内部业务层，不通过 Host 泄露。
