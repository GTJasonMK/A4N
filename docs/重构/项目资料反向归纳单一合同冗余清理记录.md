# 项目资料反向归纳单一合同 BFS 冗余清理记录

日期：2026-08-14

## 结论

本专项从项目详情页“项目资料归纳”功能出发，按 BFS 逐层覆盖故事蓝图、章节大纲、分部大纲三种目标的预览、执行、恢复、确认、取消、正式资料事务、项目状态推进、事件发布与 RAG 派生索引同步。

BFS 确认核心冗余是同一能力长期存在三套 Host 命令、三套预览命令、两处前端执行入口、前端自行解释通用 workflow JSON、Runtime 重复 DTO 与动态响应修补，以及 checkpoint candidate 重复保存 workflow 已经拥有的身份字段。

本批将反向归纳收敛为四条强类型命令：

```text
reverse_engineer
preview_reverse_engineer_request
get_reverse_engineering_candidate
confirm_reverse_engineering_candidate
```

三种业务目标只通过唯一 `ReverseEngineeringTarget` 区分。执行、预览、恢复和确认统一返回 `ReverseEngineeringCandidate`；候选结果始终携带完整归纳输出，前端不再拼装 workflow、checkpoint、artifact 或确认响应。

未新增兜底、兼容转换、旧命令别名、回退路由、占位状态、第二套 DTO 或静默修复。

## BFS 调用拓扑

### 用户入口

```text
NovelDetail
  ├─ OverviewTab / SynopsisCard
  │  └─ “前往导入/归纳” -> 切换到 ImportsTab
  └─ ImportsTab / ImportToolsPanel
     ├─ 查看模型请求
     ├─ 归纳正式蓝图
     ├─ 生成章节大纲候选
     ├─ 生成分部大纲候选
     └─ 恢复并确认最近候选
```

概览页不再拥有第二套蓝图归纳状态、任务 ID、取消、进度、错误和结果解释逻辑。

### 执行路径

```text
ImportsTab
-> frontend/src/api/import/reverse.ts::reverseEngineer
-> apiInvoke("reverse_engineer")
-> Web/Tauri 通用 Host 分发
-> a4n-server 严格 envelope 解析
-> Runtime 一次 Editor 授权
-> Orchestrator 解析人工样本或项目自动上下文
-> PromptRenderer + prompts/_registry.yaml
-> 创建 import_reverse_engineer workflow 与输入指纹
-> LLM 结构化调用 / 截断检查 / schema 校验 / repair
-> workflow checkpoint + candidate artifact
   ├─ Blueprint：同一工作流内事务写入正式蓝图
   └─ Outline / PartOutline：返回 proposal，等待显式确认
-> workflow 完成与任务进度完成
-> 正式资料提交后的 RAG 派生索引同步
-> ReverseEngineeringCandidate
```

### 请求预览路径

```text
ImportsTab
-> previewReverseEngineerRequest
-> preview_reverse_engineer_request
-> 严格 ReverseEngineerInput
-> Runtime Editor 授权
-> Orchestrator 使用与正式执行相同的上下文解析和请求构建
-> ModelRequestPreview
```

预览不创建 workflow、不调用模型、不写 checkpoint、不修改正式资料。

### 候选恢复路径

```text
ImportsTab
-> getReverseEngineeringCandidate(project_id, target)
-> Runtime Project access 授权
-> Orchestrator 计算唯一 business_key
-> 查询最近 completed workflow_run
-> 校验 workflow kind / mode / project / target / 输入指纹
-> 查询并校验对应 workflow_checkpoint
-> 校验候选状态与输出 fingerprint
-> ReverseEngineeringCandidate | null
```

前端不再调用通用 `listWorkflowRuns`、`getWorkflowRunDetail`，也不再自行关联 run、checkpoint 和 artifact。

### 候选确认路径

```text
ImportsTab
-> confirmReverseEngineeringCandidate(workflow_run_id)
-> Runtime 从 workflow 解析项目并执行 Editor 授权
-> Orchestrator 事务锁定项目正式资料、workflow_run、workflow_checkpoint
-> 校验 workflow / checkpoint / target / 输出 fingerprint / 来源新鲜度
-> DB 唯一正式资料写入
   ├─ apply_reverse_outline_records
   └─ apply_reverse_part_outline_records
-> 更新 candidate state/apply_result
-> 必要时推进项目状态并发布内部事件
-> 提交事务
-> RAG 派生索引同步
-> 完整 confirmed ReverseEngineeringCandidate
```

确认只读取服务端 checkpoint 中的模型输出，不接受客户端上传候选 JSON，也不重新调用模型。

### Host 路径

```text
Web    -> a4n-server command dispatch
Tauri  -> invoke_host_command -> 同一 Server command dispatch
CLI    -> command_manifest -> HTTP Host command -> 同一 Server command dispatch
```

桌面、Web 和 CLI 没有各自的反向归纳业务实现。

## 入向引用闭包与冗余判定

- `reverse_engineer_blueprint`、`reverse_engineer_outline`、`reverse_engineer_part_outline` 仅以目标不同复制同一 Host、Runtime 和 Orchestrator 流程。
- 三个 `preview_reverse_engineer_*_request` 仅以目标不同复制同一预览流程。
- OverviewTab 的蓝图归纳与 ImportsTab 的蓝图归纳服务同一业务目的，却各自维护任务、取消、进度、错误、刷新和响应解析。
- Runtime `contracts.rs` 复制 API 输入并允许动态 `variables`，随后再转换为 Prompt 变量对象。
- `ReverseEngineerTaskScope` 只为重复授权后返回 project ID 和常量总数。
- Server 在任务注册前授权一次，Runtime 执行时再次授权同一项目。
- candidate artifact 中的 `candidate_id`、`workflow_run_id`、`target`、`origin` 与所属 workflow/checkpoint 重复。
- `already_confirmed` 是同一 confirmed 业务状态的传输分叉。
- `confirmed_at` 写入后没有读取者。
- Runtime 动态 warnings 修补会在类型错误时静默把原值重置为空数组。
- 前端 `parseReverseCandidateEnvelope` 重复 Rust serde/schema 校验。
- 前端 `reverseCandidateFromCheckpoint` 重复 Orchestrator workflow/checkpoint 关联、状态和 fingerprint 边界。
- 前端确认后把旧 `result` 拼回新响应，暴露了同一候选合同在不同命令间的字段分叉。
- `reverseBusy: "preview"` 实际表示正式归纳执行，与真正的请求预览状态重名。
- `success_message`、`cancelled_message` 在命令合并后无调用者。
- Prompt Registry 的三个旧 `used_by` 名称只描述已退役命令。

## 清理后唯一事实标准

```text
a4n-api-contract::import_reverse
  -> Rust Host contract
  -> Command Manifest schema
  -> generated host.ts
  -> Runtime / Server / Tauri / CLI / Frontend
```

```text
ReverseEngineeringTarget
  -> Prompt 名、请求文案、token profile、预览标题、进度文案
  -> Orchestrator 域映射
  -> 前端目标选择
```

```text
workflow_run + workflow_checkpoint
  -> 唯一候选身份、目标、输入指纹、模型输出和可变候选状态
  -> get/confirm 业务接口
  -> ReverseEngineeringCandidate
```

- 同一反向归纳能力只有一个执行命令和一个预览命令。
- 同一候选恢复只由 Orchestrator 解释 workflow/checkpoint。
- 同一正式资料写入只由 `a4n-db::import_reverse` 事务 owner 执行。
- 同一目标类型只由生成合同表达。
- 同一进度总数只由 API contract 常量表达。
- 同一候选状态只有 proposal/confirmed。
- 同一蓝图归纳入口位于 ImportsTab；概览页只负责导航。

## 明确保留的真实边界

### 蓝图自动应用与大纲显式确认

蓝图入口的产品语义是“归纳正式蓝图”，成功后直接事务写入；章节大纲和分部大纲需要先审阅候选再确认。两者共用请求、模型、checkpoint、候选和正式写入基础设施，但保留不同提交时机，不属于重复实现。

### RAG 同步警告

正式蓝图/大纲事务成功提交后才同步 RAG 派生索引。RAG 失败时：

- 正式资料已经持久化，不能把命令伪报为整体失败；
- 把错误升级为失败会诱导用户重复确认已提交的候选；
- RAG 是可重建派生数据，项目操作中已有显式重新同步入口；
- 警告保留原错误文本，不静默吞错，也不伪造同步成功。

因此 `warnings` 表达“正式资料已提交、派生索引未完全同步”的真实部分成功状态，不是默认值、旧格式兼容或业务回退。

### Workflow checkpoint 与 candidate artifact

workflow/checkpoint 保存不可替代的恢复与防篡改事实；candidate artifact 只保存候选自身可变状态。二者职责不同，不合并为客户端 DTO，也不删除持久恢复能力。
