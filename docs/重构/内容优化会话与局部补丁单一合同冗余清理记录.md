# 内容优化会话与局部补丁单一合同 BFS 冗余清理记录

日期：2026-08-14

## 结论

本专项从小说详情页“内容优化”功能出发，按 BFS 逐层覆盖会话创建与恢复、章节分析、普通对话、模型请求预览、三类 generation task、Agent Loop、局部补丁生成与审阅、正文写回、派生资料同步、取消、失败终态、项目删除/重置和数据库账本。

BFS 确认主要冗余是：15 条 Optimize Host 命令长期使用 opaque 或手工参数合同；前端重复发送 `userId`；Server 继续按动态 `projectId/chapterId/sessionId/content` 解包；API、Runtime、Orchestrator 和前端各自维护补丁与权限镜像 DTO；权限缺失时逐字段静默补默认值；对话权限在请求与会话之间回退；“确认应用”仅由客户端布尔值自证；待审阅补丁又被前端重新拼成第二种响应；丢弃补丁需要前端连续调用“记录事件”和“拒绝补丁集”，产生部分成功分叉。

清理后：

- `a4n_api_contract::optimize` 是输入、输出、权限和补丁 operation 的唯一合同源。
- 15 条 Optimize Host 命令全部使用严格 typed args/result，并统一归属 `optimize` domain。
- 三条 Optimize generation 启动合同继续复用同一 API 类型，不再接受可空权限。
- Runtime 不再拥有 Optimize 私有合同或转换层。
- 前端直接消费 `OptimizationPatchSetSummary`，不再构造 proposal 镜像。
- 丢弃待应用补丁由后端单一事务同时更新补丁状态并记录事件。
- 缺失或非法权限、非法数据库 operation 和未知字段全部显式失败。

未新增旧字段别名、兼容转换、默认权限回退、旧命令路由、异常吞掉、占位响应或第二套 DTO。

## BFS 调用拓扑

### 页面与会话入口

```text
NovelDetail / WritingDesk
-> OptimizeTab
-> useOptimizeSessionState / useOptimizeActions / useOptimizePatchReviewState
   ├─ 会话列表、会话详情、Turn、事件和 PatchSet 恢复
   ├─ 创建普通对话会话
   ├─ 创建或准备章节分析会话
   ├─ 请求预览
   ├─ 启动、取消和恢复 generation task
   ├─ 审阅并应用局部补丁
   └─ 丢弃待应用补丁
```

### 分析路径

```text
OptimizeTab
-> create_optimization_analysis_session / prepare_optimization_analysis_session
-> strict runtime input + authenticated Host user_id
-> Runtime optimization_analysis_variables
-> Orchestrator 章节权限与会话状态校验
-> content_optimization Prompt Registry
-> 项目/蓝图/大纲/角色/伏笔/相邻章节上下文
-> optimization_session + message ledger
-> start_optimize_analysis_generation
-> workflow / generation reservation / Agent Loop / checkpoint
-> issues、summary、Turn/Event 与 generation terminal
-> 前端通过 result_ref 和会话账本恢复
```

### 普通对话路径

```text
OptimizeTab
-> create_optimization_chat_session
-> SendOptimizationMessageInput { session_id, message, permissions }
-> start_optimize_chat_generation
-> Runtime generation worker
-> Orchestrator 使用本次请求唯一 permissions 构建上下文、提示词和 Turn snapshot
-> content_optimization_chat Prompt
-> think / get_project_information / edit_article / final
-> optimization_turn + optimization_turn_event
-> generation terminal + result_ref
```

对话上下文、提示词写回策略和 Turn 权限快照现在都使用同一个请求权限值；不再从会话权限静默回退，也不再出现“上下文使用请求权限、提示词却使用会话权限”的双来源。

### 补丁生成与应用路径

```text
OptimizeTab
-> start_optimize_patch_generation
-> ProposeOptimizationPatchesInput
-> Orchestrator 读取会话问题、权限和当前章节 hash
-> content_optimization_patch Prompt
-> 强类型 OptimizationPatchOperation
-> schema / 数量 / 长度 / old_text 唯一匹配校验
-> optimization_patch_set + optimization_patch
-> OptimizationPatchSetSummary
-> 前端逐条审阅或批量审阅
-> apply_optimization_patches
-> base_content_hash 并发校验
-> 唯一正文补丁应用器
-> 章节正文写入
-> RuntimeChapterAnalysisHostPort
-> postprocess_chapter_derived_data_validated
-> 派生资料与索引同步
-> PatchSet 标记 applied
```

### 丢弃补丁路径

```text
OptimizeTab
-> discard_pending_optimize_patch_sets
-> strict OptimizeSessionInput
-> authenticated Editor permission
-> 单一数据库事务
   ├─ 查询该会话所有 pending PatchSet
   ├─ PatchSet.status = rejected
   ├─ Patch.decision = rejected
   ├─ 保留 Patch.apply_status = pending（未发生写回）
   └─ 写入一条 agent_event
-> commit
```

前端不再先写事件、再逐个拒绝补丁集；任一步失败都会回滚，不存在事件已写但补丁仍 pending 的部分成功状态。

### Host 与生产入口

```text
Web
-> a4n-server /api/commands/{command}
-> characters/optimize/* strict dispatcher

Tauri
-> command_registry / invoke_host_command
-> 通用 Host command dispatcher

CLI
-> command_manifest / routing
-> HTTP Host command

Generation
-> /api/generation-tasks/{optimize-chat|optimize-analysis|optimize-patch}
-> Runtime typed start action
-> Orchestrator generation worker
```

Web、Tauri 和 CLI 没有各自的 Optimize 业务实现；差异只在 transport，最终进入同一 Runtime/Orchestrator 路径。

## 冗余判定

- API `OptimizationPatch` 与 Orchestrator `OptimizationPatch` 字段完全相同，只因模块历史形成两套类型。
- Runtime `contracts.rs` 只把 API DTO 逐字段复制成 Orchestrator DTO，没有独立业务规则。
- 前端 `Omit<..., "operation">` 再手写同一 operation 联合类型，重复生成合同。
- `ProposeOptimizationPatchesResponse` 与持久化 `OptimizationPatchSetSummary` 表达同一待审阅补丁事实，前端还需二次拼装。
- `confirmed_apply` 只由同一客户端在点击后发送，不能证明真实用户确认，也不能建立安全边界。
- Apply 响应的 `session_id` 和 `content_hash` 没有消费者；会话 ID 调用方本来就持有，正文 hash 只用于服务端并发控制。
- 权限 `Default`、serde 字段默认和逐字段 `unwrap_or(default)` 会把缺失/损坏数据伪装成合法权限。
- `permissions_override -> session permissions` 让同一次对话可能由两个事实源决定读取范围。
- Server Optimize 专用 session/project/content 手工解析绕过统一 strict typed envelope。
- `reject_pending_optimize_patch_sets` 只改状态；前端另调 `record_optimize_agent_event`，任何一个失败都会产生分叉状态。
- 事务收口后，`OptimizeApplication::pending_optimization_patch_sets` 与 Orchestrator wrapper 已无调用者，属于显性死代码。
- `OptimizationAgentPermissions::as_value` 手工列出全部字段，形成 serde 合同的第二份字段清单。

## 明确保留的真实边界

### UI 初始权限值

`createDefaultOptimizationAgentPermissions` 只负责新会话表单的可见初始选择；它不会在后端权限缺失、数据库损坏或请求字段缺失时兜底。后端所有入口仍要求完整权限对象，因此该 UI 初始值不是兼容或异常回退。

### 数据库存储字符串与 JSON

现有表继续以 JSON 保存权限、以字符串保存 patch operation，这是持久化 schema 边界。写入前来自强类型合同，读取时由 Runtime/Orchestrator 严格反序列化；非法值显式失败，没有旧格式转换或默认值。

### 三类 generation 路径

分析、普通对话和补丁生成具有不同输入、Prompt、状态机和 result_ref，保留三条 generation start 路由。它们共用 generation reservation、workflow/checkpoint、权限合同和 Agent Loop 基础设施，不是同一业务的重复实现。

### 正文写回 Host port

`OptimizePatchApplyHostPort` 隔离 Orchestrator 的正文事务与 Runtime 的派生资料后处理。它避免 Orchestrator 反向依赖具体 Host，并确保章节结构化分析、素材和索引同步仍经项目既有唯一入口；不是备用实现。

### 独立 Agent 事件命令

`record_optimize_agent_event` 仍用于取消等独立用户动作的可见账本。丢弃补丁不再调用它，而由 discard 事务内部写事件；两者触发场景不同。
