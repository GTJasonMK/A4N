一、结论

这份分析的方向基本正确：顶层入口应该从“项目类型”转向“创作起点/工作流”。“导入分析”不必作为独立的项目类型，它更适合作为文本项目内部的一种输入和分析方式。

当前真正需要解决的不是创建模式有几个，而是现有项目把创作过程建模成了一条固定的线性链路：

    draft -> blueprint_ready -> part_outlines_ready -> chapter_outlines_ready -> writing

这条链路适合“从想法开始创作”，但不能自然支持“已有设定开始写”“已有正文边分析边续写”“先写正文后补蓝图”等情况。

二、当前“AI辅助创作”和“自由创作”的实际区别

目前两者还不是持久化的项目类型，也没有不同的数据模型：

1. 前端创建 AI 项目和自由项目时调用的是同一个 createProject，参数相同。
2. 后端创建文本项目时统一保存为 project_kind=text、source_mode=self、status=draft，没有区分 AI/free 创作意图的模式字段。
3. AI 辅助创作创建后立即进入灵感对话；自由创作暂时留在项目列表，主要区别只有这一处导航行为。
4. 草稿项目再次打开时，当前路由逻辑仍可能把它送回灵感页，因此自由创作并没有真正绕开灵感流程。
5. source_mode=freeform 目前是画布项目语义，不能直接拿来表示文本项目的“自由创作”。

因此，保留两个入口可以作为用户体验上的起点选择，但不应该把它们固化成两个互斥的项目类型。用户可以先用灵感对话，之后导入正文；也可以先写正文，之后再使用灵感对话或反推工具。

三、三个用户场景与当前实现的匹配程度

场景一：只有想法，从灵感到正文。

当前支持较完整，现有“灵感对话 -> 蓝图 -> 分部/章节大纲 -> 写作”的链路与这个场景基本一致。

场景二：已有设定或大纲，希望直接辅助写作。

当前支持不足。自由创建不会收集用户已有的蓝图、角色和大纲；详情页也缺少完整的空白资料手工录入路径。部分编辑能力只有在蓝图存在时才开放，章节和大纲生成也有蓝图前置条件。因此用户虽然能创建“自由项目”，但还不能顺畅地从已有资料直接进入写作。

场景三：已有部分正文，边分析边续写。

当前有较好的基础，但流程仍偏线性。章节分析可以同步角色、场景、物品、伏笔等资料；导入分析和反推工具也能生成章节大纲、分部大纲和蓝图。但普通逐章分析主要更新局部档案，不会自动更新高层规划，而且没有蓝图时，状态机仍可能阻止后续大纲生成或写作。

四、对“蓝图”功能和时间性的修正建议

蓝图的核心功能不是对正文做回顾性总结，而是作为用户在当前创作阶段确认的全局创作依据。它用于统一主题、主线冲突、世界规则、人物目标和人物弧线，并为后续分部大纲、章节大纲和正文生成提供共同上下文。

“蓝图依赖完整小说”这个判断需要放宽：蓝图不必等整本小说完成后才能存在。用户可以在写作前建立蓝图，也可以在写作过程中根据当前资料重新整理和修订。关键不在于它是否覆盖完整小说，而在于它是否被用户确认，以及它对哪个时间点和资料范围负责。

不建议把“暂定蓝图”作为一种正式的蓝图类型。时间会改变蓝图的内容，但应通过版本和来源表示，而不是再定义一个临时蓝图：

1. AI 尚未经过用户确认的输出，是“蓝图提案/预览”，不是正式蓝图。
2. 用户确认后，形成当前正式蓝图版本，例如 V1；即使它只基于已有的部分资料，也仍然是蓝图。
3. 后续创作发生变化时，形成 V2 等新版本；旧版本保留为历史版本，必要时标记为过时。
4. 如果某个结果只是把已有正文总结成事实，它应归入章节分析或故事事实摘要，不能因为内容比较完整就自动称为蓝图。

正式蓝图版本至少应记录：

- 版本号和生效/生成时间；
- 来源范围，例如第 1 至第 5 章，或用户输入的设定；
- 来源内容的版本或指纹；
- 产生方式，例如手工、正向 AI、导入分析或反向推断。

未确认的提案可以有自己的工作流状态；但一旦称为蓝图，就应明确它是当前版本还是历史版本，而不是“暂定版本”。

同样，章节大纲也要区分“写作前计划”和“正文完成后的回顾摘要”。两者可以复用相同的结构，但不能在业务上默认等价。

五、项目资料保持自洽的基本规则

建议先确定以下不变量，再讨论具体页面和接口：

1. 已经写入正文的内容，是已发生的事实；分析结果不能静默改写它。
2. 用户手工确认过的蓝图、角色和大纲，不应被自动分析直接覆盖。
3. AI 分析和反推结果默认是“提案”；用户确认后才写入当前蓝图或其他正式资料的新版本。
4. 高层资料必须标明来源范围和新鲜度，能够判断它是否已经被后续正文过时。
5. 当正文、手工设定和 AI 推断发生冲突时，系统应显示冲突，不能用隐藏的优先级悄悄覆盖其中一方。

项目现有的蓝图版本、生成指纹和依赖图可以作为实现基础，暂时不需要立即引入一个庞大的通用知识图谱。

六、建议的产品形态

顶层保留三个入口：

- AI 辅助创作：直接进入灵感对话。
- 自主创作（也可以叫“从已有内容开始”）：进入项目详情/设置首页。
- 视频画布：进入画布工作台。

“自主创作”内部再提供几种起点：

- 从空白设定开始；
- 录入已有设定或大纲；
- 导入/粘贴已有正文；
- 新建空白章节直接写作。

这仍然只有三个顶层选择，但能够覆盖文档中的三种场景。

七、实施优先级（按最小改动排序）

P0：先修正用户路径（基础路径已完成）。

- 顶层只保留 AI 辅助创作、自由/自主创作、视频画布三个入口；导入分析已回到文本项目内部工具，不再作为第四种项目类型。
- 自主创作创建后已进入项目详情；草稿项目再次打开也不再一律跳转灵感页，详情页保留“继续灵感对话”入口。
- 详情页根据已有蓝图、章纲、正文和分析进度显示下一步操作，而不是只根据一个 status 选择固定路径。

P1：让自主创作真正可用。

- 已支持创建任意章节号的空白章节并直接手工写作；下一步是让无蓝图的 AI 章节生成以章纲或本章 brief 作为最低上下文。
- 提供蓝图、角色、关系和大纲的手工创建/编辑入口，让用户可以从已有资料直接开始。
- AI 补全和反推统一先形成可审阅候选，确认后写入正式资料或新版本；确认接口只能引用已保存候选，不能接受前端任意 JSON 或重新调用模型。
- 对正式资料与候选之间的字段冲突提供差异预览；用户明确确认后才允许更新可被修订的蓝图主体，用户拥有的角色、关系和章纲字段继续保留并显示冲突。

P2：处理非线性和来源一致性。

- 导入分析已经拆出章节分析、回顾性章纲、蓝图候选和分部大纲候选阶段；下一步是让这些阶段在界面上可单独重跑、审阅和撤回，而不把它们重新拼成线性门禁。
- 为所有正式蓝图/大纲版本统一记录来源范围、输入指纹、生成方式、生效时间和过期状态，并在详情页展示“当前/需复审/未知来源”。
- 为分部编号和章节范围增加项目内数据库约束，并审计历史重复数据；写入事务的行锁只能降低并发风险，不能替代约束。
- 将 status 降为项目进度摘要，功能前置条件改为按实际产物和来源新鲜度判断；补充 RAG 失败后的可重试/对账入口。

八、已经确定的原则与仍需决定的问题

已经确定：

1. 不建立“暂定蓝图”正式类型。未确认结果称为蓝图提案，确认后创建正式蓝图版本；时间变化通过版本、来源和新鲜度表达。
2. 导入分析和反推都遵循“正文事实 → AI 候选 → 用户确认 → 正式资料/版本 → 后续生成上下文”。未确认候选不进入正式生成上下文，也不推进项目状态。
3. 用户手工资料和已确认资料不被自动分析静默覆盖。反推蓝图的角色、关系采用补空并保留冲突；确认的蓝图主体字段可以形成新版本，但冲突展示和确认层级仍需产品定义。

仍需决定：

1. “自由创作”是否改名为“自主创作”或“从已有内容开始”；创建后的默认落点已经确定为项目详情。
2. 无蓝图时 AI 章节生成的最低上下文具体采用哪些必填字段；手工写作已经不再要求蓝图或章纲。
3. 蓝图主体字段冲突是否在一次确认中处理，还是要求差异预览后的二次确认。
4. 来源范围、过期状态、历史/未知 provenance 在界面中如何呈现，以及用户是否可以手动标记“继续有效”。

以上判断基于当前前端创建入口、项目路由、项目状态机、导入分析、反推工作流和章节分析实现。

九、本轮已实现（2026-08-08）

本轮先处理“正文事实不能被分析静默改成正式规划”这一核心不变量：

- 导入分析自动生成章节事实和带 `retrospective_analysis` provenance 的回顾性章纲；蓝图、分部大纲只保存为候选，不直接写正式资料。
- 导入蓝图/分部候选带 `origin`、项目标识、来源范围和输入指纹；候选确认从项目进度读取，不接受调用方上传 JSON。确认时锁定正文行再锁项目行，校验阶段完成状态、候选身份、正文章节集合/正文 SHA-256 和候选内容；正式资料与候选确认状态在同一事务提交，重复确认返回已有应用结果。
- 导入分析确认不会覆盖用户拥有的章纲；同来源且指纹变化的自动章纲才允许刷新，手工编辑会清除自动 provenance。分部大纲同编号或范围重叠时不覆盖已有正式记录，完全相同的记录可幂等复用。
- 非线性章节号按最高章节号计算规划范围，但只为实际有正文的分部桶生成候选；空档不被伪造成“已完成”的分部或同步来源。
- 反推结果保存为 workflow checkpoint 候选。候选 `candidate_id` 与 `workflow_run_id` 绑定，并校验 workflow、mode、project、status、step、business key、checkpoint 身份、target、候选 ID 和 output fingerprint；`apply=true` 旁路明确拒绝。确认只接收 `workflow_run_id`，从同一 checkpoint 读取结果，不重新调用模型，重复确认幂等返回。
- 反推自动上下文把样本来源 SHA-256 写入输入指纹；确认前重新计算，项目资料变化时返回 `reverse_candidate_source_changed`。前端按 target 映射候选，并在刷新/切换页面后从已完成 checkpoint 恢复待确认或已确认结果。
- 正式反推蓝图确认创建新蓝图版本；角色和关系只补空、保留冲突，并在同一事务内播种/补齐 protagonist profile，使后续上下文读取同一套角色资料。
- 角色时间线记录 `user`、`ai_sync`、`legacy_unknown` 来源。重同步只清理 `ai_sync` 事件/行为，RAG 删除 ID 来自实际删除结果；`current_state` 以 `base_attributes + 事件` 重建，并保护无法追溯 provenance 的顶层用户字段，事件重放不依赖未来快照或状态索引。AI canonical 字段按章节检查用户/历史归属；缺少 snapshot 不再阻止同步，蓝图播种保持顶层展示字段与 `current_state` 一致。
- 角色同步准备阶段记录每个来源章节的 ID、章节号、正文 SHA-256、标题和 `updated_at`；持久化事务锁定章节行并再次比较，正文、标题、时间戳或章节身份变化会在任何时间线清理/写入前返回 `character_sync_source_changed`。这些来源哈希同时写入 generation run 的 `source_refs_json`。
- 旧反推“生成并应用”旁路已停止，页面只生成反推结果，不会在第二次模型调用后直接写正式蓝图或大纲。章节重分析不会再自动删除本次未重复识别的伏笔，也不会因章节重写级联删除角色档案；这些记录保留给后续审阅或重建。

十、当前实现核对、剩余风险与下一步

截至 2026-08-08，资料同步的核心事务闭环已经能够满足“先确认、后入正式资料”的要求，但还不能说整个非线性创作体验已经完成。当前实现可以概括为：

    正文事实 → AI 候选 → 用户确认 → 正式资料/版本 → 后续生成上下文

已基本闭环的部分：

1. 候选不会再因为重试、刷新或并发确认而重新调用模型或重复写入；确认失败会显式返回过期、身份不匹配或冲突错误，不提供静默兜底。
2. 正文、候选和角色同步都有来源指纹/版本检查；写入前先锁定事实来源，发现变化就要求重新分析。时间线的 AI 清理、状态重建和 RAG 清理边界已经收敛到真实来源。
3. 蓝图版本、角色/关系合并和 profile seed 已能把确认后的资料传递到后续上下文；稀疏章节不会生成空档资料。

仍未闭环或需要产品/工程决策的部分：

1. 用户路径的第一层阻塞已经修正：顶层创建入口只保留 AI 辅助创作、自由创作和视频画布；自由创作创建后进入项目详情，草稿文本项目再次打开也不再被强制送回灵感页；写作台允许没有章纲时直接创建任意章节号并手工写正文。尚未持久化“创作起点/用户意图”字段，因此目前只能表达当前资料状态，不能完整解释用户最初为何创建这个项目；是否新增该字段应等实际产品展示或统计需求出现后再决定。
2. 蓝图主体字段的冲突策略尚未完全产品化。当前明确确认会创建新版本并更新主体字段，而角色和关系采取补空/保留冲突；尚缺字段级差异预览、冲突处理记录和统一的来源范围/生效时间展示，不能把“用户点击确认”误解为所有冲突都已被用户审阅。
3. 分部表还没有项目内编号/章节范围的数据库唯一约束；行锁能串行化主要写入，但历史重复数据和异常软关联仍需审计。角色时间线旧记录已用 `legacy_unknown` 标记；章纲等其他资料缺少 provenance 时只能按保守的用户/未知来源处理，不能事后推断为用户或 AI。
4. 章纲、角色同步、角色发现、场景、物体、伏笔和档案证据绑定的正式写入已经覆盖章节 ID、章节号、正文 hash、标题和 `updated_at`，工作流恢复指纹也纳入标题和更新时间。角色、场景、物体证据会在自己的事务中重新锁定来源章节，并验证 text-anchor 仍属于同一版正文。尚未闭合的是整批分析的全有或全无语义，以及 RAG 的当前正文版本门禁和完整重试/对账界面。
5. 伏笔重分析不再把“模型本次没识别到”解释成用户删除，且写入前会校验正文版本；但仍没有独立的用户确认、冲突处理和失效资料审阅界面。状态机也仍有若干线性门禁，可能影响“已有正文但没有蓝图”的部分 AI 生成路径。
6. 验证边界仍不完整：本环境没有配置 `A4N_TEST_DATABASE_URL`，尚未做 PostgreSQL 真实并发/锁顺序实测，也没有真实浏览器交互验证；前端生产构建和目标路由测试已经通过，数据库集成测试和完整浏览器流程仍需在完整环境补跑。
7. `PromptInsertedSegment` 视频操作目前仅收敛为显式“尚未接入专用 worker”的失败路径，未完成视频插入生成链路；这不是资料同步闭环的阻塞项，但不能在产品层显示为已支持。

下一步建议按以下顺序推进：

- P0：为 RAG 增加来源正文版本标识、写入前校验和失败后的重试/对账入口；检索时排除不对应当前正文版本的向量记录。
- P1：补字段级候选差异预览、冲突确认和来源状态展示；把蓝图/角色/关系/大纲的手工编辑入口接到同一套版本与 provenance 合同。
- P2：增加分部唯一约束和历史数据审计，补伏笔确认界面和 PostgreSQL/浏览器验证；再逐步拆除只依赖 status 的线性门禁。

十一、非线性资料同步 freshness 完善（2026-08-08）

本轮继续落实一个用户可以直接理解的不变量：用户点击分析后仍然可以继续修改正文，但旧分析不能因为模型较晚返回，就被当成新正文的正式资料。

已经完成：

1. 统一章节来源快照 `ChapterSourceSnapshot`，以项目、章节 ID、章节号、标题、正文 SHA-256 和 `updated_at` 共同描述一次分析所依据的正文版本。
2. 导入章纲和回顾性章纲在事务内锁定来源章节并重新比较快照；正文已变化时返回 `chapter_analysis_source_changed`，不写入旧章纲。
3. 场景替换、物体发现、角色发现和伏笔同步都增加 checked 写入路径。PostgreSQL 下先 `FOR UPDATE` 锁定来源章节，再写正式派生资料和 generation run；来源变化时分别返回明确的 source-changed 错误。
4. 角色发现创建新档案前校验来源版本；绑定到已有角色前也会重新预检。角色、场景和物体的 generation run 都记录来源标题、正文 hash 和更新时间，便于追溯结果到底基于哪版正文。
5. 角色/物体共享发现工作流以及场景同步工作流的恢复指纹加入标题和 `updated_at`。正文内容没变但标题或章节元数据已变化时，不再恢复旧 checkpoint。
6. 伏笔重分析不再删除本轮未重复识别的正式记录。一次模型观察不等于用户发出的删除指令；旧记录保留，等待后续冲突审阅或明确清理。
7. 角色、场景和物体的 text-anchor evidence 改用 checked 写入。每次绑定都会在同一事务中锁定全部来源章节，重新比较正文快照，并确认锚点的章节身份和 `source_version_hash`；正文或锚点来源已经变化时返回 `profile_evidence_source_changed`，不再挂接旧证据。

从用户创作方式看，这意味着系统不再要求用户为了等 AI 而停止写作。用户可以继续修改章节；最坏结果是旧任务被明确拒绝并提示重新分析，而不是让角色、场景、物体、伏笔或回顾性章纲悄悄混入新正文项目。

仍需继续处理的两个边界：

1. 当前保证的是“每一次正式写入都基于当时仍有效的正文”，不是“整批角色/场景/物体分析全有或全无”。一个批次包含多个档案时，前几个已成功、后一个因正文变化失败，可能保留已成功部分；只有产品确认必须整批撤销时，才值得引入更大的批量事务。
2. RAG 属于数据库外部副作用，无法只靠数据库事务解决。需要给向量记录携带来源章节版本，在上传前再次校验，并提供按项目/章节对账和重建能力；检索侧还应忽略已经不对应当前正文版本的记录。

十二、RAG 章节来源 freshness 第一阶段（2026-08-08）

本轮先闭合“旧章节资料不能继续进入 AI 上下文”这一层，不引入新的蓝图或资料类型。对用户而言，资料索引仍然只是当前正式资料的检索副本；正文和数据库资料才是事实来源。

已经完成：

1. 章节正文分块、章节摘要和章节分析 RAG 记录统一携带 `source_chapter_id`、正文 SHA-256 和章节 `updated_at`。RAG 记录自身的 `content_hash` 只表示该分块文本，来源章节版本使用独立字段，不再混用两个概念。
2. RAG 同步判断除分块文本、索引格式和 embedding identity 外，也比较来源章节版本。即使摘要或某个分块文字碰巧没变，只要它所依据的章节版本变化，也会重新写入 metadata，而不会错误地标记为 `Skipped`。
3. 服务端单章同步、批量同步和客户端向量写入在写入前都会重新读取当前章节来源版本；同步完成后再检查一次。用户在同步过程中修改正文时，任务会明确失败并要求重新同步，不会报告假成功。
4. 本地桌面 prepare→embedding→upload 协议为每条向量回传 prepare 时的 `content_hash`。上传时若当前 canonical 记录已经变化，整批在写入前拒绝，避免把旧文本向量与新文本、当前 hash 和当前 metadata 拼成一条看似有效的记录。
5. 章节生成 RAG 和增强检索在结果融合前按当前章节 ID、正文 hash 和 `updated_at` 过滤。来源不匹配、来源字段畸形，以及旧版没有来源版本的章节正文/摘要/分析记录都不会进入后续生成上下文。
6. 向量库写入仍然是数据库外部副作用，无法获得数据库事务级原子性；因此当前采用“写入前/后校验 + 检索侧最终过滤”两层规则。即使极小竞态窗口内旧向量已经到达向量库，它也不能继续被当前章节上下文使用。

当前边界：

1. 本阶段严格覆盖章节正文、章节摘要和由 `chapter:*` 记录族产生的章节分析结果。角色状态、属性事件、场景出场/位移等资料虽然带章节号，但现有表和 builder 还没有统一、可信的来源章节版本合同；不能仅凭章节号伪造 provenance。下一阶段应从这些正式派生记录的数据库来源字段开始补齐，再接入同一套 RAG 门禁。
2. 正式角色档案、蓝图、章纲和用户维护的伏笔不是章节分块副本，不能因为某章正文变化就统一判为过期。它们仍应按各自的版本、确认状态和来源范围决定新鲜度。
3. 目前用户可以从项目详情重新执行“同步资料索引”，错误也会明确提示重新 prepare/同步；尚缺按章节显示“当前、过期、缺失、写入失败”的对账界面，以及只重建单章/单类资料的产品入口。
4. 物体资料当前直接从数据库进入章节上下文，没有独立 `RagDataType` 和向量记录。这不影响本轮防止旧章节向量进入上下文，但若后续需要跨章语义检索物体，应先明确物体档案的正式来源和更新规则，再增加 RAG，而不是把场景 JSON 中的物体文字当成第二来源。

十三、章节生成资料上下文 freshness 第二阶段（2026-08-08）

本轮继续解决“用户可以非线性修改资料，但旧检索结果不能悄悄参与新正文生成”的问题。实现不新增候选上下文表、签名 token 或临时蓝图，而是缩小客户端能够提交的内容：客户端只负责本地 Embedding 计算，正式资料选择和上下文组装始终由服务端完成。

已经完成：

1. 章节生成和增强检索的内部执行入口现在必须显式接收当前章节来源版本映射，不再允许用 `None` 跳过 freshness。缺少来源、来源字段畸形或版本不匹配的章节记录会被统一排除。
2. `CharacterState`、`CharacterAttributeEvent` 暂时退出章节生成 RAG 白名单。它们尚未持久化可信的来源章节版本，继续放入 RAG 会形成无法证明新鲜度的第二来源；当前角色状态仍由数据库正式档案上下文提供。
3. 桌面本地 Embedding 链路由 `prepare -> finish context -> start` 改成 `prepare query -> local embedding -> start vectors`。`StartChapterGenerationInput` 不再接受 `client_rag_context` 裸字符串，原 `finish_chapter_generation_rag_context` Host 命令也已删除，因此客户端不能把任意文本伪装成资料检索结果注入正文提示词。
4. prepare 返回服务端生成的 query fingerprint。该指纹绑定项目、目标章节、实际查询文本、查询权重和 embedding identity；查询文本由当前章纲/本章简报、标题、待处理伏笔和相关检索输入生成。start 与 worker 都会重新构造当前查询并比较指纹，旧向量、字段缺失、维度错误、非有限数和 identity 不匹配都会显式失败。
5. worker 收到可信查询向量后，才用当前正式资料和当前章节来源版本执行检索。生成上下文同时绑定 freshness fingerprint，其中包含 query fingerprint 和所有可用前序正文章节的 ID、章节号、正文 SHA-256 与 `updated_at`。
6. freshness 在提交 LLM 前和模型返回后各复验一次。用户可以在任务运行期间继续修改正文或规划；一旦来源发生变化，旧结果可以流式展示，但不会作为新章节正文正式落库，任务会明确提示重新生成。
7. Qdrant 的 `SearchFilter.equals` 已与内存后端收敛：所有字段映射到真实 `metadata.<key>`，支持 null、bool、i64 和精确字符串；对象、数组、浮点数、不安全字段名及空 `data_types` 会显式报错，不再静默忽略过滤条件而扩大检索范围。

从用户创作方式看，这一阶段把“本机算向量”和“决定哪些资料可以参与创作”分开了：本机只做计算，正文事实、正式资料选择、新鲜度判断和提示词上下文仍由项目服务端规则统一拥有。用户不需要为了等待 AI 停止编辑；资料变了，旧任务失败并可重试，而不是生成一章看似成功但依据已经过时的正文。

当前仍需继续处理：

1. Qdrant 的嵌套 metadata 条件目前没有专用字段索引，语义正确但大项目下需要实测性能后再决定是否增加索引，不能为了预判性能复制一套顶层 metadata。
2. 角色状态、属性事件、场景出场/位移等派生资料仍需先在数据库层补齐可信 provenance，再逐类恢复 RAG；不能仅凭章节号推断它们来自当前正文。
3. 项目详情已有全量“同步资料索引”入口，但仍缺按章节/资料类型展示当前、过期、缺失和失败状态的对账界面，以及只重建单章或单类资料的入口。

十四、RAG freshness 有界补取（2026-08-08）

本轮继续处理一个会直接造成用户误判的问题：旧向量虽然已经被 freshness 过滤，但如果它们先占满向量库返回的 top-k，当前有效资料可能根本没有机会进入过滤阶段，界面和生成任务就会把“存在当前资料”错误表现成“没有命中”。

已经完成：

1. 章节生成 RAG 和增强检索统一改为“检索一批 → 过滤旧来源 → 当前结果不足时扩大检索范围”。补取只发生在初始结果确实被旧来源挤占、且向量库仍可能有后续候选时。
2. 补取采用明确上限：每次将 pull-k 翻倍，最多达到初始值的四倍且不超过 200；向量库已经返回不足一批、当前结果已达到原目标或到达上限时立即停止，不会无限扫描整个项目。
3. 服务端 Embedding 路径每个查询只计算一次查询向量，后续补取复用同一个向量；桌面本地 Embedding 路径继续复用客户端提交并已验证的查询向量。补取不会重复调用模型，也不会引入候选表、临时状态或第二套检索合同。
4. 新增回归测试模拟“初始 top-k 全是旧章节记录、当前记录排在后面”的情况，确认系统能继续拉取并只返回当前来源记录。

从用户创作方式看，这意味着用户重写前面章节后，即使旧索引尚未完成物理清理，后续章节生成仍能找到排在旧记录之后的当前资料；系统不会因为索引清理滞后而静默降低上下文质量。数据库正文和正式资料仍是事实来源，向量库只是可重建的检索副本。

当前边界：

1. 有界补取解决的是正确性和可用性，不替代物理对账与清理。大量旧记录会增加检索成本，仍应提供按项目/章节/资料类型查看当前、过期、缺失、失败并定向重建的入口。
2. 当前版本条件尚未完全下推到 Qdrant 查询，因为不同资料类型的 provenance 合同还未统一；在合同统一前，读侧最终过滤仍是防止旧资料进入生成上下文的必要门禁。
3. 真实 Qdrant 大项目下的补取次数、嵌套 metadata 性能和字段索引收益尚未实测。只有观测到明确瓶颈后再增加索引或下推条件，避免提前维护重复 metadata。

十五、资料同步无损重建与完整生成来源校验（2026-08-08）

本轮继续收敛两个用户不可接受的结果：一是“点了重建，失败后原索引反而没了”；二是“资料检索不可用或正式资料变化后，旧上下文生成的正文仍被保存成功”。

已经完成：

1. 桌面本地 Embedding 的重建不再在 prepare 阶段清空项目索引。`rebuild=true` 会把当前 canonical 记录全部标记为待上传；客户端完成全部向量计算后统一写入，成功后才清理已经不属于当前项目资料的旧记录。Embedding 或上传失败时，原索引仍保留。
2. 服务端一阶段强制重建在没有 staging collection/原子切换能力前显式拒绝，并提示使用普通同步；不再用“先删库再逐类写回”的方式制造空索引或半成品索引。普通同步仍会按内容、metadata 和 embedding identity 更新当前资料并清理各资料类型的旧记录。
3. 本地 upload 会按上传时重新构造的 canonical 集合计算所有当前 `Added/Updated` 记录，并在任何写入前验证客户端是否全部回传。少传、空传但仍有待更新项、重复 ID、越权 ID 或正文 hash 变化都会明确失败，不再把遗漏项反算成 `skipped` 后返回 `success=true`。
4. 增强检索保持 `data_types=None` 表示用户未指定类型；一旦调用方显式提交空数组或全空白数组就返回参数错误，不再把“请选择零种资料”静默解释为“搜索全部资料”。生成的 TypeScript 合同也已修复 nullable array，`data_types` 现在是 `string[] | null`，不再退化成 `unknown`。
5. 章节生成新增独立于 RAG 成功与否的完整 prompt 来源指纹。指纹覆盖项目/目标章节、正式章纲身份与版本、实际组装后的章纲/简报/角色关系/蓝图/伏笔等参考上下文、前文摘要/分析/角色状态/物体/场景上下文，以及所有前序正文的 ID、章节号、正文 hash 和更新时间；非线性补写时还会绑定最近一个后续已写章节的完整正文版本。
6. 该来源指纹在提交 LLM 前、模型返回后和 generation terminal 正式写入前各复验一次。Embedding 或向量库不可用只会跳过可选检索，不再同时关闭正文与正式资料的新鲜度校验；内部错误也不再伪装成“Embedding 可选不可用”后继续成功。
7. 客户端查询向量和服务端 Embedding 两条路径现在对向量库不可用采用同一语义：合同、身份、查询指纹和向量形状错误必须失败；纯向量库/Embedding 能力不可用可以跳过 RAG，但完整正式资料来源指纹仍然生效。
8. 正式正文保存事务统一锁定项目章节行、项目行和目标章纲集合。已有章纲的 ID/更新时间变化会拒绝保存；按简报开始生成后若用户新建了该章章纲，也不再把旧简报结果落库并留下不一致引用。

从用户创作方式看，这些规则允许用户继续非线性修改正文、角色和规划，同时明确区分“资料索引只是可重建副本”和“正式资料是生成依据”。同步失败保留上一版可用索引；生成依据变化则拒绝保存旧结果，不要求用户为了等待 AI 锁住整个项目。

当前边界：

1. 正式参考资料的最后一次完整来源复验已移到 terminal 写入前，但蓝图、角色、关系、伏笔、物体和场景的重读尚未全部使用同一个数据库事务和行锁；极小的复验后并发写窗口仍需通过统一 project source revision 或事务内 source snapshot CAS 彻底关闭。
2. 章节正文已提交并将 generation task 标为 completed 后才执行派生清理、样式/RAG 等后处理。后处理失败目前会让 workflow 失败并记录错误，但前端仍可能先显示“章节正文生成完成”；需要增加 `sync_pending/sync_failed` 投影和定向重试，或调整终态顺序。
3. 服务端强制 rebuild 需要 staging collection、完整性校验和原子切换后才能恢复；当前普通同步可安全更新，但不能强制重算 metadata 完全相同却物理损坏的向量。
4. `prepare_chapter_generation_rag_embedding` 和 RAG prepare/upload DTO 仍有部分定义在 orchestrator/runtime 与前端手写类型中，尚未全部收敛进共享 API contract；运行时校验已正确，但 schema/parity 对这些复合状态的表达仍偏弱。

十六、非线性补写的后续落点与资料检索降级可见性（2026-08-08）

本轮继续处理两个直接影响用户判断的问题：一是用户先写了后面的章节，再补写中间章节时，AI 不能只看前文而无视已经确定的后续落点；二是资料检索没有参与生成时，界面不能仍然只显示一句模糊的“生成完成”。

已经完成：

1. 章节生成从同一次项目章节读取中选择目标章节之后最近一个有有效正文的章节，作为“后续已写正文约束”。空正文和已删除章节会被忽略；目标第 5 章、已有第 10 和第 12 章时只选第 10 章，不把所有未来章节堆进提示词。
2. 后续约束独立于普通前序 RAG。RAG 仍然只允许检索目标章节之前的资料；后续章节只提供章节号/标题、可选摘要和约 600 字正文开头，并明确要求保留中间未写章节的创作空间，不得把后续事件当成本章既成事实，也不得提前揭露、复述或直接推进到后续章。
3. 原来“第 1 章直接返回”和“没有前文章节直接返回”的两个线性假设已经移除。即使项目只有第 10 章正文，用户补写第 1 章或第 5 章时，仍然可以得到后续落点约束；没有前文和后文时仍保持无上下文。
4. 后续约束被放在 16000 字章节连续性上下文的前部，避免长前文把它整体截掉。实际提示词只使用有界片段，但完整来源指纹会额外绑定该后续章节的 ID、章节号、完整正文 SHA-256 和 `updated_at`；即使只修改了 600 字截取范围之外的内容，LLM 前、返回后和 terminal 保存前三次 freshness 复验仍会拒绝旧结果。
5. 生成任务现在会公开资料检索的实际使用情况。未命中属于信息提示：“仅使用章节规划、正式参考资料和正文上下文继续生成”；Embedding、索引或搜索服务不可用属于警告：“本次不使用检索资料继续生成”。两种情况都会进入最终 completed summary。
6. 前端 generation reducer 会同时保存实时 completed 事件和恢复快照中的 summary，写作台成功提示优先展示后端结果；因此刷新、断线恢复或普通流式完成后，用户都能知道本次正文是否实际使用了检索资料。
7. 桌面客户端查询向量路径不再把 `ReadStoredMetadata` 之类的索引能力故障提前压成普通字符串硬失败。合同、查询指纹、Embedding identity 和向量形状错误仍必须失败；纯能力不可用则与服务端 Embedding 路径一致，跳过可选 RAG，但完整正式资料 freshness 继续生效。

从用户创作方式看，这意味着非线性写作不再被强行解释成“只能从第 1 章顺序写到最后”。已经写定的后续正文是一个需要兼容的落点，不是未来事实库，也不是新的蓝图类型；资料检索则是可选增强，是否真正参与了本次生成必须对用户透明。

当前边界：

1. 系统目前只选最近一个后续已写章节。若以后出现用户明确要求同时约束多个远期关键落点的场景，应先设计用户可选择的“连续性锚点”，而不是默认把所有未来正文塞进上下文。
2. `writing_context_before` 的最小压缩变体仍只保留内容 hash 和字符数；极端 token 压力下，实际连续性文字可能被压掉。若后续落点被产品定义为不可丢失的硬约束，应让最小变体保留精简落点，或在无法保留时显式拒绝生成。
3. terminal 最后一次来源复验仍通过普通连接完成，尚未在保存事务内锁定后续来源章节；复验后到提交前仍有极小并发窗口。长期应通过统一 project source revision 或事务内 source snapshot CAS 收口。
4. 章节正文 terminal 已完成后才执行派生后处理的问题仍然存在；本轮让 RAG 降级结果可见，但没有把后处理失败误报成功的问题伪装成已解决。

十七、必需创作上下文不能压缩成 hash（2026-08-08）

本轮修正了一个会直接破坏创作质量的错误抽象：hash 只能证明“来源有没有变化”，不能代替真正要交给模型阅读的创作资料。章纲、上一章结尾和已经写定的后续落点都是创作约束；即使 token 紧张，也不能只剩字符数和内容 hash。

已经完成：

1. 章节生成的 `full -> focused -> minimal` 三档上下文都保留真实章纲和连续性文本，不再把最小档退化成只有 hash 的审计信息。
2. 后续已写正文约束和上一章结尾进入 16000 字连续性上限的高优先区域。普通历史摘要可以继续裁剪，但本章必须承接的尾声和必须兼容的最近后续落点不能先被挤掉。
3. 后续章节仍然只是“兼容落点”，不是未来事实库，更不是暂定蓝图。提示词明确要求为中间未写章节保留空间，不得提前揭露或直接推进到后续章。
4. 完整来源指纹继续绑定真实来源正文、章纲和资料版本。hash 在这里负责防止旧结果落库，而不是替模型理解创作内容。

从用户创作方式看，系统允许先写第 10 章再补第 5 章：生成第 5 章时既能看到真实前文和章纲，也能看到第 10 章已经形成的落点；如果这些来源在生成期间变化，旧结果会被拒绝保存，而不是用 hash 冒充上下文继续生成。

十八、正文事实与派生资料同步采用双终态（2026-08-08）

本轮正式移除“正文生成成功就等于所有资料都已同步成功”的假设。用户最不能接受的是正文已经写好并落库，却因为 RAG、媒体文件或派生资料清理失败而被界面恢复成旧稿；同样不能接受正文已经变化，旧角色状态、场景或检索副本仍被当作当前资料继续分析和生成。

当前实现：

1. 正文是事实来源。手工编辑、单章导入、AI 正文生成、用户确认的优化补丁以及导入审核的接受/修改接受，会先把正文、数据库内派生资料失效处理、`chapter_content_sync` workflow run 以及 cleanup checkpoint 放在同一事务提交。计划无法持久化时正文也不会单独提交。
2. cleanup checkpoint 持久化本次实际清理产生的角色状态、属性事件、场景变更、需删除媒体路径等 artifact；章节 RAG 会先清理旧版本，再把当前正文分块和当前摘要同步回索引。进程退出或外部服务失败后，统一 workflow 恢复入口可以继续执行，不依赖内存任务。
3. 每一次正式保存都有独立 `sync_revision`，即使用户重复保存完全相同的正文，也不会复用正在执行的旧同步任务。`source_fingerprint` 只判断任务是否仍对应同一份正文事实；最新 workflow run 身份负责判断它是否已被后一次保存取代。
4. 新正文覆盖旧正文时，旧失败或未完成任务里的 cleanup artifact 会合并进最新任务并去重。旧任务失去恢复资格，但尚未完成的外部清理不会因为数据库记录已经被删掉而丢失。
5. 同章同步在当前单主机进程内串行执行。等待中的旧任务在执行外部删除前会检查最新 run；执行期间若又发生保存，完成前会再次检查，旧任务不会把自己标成当前版本已完成。多 worker 部署时再升级为数据库租约，不提前增加新表。
6. 正文保存成功后，派生同步失败只把 `chapter_content_sync` 标记为可重试失败，不反向把正文生成 workflow 宣告为失败，也不恢复旧编辑器快照。
7. 章节投影公开 `derived_sync_status`、workflow run ID、是否可恢复和错误信息。写作台与章节列表显示“资料同步中/失败”，失败时提供“重试资料同步”，同步中自动刷新。
8. 用户主动运行章节分析前必须确认当前正文对应的派生同步已完成。分析结果如何进入正式资料仍由角色、场景、伏笔等各自现有的确认与同步规则决定；正文保存后的同步只负责让旧资料失效和恢复基础索引，不制造新的暂定蓝图或第二来源。

这套状态关系应保持为：

`正文已保存` 与 `派生资料已同步` 是两个可分别观察的结果。前者成功后永不因后者失败而假装不存在；后者失败时必须显式可见、可重试，并阻止依赖当前资料一致性的分析继续运行。

当前边界：

1. 手工保存、单章导入、AI 生成、优化补丁以及导入审核的接受/修改接受，已经保证“正文 + 同步计划”同事务。整项目文本导入创建的是全新项目和全新章节，没有旧章节资料需要失效，但崩溃后可能缺少样式标签等可重建后处理结果。
2. 当前同章互斥是单进程锁。只有部署多个可同时处理同一数据库的 worker 后，才需要数据库租约或 advisory lock。
3. RAG 和文件删除是数据库外部副作用，无法获得普通数据库事务的原子性。checkpoint、幂等重试、来源 freshness 和检索侧最终过滤共同承担恢复与防旧数据使用；不能用“同步成功”布尔值掩盖这些边界。

十九、正文同步完成必须包含当前正文基础索引（2026-08-09）

本轮修正“资料同步完成只删除旧向量、却没有重建当前正文向量”的语义缺口。用户重写一章后，不应为了让后续 AI 找到这版正文，再到项目详情手工执行一次全量索引同步。

已经完成：

1. 正文保存产生的 `chapter_content_sync` workflow 输入显式记录 `sync_current_chapter_rag=true`。清理旧角色、场景、伏笔和章节向量后，同一可重试 workflow 会同步当前章节正文分块及当前摘要；只有两部分都成功才标记资料同步完成。
2. 重分析前的清理使用 `sync_current_chapter_rag=false`。它会删除旧章节分析向量，但不会在新分析开始前把旧 `analysis_data` 重新写回索引；新分析完成后仍由章节分析 workflow 同步新的正文、摘要和分析记录。
3. workflow 指纹升级为 schema 3，并保留 schema 1/2 的恢复兼容。旧任务没有明确同步意图时维持原行为，不根据章节字段猜测任务目的；新保存和新分析清理则使用显式输入。
4. 当前正文同步期间若正文再次变化，既有来源前后校验和最新 run 门禁会拒绝把旧任务标记为完成；最新保存创建的新 run 继续承担当前正文的索引同步。

从用户创作方式看，保存正文之后显示“资料同步完成”，现在同时意味着旧派生资料已经失效、当前正文的基础检索记录已经可用。用户仍需主动点击“分析”来生成角色、场景、物体、伏笔和回顾性章纲；保存动作不会擅自制造这些正式资料或蓝图。

当前边界：

1. 当前仍只有章节级总体同步状态，尚未提供按正文、角色、场景、伏笔等资料类型展开的对账视图。
2. Embedding 或向量库失败会保留正文并把 workflow 标记为可重试失败；不会把“旧资料已清理但新索引未完成”显示成同步成功。

二十、按资料类型对账，并区分“本次分析是否已落库”（2026-08-09）

本轮把“章节总体同步完成”进一步拆成用户真正需要判断的五类资料：正文基础索引、章纲与伏笔、物品档案、角色资料、场景资料。系统不再用一个总体布尔值替用户猜测每一类资料的状态。

已经完成：

1. 分析 workflow 的阶段 checkpoint 是分类型状态的唯一事实来源。只有 checkpoint 的正文指纹与当前章节完全一致、状态为 completed 且合同字段 `completed=true`，对应资料才显示“已完成”。正文变化后，旧 run 和旧 checkpoint 不再投影为当前资料。
2. 各类状态统一投影为 `completed`、`pending`、`running`、`failed`、`needs_analysis`、`unknown`。无法由当前来源指纹或 checkpoint 证明的情况显示“待核对”，不把旧资料或缺失记录猜成已同步。
3. 正文基础索引同时参考 `chapter_content_sync` 的显式意图：正文保存任务完成才代表当前正文索引完成；重分析前的清理任务完成只代表旧索引已失效，必须等分析输出 checkpoint 完成后才重新显示正文索引完成。
4. 章节列表显示简短的资料状态摘要，写作台分析页展开显示五类状态。失败状态保留工作流错误和恢复入口；用户可以据此决定重试资料同步、继续已落库的分析，或重新分析，而不需要猜测系统做到了哪一步。
5. 新增 `analysis_stored` checkpoint，明确证明本次模型结果已经写入章节。重新分析失败时，即使数据库里还保留上一次 `analysis_data`，恢复逻辑也不会把旧结果误当成本次结果继续同步；没有该证明时只能重新分析。
6. 章节列表读取当前分析 run 的 checkpoint 采用批量查询，不新增状态表、补偿队列、候选蓝图或第二套资料状态。
7. 分析运行期间不再阻止用户保存正文。分析落库使用正文、标题和章节 `updated_at` 做原子 CAS；后续各阶段继续使用同一来源快照校验。即使用户重复保存完全相同的文字，旧分析也会失败而不能回写。相同正文被再次保存并清空分析后，旧 completed checkpoint 不再显示为当前资料“已完成”。

从用户创作方式看，用户可以随时补写、重写、跳写章节，也可以在分析失败后继续编辑正文。系统向用户展示的是“这版正文下哪些资料已被确实更新”，而不是“某次任务曾经运行过”。分析仍由用户主动触发；保存正文只维护基础索引，不擅自生成蓝图或把分析提案当正式资料。

当前边界：

1. 对没有历史 provenance 的旧记录，状态只能显示“待核对”；系统不会事后推断它来自哪一版正文。用户需要重新分析或执行对应同步来建立可证明的来源。
2. 本轮提供章节级五类对账，尚未增加“只重建某一类资料”的独立按钮；只有当用户真实需要按类重试、且现有阶段能安全拆分时再增加入口。

二十一、清理任务发生后，旧分析 checkpoint 不再作为当前证据（2026-08-09）

本轮修正一个跨 workflow 的对账漏洞：用户点击重新分析后，系统会先提交角色时间线、场景记录和旧索引的失效计划。如果这次清理随后失败，新分析 workflow 还没有启动，旧的 completed 分析 run 与 checkpoint 过去仍可能被界面显示为“角色资料/场景资料已完成”，但对应数据库资料已经被本次清理改变。

现在章节投影会比较同一章节最近的 `chapter_content_sync` 与 `chapter_analysis` workflow 身份顺序：

1. 后发生的正文清理或分析前清理，会使更早的分析 run/checkpoint 失去当前资料证明资格；即使最近清理记录的正文指纹已经过期，这次清理仍然会使旧证据失效。旧分析正文仍可保留查看，但五类资料不会继续显示为已完成。
2. 统一恢复入口同样执行这项校验，不能再通过旧 workflow ID 绕过页面继续同步已经被清理改变的旧 checkpoint；此时必须重新分析。
3. 只有清理之后新建的分析 run 才能重新使用 checkpoint；恢复旧 run 不会因为 `updated_at` 被刷新而重新获得资格，必须重新分析生成新 run。
4. 该规则只组合已有 workflow run，不新增状态表、失效标记或补偿队列；正文、workflow 与 checkpoint 仍是唯一证据。

从用户角度看，“资料已完成”现在不仅要求正文内容和 checkpoint 指纹匹配，还要求这份分析证据没有被后发生的清理动作推翻。清理失败会明确显示失败/待核对，而不会用清理前的绿色状态掩盖当前缺口。

二十二、相同正文重新保存后，新分析必须使用新的 workflow run（2026-08-09）

本轮修正另一个会影响用户连续编辑的问题：章节分析 workflow 过去只用正文 hash 和标题作为输入指纹。用户在分析运行期间重复保存完全相同的文字后，正文版本已经变化，但立即重新分析仍可能复用旧的 running run，导致新旧模型调用争用同一个 workflow 状态和 checkpoint。

现在的规则是：

1. 正文与标题继续作为可比较的来源指纹；每次真正开始新的模型分析，额外生成独立的 `analysis_revision`，因此新分析一定创建新的 run。
2. 同一版正文已经有分析在运行时仍阻止重复启动，避免两个有效模型调用互相覆盖；如果用户在运行期间保存了正文，后生成的 `chapter_content_sync` 会使旧分析失效，此时允许为当前保存版本启动新分析。
3. “继续已保存分析的派生同步”不创建新 revision，而是直接恢复原 run，继续使用原 checkpoint。没有保存分析结果的失败任务重新执行模型时则创建新 run。
4. 旧版直接使用正文指纹的 workflow 仍可读取；新旧格式都由同一来源匹配函数处理，不新增状态表或迁移任务。
5. 启动分析与继续同步都会在现有同章资料锁内重新执行门禁并认领 run；模型返回后落库前再次确认该 run 仍是当前最新、仍晚于最近正文清理。在当前单主机进程内，重复请求不能同时通过，已被新分析或正文更新取代的旧模型结果也不能回写；多 worker 部署沿用正文同步的边界，届时再把同章锁升级为数据库租约。

从用户创作方式看，用户不需要等旧分析结束才能重新保存和继续工作；但系统会把“重新运行模型”和“继续同步已保存结果”明确区分，前者拥有新的运行身份，后者才允许复用旧 checkpoint。

二十三、正式资料所有权与证据失效审计（2026-08-09）

本轮不再继续增加状态，而是核对五类资料实际落库时是否真的遵守“正文是事实来源、用户资料不能被分析静默覆盖”。审计发现，章纲 provenance、物体/场景档案的保守字段合并以及角色属性事件来源已经基本符合要求，但仍有三处会破坏用户判断的真实缺口。

已经修正：

1. 角色删除候选补齐与属性事件、行为记录相同的 `source_kind`：`user`、`ai_sync`、`legacy_unknown`。历史记录迁移后统一标为 `legacy_unknown`，不会事后猜测来源。
2. AI 只能累计、回退和执行自己的删除候选。已有用户或未知来源候选时，AI 同步会保留原记录；用户明确提交候选时可以接管已有 AI 候选。章节重写和角色重同步只回退 `ai_sync` 候选，不再删除用户留下的判断。
3. 用户手工修改角色属性会清除该字段全部未执行删除候选，因为新的用户事实已经使旧候选失效；AI 更新属性只清除自己的候选，不能借“状态重算”删除用户候选。
4. 场景档案的首次/最近出现章节在分析刷新时只允许向外扩展，不再被当前一次模型识别出的较窄范围覆盖。场景的 `current_state_json` 仍按真实出场记录重建，因为它是明确的派生状态，不是用户可编辑档案字段。
5. 当前正文文本锚点重建前会先删除引用旧锚点的 `profile_evidence`。旧锚点 ID 被替换后不再留下看似存在、实际指向已删除正文证据的悬空记录；新分析必须基于当前正文锚点重新绑定证据。
6. 导入分析预览已跟随新的章节分析合同传入完整章节记录，而不是只传章节 ID，避免预览阶段绕过当前章节内容校验。

本轮明确没有增加的结构：

1. 伏笔索引目前没有用户创建或编辑入口，正式记录只由章节分析生成，因此“相同描述覆盖用户手工伏笔”的假设在当前产品中不成立。本轮不为假设场景新增伏笔 provenance 表；将来真正开放手工伏笔管理时，再把来源和确认语义一并加入。
2. 物体和场景档案仍采用“已有非空字段按用户拥有处理、自动分析只补空”的保守规则。它会让某些旧 AI 字段不能自动刷新，但比静默覆盖用户编辑安全；只有产品需要自动刷新 AI 字段时，才值得增加字段级 provenance 和冲突审阅。
3. 没有增加整批分析事务、补偿队列或通用知识图谱。当前继续保持每类正式写入来源校验、失败显式可重试和 checkpoint 对账。

从用户创作方式看，这一轮解决的是资料更新的所有权边界：用户可以重写正文、修正角色或调整场景范围，AI 仍能重建自己的派生数据，但不能把用户判断当成可回滚缓存；正文证据失效时，系统删除的是旧证据关系，而不是悄悄保留一个失去来源的“正式事实”。

当前边界：

1. 场景和物体档案缺少字段级来源，因此保守合并不能同时做到“自动刷新所有 AI 字段”和“绝不覆盖用户字段”。在出现真实冲突审阅需求前，不再增加猜测性结构。
2. 文本锚点的 PostgreSQL 集成回归需要配置 `A4N_TEST_DATABASE_URL`；无测试库环境只能完成编译、查询合同和单元规则验证。

二十四、角色初始资料与全部属性键的所有权补全（2026-08-09）

本轮继续核对角色同步后发现：属性事件虽然已有 `user / ai_sync / legacy_unknown` 来源，但门禁只覆盖性别、年龄、外貌、背景、性格五个摘要字段；同时，用户手工新建角色时填写的初始资料与角色发现生成的初始资料仍共用同一份 `base_attributes`，AI 无法判断哪些初始值可以继续自动更新。

已经修正：

1. 复用现有 generation run 判断角色初始资料来源，不新增角色来源表或字段。只有存在 `character_discovery` 正式生成记录、且当前没有同名正式蓝图角色时，初始属性才视为 AI 基线；手工创建、正式蓝图已有角色和无法追溯来源的历史角色都按用户资料保护。
2. AI 属性修改和删除门禁扩展到全部 `explicit / implicit / social` 属性键，不再只保护五个摘要字段。某个属性出现用户或历史事件后，从该章节起由用户拥有，后续 AI 事件不能静默覆盖或删除。
3. 非线性重放使用同一所有权规则：AI 发现角色可以重放自己的历史变化；手工/蓝图基线不会被旧 AI 事件改写；用户事件发生前的 AI 历史仍保留，用户接管后的冲突 AI 事件会被忽略。
4. AI 删除候选也经过同一属性所有权门禁，因此不能通过“连续缺失”绕过属性修改保护，间接删除用户或正式蓝图资料。

从用户创作方式看，角色工作台里的“新建角色”和正式蓝图不再只是给 AI 的初始提示，而是用户拥有的正式资料；角色发现生成的档案则仍可由后续章节分析持续演化。用户无需理解内部事件表，系统依据已有生成证据和实际编辑事件决定谁可以更新该字段。

当前边界：

1. 历史 AI 角色若缺少可验证的角色发现 generation run，会按未知来源保护。这可能减少自动更新，但不会为了追求自动化而猜测并覆盖资料。
2. 当前仍不增加字段级冲突审阅界面；AI 遇到用户拥有属性时显式拒绝该次写入。只有用户确实需要逐字段接受 AI 建议时，再设计候选差异和确认记录。

二十五、正文重写立即失效旧证据，AI 资料只凭当前事实进入创作上下文（2026-08-09）

本轮修正正文重写后的实际泄漏：旧章节锚点过去要等到下一次分析重建时才会被替换，因此用户已经从正文删除的角色、物品或场景，仍可能凭旧 `profile_evidence` 和档案范围进入后续章节生成上下文。

现在的规则是：

1. 正文保存、覆盖或删除在提交新的 `chapter_content_sync` 计划时，会在同一数据库事务中删除该章旧的当前正文锚点及其全部角色、物品、场景档案证据。旧证据从正文事实变化的那一刻起失效，不再等待用户重新分析。
2. 档案本身不会随正文重写自动删除。用户可能已经接管档案、绑定素材，或者只是把资料移到其他章节；真正删除仍走显式档案删除入口。
3. AI 同步资料要进入第 N 章的创作上下文，必须至少保留一条来自第 N 章之前有效正文的当前证据：锚点属于同一文本根项目和真实章节正文、不是来源快照、章节未删除且有正文、锚点章节身份一致，并且 `source_version_hash` 等于该章当前正文 SHA-256。旧正文 hash、未来章节证据或悬空锚点均无效。
4. 物品和场景使用档案当前 `ownership_kind` 判断是否需要机器证据；角色继续复用已有角色发现运行、正式蓝图和用户属性/行为/删除事件判断。手工角色、正式蓝图角色、用户已经接管的 AI 角色及历史来源角色继续作为正式资料保留。
5. 用户资料和历史来源资料不以“是否还在某章正文出现”作为隐藏条件。正文证据门禁只限制仍由 AI 同步拥有的派生资料，不能反向删除用户明确维护的设定。

从用户创作方式看，用户可以在第 1 章删掉一把不再存在的钥匙后直接续写第 2 章；系统不会继续把这把仍由 AI 同步拥有的钥匙塞进提示词。档案仍保留供用户审阅或复用，重新出现在有效正文并完成分析后又可参与续写。用户手工建立、正式确认或已经接管的资料不会因为缺少机器证据而被隐藏。

二十六、档案当前所有权与用户接管（2026-08-09）

生成运行只能说明“过去由哪次任务创建或更新”，不能证明档案现在仍然属于 AI。自动刷新也会改写 `updated_at`，因此不能用时间戳推断用户是否编辑过档案。本轮为物品和场景档案增加一个最小的当前所有权字段 `ownership_kind`，生成运行继续只负责历史追溯。

具体规则：

1. `user` 表示用户当前拥有；手工创建或任意手工编辑后立即进入该状态。
2. `ai_sync` 只在 AI 真正新建物品或场景档案时写入。AI 更新已有档案时保持原所有权，不能因为再次同步而夺回用户资料。
3. `legacy_unknown` 保护迁移前的历史档案。系统不根据旧生成摘要或时间戳猜测其来源，避免误伤已经被用户编辑过的资料。
4. 界面只读显示“用户资料 / AI 同步资料 / 历史来源”。这不是审核状态，也不制造“暂定资料”：档案始终是同一份档案，区别只在于它能否被自动更新，以及失去正文证据后是否仍参与续写。
5. 物品和场景的自动合并继续保留已有非空字段，只补空字段并扩展实际出现范围；在没有字段级来源的情况下，这是避免覆盖用户表达的保守边界。

当前边界：

1. 当前所有权按整份物品/场景档案计算，不能同时自动刷新一部分 AI 字段、保护另一部分用户字段。只有用户确实需要逐字段接受或拒绝建议时，再增加字段级差异审阅。
2. `profile_evidence` 和迁移的 PostgreSQL 集成回归仍需要配置隔离的 `A4N_TEST_DATABASE_URL`；无测试库环境只能完成纯规则、编译和合同验证。

二十七、本章正式资料与非线性场景状态边界（2026-08-09）

继续从用户实际写作顺序核对后发现两个线性假设：物品和场景查询只接受“首次出现章早于目标章”，因此用户为第 1 章或当前要写章节手工建立的正式资料不会参与生成；场景档案的 `current_state_json` 又代表全项目最后一次出场，补写中间章节时可能把后续章节状态当成前文事实。

现在的规则是：

1. 用户资料和历史来源资料在 `first_seen_chapter == 目标章节` 时即可参与本章创作。首次出现章节是用户声明的适用范围，不要求正文先存在才能使用正式设定。
2. “没有前文章节”不再提前结束上下文组装。第 1 章仍会读取角色、物品和场景正式资料；没有前文只表示没有摘要和上一章结尾。
3. AI 同步资料仍必须有目标章节之前的当前正文证据。候选范围放宽到本章不会让本章分析结果倒灌，因为证据门禁仍严格要求来源章节号小于目标章节。
4. 场景静态设定继续来自档案；“当前状态”改为目标章节之前最近一次真实场景出场的派生状态。补写第 5 章时不会再读取第 10 章的场景状态。
5. 当前章之前没有场景出场记录时，不伪造状态，也不回退到全项目最新状态；只向模型提供用户维护的基础定义、视觉、布局和氛围。
6. 出场状态 JSON 的构造复用同一个模型方法，档案刷新和章节上下文不各自维护一套字段映射。

从用户创作方式看，用户可以先为第 1 章建立“旧车站”和“红色手提箱”，再生成第 1 章正文；也可以先写第 10 章再补第 5 章，而系统只把第 5 章之前的车站状态当作历史事实。后续正文仍通过独立的“兼容落点”提供约束，不会伪装成当前场景状态。

二十八、正文改写立即撤销由本章埋设的旧伏笔（2026-08-09）

伏笔索引当前没有用户创建或编辑入口，记录全部来自章节分析。此前正文改写只会回退“在本章回收”的伏笔，却保留“由本章埋设”的旧记录；因此用户删掉正文中的暗示后，旧伏笔仍会进入后续章节的关键参考和检索查询。

现在的规则是：

1. 正文保存、覆盖、删除以及重新分析前清理，都会在同一数据库事务中删除 `setup_chapter == 当前章节` 的旧伏笔记录，并把 ID 写入已有的 RAG 删除清单。
2. 其他章节埋设、只把当前章节作为回收点的伏笔不会被删除；它们只清空 `payoff_chapter` 并回退为 `pending`，等待新的正文重新确认回收位置。
3. 同一条记录若既在本章埋设又在本章回收，以埋设来源失效为准直接删除，不再先修改后删除。
4. 清理继续复用 `ChapterDerivedCleanupArtifacts` 的 `stale_foreshadowing_ids / changed_foreshadowing_ids`，没有增加失效表、候选状态或补偿队列。
5. 重新分析模型失败时，本章旧 AI 派生伏笔不会继续冒充当前事实；正文和分析状态会明确显示需要重新同步。

从用户创作方式看，用户可以删掉第 2 章“门后脚步声”的暗示后直接续写第 3 章，系统不会继续要求后文回收一个已经不存在的伏笔；如果第 2 章重新分析后仍识别到该暗示，它会依据当前正文重新创建正式索引。

二十九、角色动态状态只保留一个时间化创作入口（2026-08-09）

继续核对章节生成提示词后发现，角色资料过去同时从两条路径进入模型：章节前置上下文会按目标章节读取角色状态并执行正文证据门禁；“关键参考”却再次读取全项目最新主角档案，把最新 `current_state` 直接写入提示词。后者会绕过前者的非线性时间边界，使用户先写后章再补前章时看到未来状态，也可能让已经失去当前正文证据的 AI 角色继续影响创作。

现在的规则是：

1. 章节生成关键参考只负责正式蓝图的静态角色设定、角色关系、世界观和当前有效伏笔，不再读取主角档案的全局最新状态。
2. 角色动态状态只由章节前置上下文提供。它先执行 AI 角色的当前正文证据门禁，再读取目标章节之前最近的角色状态索引；档案同步章节不早于目标章节时，不回退使用全局 `current_state`。
3. 正式蓝图角色仍然是用户确认的创作约束，不依赖机器正文证据，也不因为删除重复状态源而消失。静态设定与动态状态职责分开，但不会生成“暂定蓝图”或第二份角色档案。
4. 数据库参考上下文合同同步删除 `protagonist_profiles` 字段，避免未来调用方再次把全局最新角色状态当作普通参考数据使用。

从用户创作方式看，用户可以先写第 10 章角色受伤后的状态，再补第 5 章；第 5 章只会看到第 5 章之前已经成立的角色状态和正式静态设定，不会因为数据库中的档案已经同步到第 10 章而提前受伤。用户修改前文导致 AI 角色证据失效时，也不会被“关键参考”中的第二份旧档案绕过。

三十、正文优化复用同一套角色时间边界（2026-08-09）

章节生成修正后继续检查“正文优化”发现，优化上下文仍会读取全项目最新主角档案。用户优化较早章节时，模型可能依据后续章节同步出的角色状态提出修改，这与非线性写作中的实际时间顺序冲突。

现在的规则是：

1. 优化器不再从优化专用数据库查询直接读取全部主角档案，而是复用章节生成已经使用的角色正文证据门禁；失去当前正文证据、且未被用户或正式蓝图接管的 AI 角色不会进入优化上下文。
2. 目标为第 N 章时，角色 `current_state` 由属性事件重放到第 N-1 章。第 N 章正文仍作为本次优化的直接事实来源，不用本章或后续章节的派生状态反向约束自身。
3. 优化上下文不再输出档案顶层的 `gender / appearance / personality / last_synced_chapter` 等全局最新摘要字段，避免已经正确重放的历史状态被另一组冗余字段覆盖。
4. 用户正式基础属性、角色弧光、声音约束和正式蓝图仍可用于一致性判断；本轮没有创建优化专用角色快照或第二套状态表。

从用户创作方式看，用户先写第 10 章再优化第 5 章时，优化器可以参考第 10 章作为后续落点，但不会把第 10 章角色已经受伤、离开某地或改变关系当成第 5 章开始前已经发生的事实。后续正文是兼容目标，历史角色状态是当前事实，两者不再混在同一个“最新档案”里。

三十一、全书反推只使用仍有当前来源的 AI 角色资料（2026-08-09）

蓝图反推是全项目任务，因此它不应按某个目标章节截断最新状态；但过去会无条件读取全部主角档案。正文改写后已经失去任何当前正文证据的 AI 角色仍可能进入 `extracted_characters`，并再次被写回新蓝图。

现在蓝图反推读取角色档案时复用当前正文证据门禁，并以全项目范围检查有效证据：

1. AI 发现角色至少要有一条仍指向当前有效正文的证据，或已经被用户/正式蓝图接管，才能参与全书反推。
2. 用户手工角色、正式蓝图角色和历史来源角色继续保留；全书反推不会把“正文中没有机器证据”错误地当作删除用户设定的理由。
3. 候选确认仍会重新计算完整自动上下文指纹。正文、有效角色资料或其他反推来源变化后，旧候选必须重新生成，不能继续落库。
4. 本轮没有增加反推专用角色副本；同一个证据门禁同时服务章节生成、优化和全书反推。

三十二、场景资料同步按正在分析的章节读取已有资料（2026-08-09）

场景同步不仅写场景档案，还要根据已有角色、物品和场景 ID 绑定出场与实体状态。此前重同步第 N 章时，这些参考集合来自全项目最新档案，未来章节新建的资料和最新状态可能反向影响第 N 章的识别结果。

现在的规则是：

1. 同步第 N 章时，已有场景和物品候选只取首次适用章节不晚于 N 的资料；AI 拥有的资料还必须有第 N 章及以前的当前正文证据。
2. 场景 `current_state` 只投影到第 N 章及以前最近一次出场；角色属性事件只重放到第 N 章。第 N 章之后的数据不进入本次同步请求。
3. 提示词不再输出场景/物品的全局 `last_seen_chapter` 和角色的 `last_synced_chapter`，也不再用角色顶层最新外貌覆盖已经重放的章节状态。
4. 当前章节正文和当前正文锚点仍是本次抽取的直接证据；已有档案只帮助复用正式 ID，不能替代正文制造本章出场。

从用户创作方式看，用户先分析第 10 章再回头重做第 3 章时，第 3 章的场景同步不会因为第 10 章新增了某个地点、物品或角色状态，就把它们误绑定进第 3 章。若它们确实在第 3 章正文出现，当前正文会重新提供证据并正常建立资料。

三十三、章节视频上下文与素材自动选择遵守同一时间边界（2026-08-09）

视频提示词过去直接读取全项目最新角色档案，自动素材选择也扫描全部场景和物品档案。为较早章节生成画面时，可能使用后续章节的角色外貌状态，或自动选中来自未来/已失效 AI 档案的素材图。

现在的规则是：

1. 第 N 章视频只读取第 N 章及以前仍有当前证据的 AI 角色，并把角色属性重放到第 N 章；正式蓝图的静态视觉设定继续保留。
2. 角色视频上下文只输出重放后的 `current_state` 分类，不再同时输出档案顶层的全局最新外貌、年龄、背景和人格摘要。
3. 自动场景/物品素材候选改为复用资料上下文门禁：首次适用章节晚于 N、或已经失去当前正文证据的 AI 资料不会参加自动匹配。用户明确选择的参考图仍按显式选择处理。
4. 当前章正文、摘要和分析中的名称仍可提高同章正式资料的素材匹配优先级；后续状态不再作为隐式视觉事实。

从用户角度看，同一个角色第 10 章换装后，回头为第 3 章生成视频不会自动采用第 10 章外貌；如果用户确实希望跨时间复用某张图片，仍可以显式选择，而不是由系统根据全局最新档案偷偷决定。

三十四、发现上下文与自动素材选择不再携带全局状态（2026-08-09）

继续追踪前文边界后，剩余的泄漏点不在资料查询门禁本身，而在几个“只为判断身份/相关性”的提示字段仍带着全局状态：

1. 章节生成的物体、场景资料不再输出全局 `last_seen_chapter` 范围，候选排序也不再按该字段排序；改用不受未来章节影响的 `first_seen_chapter` 做同重要性资料的稳定排序。场景当前状态仍由目标章之前最近一次出场重建。
2. 角色发现已有档案只提供 `name + aliases`。性别、外貌、属性计数、当前状态和 `last_synced_chapter` 不属于身份去重所需信息，不能借发现任务把未来状态带给模型。角色同步内部仍保留同步章节号用于确定重放与清理范围，但不再把这个全局进度字段送进 LLM 上下文；后端完整档案仍用于正式身份合并。
3. 物体发现已有档案只提供 `name + aliases + object_type`。描述、用途、位置、章节范围和最近状态属于资料内容，不是身份判断依据；删除这些字段也取消了对旧档案结构的过度校验。
4. 视频自动场景/物品素材不再因为 `first_seen_chapter <= N <= last_seen_chapter` 就隐式入选，只有当前章正文、摘要或分析明确命中名称/别名时才自动匹配。用户手工选择的素材仍按显式选择保留。

这使“已有档案用于认人/认物”和“档案内容用于创作”分成两条清晰路径：前者可以跨章节维护全局身份，后者必须经过目标章节的时间化上下文和正文证据门禁。当前仍不增加字段级历史快照；只有真实出现“同一 AI 档案不同字段需要按章节回放”的需求时，再引入字段来源或历史记录。

三十五、前章正文变化会使后续角色资料显式失效（2026-08-09）

角色状态是一条按章节累积的时间线。用户重写第 K 章时，系统会清理第 K 章及其后已经同步的 AI 角色时间线；此前章节投影却只比较目标章自己的正文同步与分析记录，导致第 K+1 章之后的角色 checkpoint 仍可能显示“已完成”，与实际资料发生分叉。

现在的规则是：

1. 第 K 章产生新的 `chapter_content_sync` 后，所有目标章节 N >= K 的角色资料，都要检查自己的 `chapter_analysis` 是否发生在这次正文同步之后。较旧的分析不能继续证明角色资料有效，状态统一显示 `needs_analysis`。
2. 用户重新分析目标章 N，并产生 ID 更大的新分析 run 后，该章角色 checkpoint 才重新获得证明资格；不要求用户按系统假设的线性顺序写作，但每一章的角色状态必须建立在当前前文之上。
3. 跨章节失效只作用于 `material_sync.characters`。物品和场景当前没有“重写前章时清除所有后续章节记录”的相同行为，因此不借此规则扩大失效范围。
4. 每章最近 workflow run 按最大 run ID 选择，而不是依赖 `updated_at`。恢复旧任务会更新时间，但不能因此遮住真正较新的正文同步或分析证据。
5. 不自动触发后续章节的批量 LLM 重分析，也不增加补偿队列或第二套失效表。现有 workflow 身份已经足够表达“哪些角色资料需要用户重新分析”。

从用户创作方式看，用户可以先完成第 10 章，再回头重写第 3 章。系统不会假装第 4—10 章的角色状态仍然可靠，也不会在后台擅自花费模型调用重写资料；它会明确标出受影响章节，用户可按自己的创作节奏逐章重新分析。

当前边界：

1. 本轮修正的是角色资料证据与界面状态的一致性，不新增“一键重分析后续全部章节”。只有用户确实需要批量处理、且成本确认和失败恢复方式明确后，再设计范围操作。
2. 物品、场景或其他资料将来若出现同样的跨章节清理语义，应复用同一 run 顺序规则，而不是为每类资料再建一套隐藏状态。

三十六、向章节空档插入正文也必须回退后续角色时间线（2026-08-09）

自由创作允许用户直接创建任意章节号，因此“新建章节”不一定发生在故事末尾。此前单章导入只有覆盖已有章节时才清理角色时间线；如果项目已经写到第 10 章，用户第一次补写第 3 章，系统会创建第 3 章正文，却保留第 4—10 章基于旧前文计算的角色状态。界面虽然能显示后续角色资料需要分析，数据库里的累计状态却没有同步回退。

现在的规则是：

1. 任意章节正文成为当前事实时，都统一失效该章及其后的 AI 角色时间线，不再由导入、编辑、生成、优化或审核入口分别传入“是否清理角色”的布尔选择。
2. 在故事末尾新增章节时，角色档案的 `last_synced_chapter` 早于新章节，清理范围为空，不会额外删除已有正确状态；在中间空档插入章节时，角色档案会回退到该章之前的状态，后续旧事件不再继续冒充当前事实。
3. 清理仍只删除可重建的 AI 时间线派生记录。用户属性、用户行为、正式角色档案和蓝图角色不会因为插入正文而被删除。
4. 同一事务继续同时提交正文和 `chapter_content_sync` 计划；第三十五节的跨章节状态规则会把受影响的后续角色资料投影为 `needs_analysis`。写作台按资料类型显示“需分析”，章节侧栏汇总为“资料需更新”，不再把已有分析但资料过期误写成“尚未分析”。
5. 不自动调用模型重算后续章节。用户可以先继续写正文，也可以选择某个后续目标章重新分析；现有角色同步会从回退位置读取可用章节并重建到目标章。

从用户创作方式看，“先写第 10 章，再补第 3 章”现在不再被实现层误解为“第 3 章是项目末尾的新数据”。章节号代表故事位置，而创建时间只代表用户操作顺序；资料同步必须服从前者。

当前边界：

1. 当前支持在空档创建真实章节，但没有提供批量章节重编号功能。将来若允许移动或重排章节，重排事务也必须复用同一“从最早受影响章节回退”的规则。
2. 本轮没有增加后台批量分析。只有用户明确需要范围分析，并能确认模型成本、顺序和部分失败处理方式时，再增加一个可观察的范围 workflow。

三十七、角色同步必须校验完整来源集合，而不只是旧来源版本（2026-08-09）

非线性创作中的来源变化不仅是“某章正文被修改”，还包括“同步范围内新增了一章”。用户可能在第 10 章角色分析运行期间补写原本空缺的第 3 章；旧任务当时只读取了第 1、2、4—10 章。此前 terminal 校验只按旧任务记录的 chapter ID 逐行比较，因此这些旧行都没变化时，任务仍可在第 3 章提交后写回一条忽略第 3 章的角色时间线。

现在的规则是：

1. 角色同步持久化在锁定角色档案后，重新读取 `start_chapter..=target_chapter` 范围内的全部章节行，而不是只查询旧任务列出的 ID。
2. 当前可用正文集合必须与准备阶段记录的来源集合完全相同：章节新增、删除、由空变为有正文、由有效变为删除，或者任一章节的 ID、章节号、标题、正文 hash、`updated_at` 变化，都会返回 `character_sync_source_changed`。
3. 只有来源集合和每一行版本都仍然相同，才允许清理旧时间线并写入新事件、状态索引和 generation run。检查发生在任何角色资料删除或写入之前，失败不会留下半次角色同步。
4. 继续复用现有 profile 行锁和章节行锁，不新增项目 revision 表。正文插入事务也会经过统一的角色时间线清理，因此无论两个事务谁先获得 profile 锁，最终都不会让旧来源结果覆盖新正文事实。
5. 第三十五、三十六节负责“正文变化后资料应显示什么、已有时间线如何回退”；本节负责“变化发生在模型运行期间时，旧任务不能重新污染已回退的数据”。三者共同闭合插入章节的正常路径与并发路径。

从用户创作方式看，用户不需要在 AI 分析时冻结整个项目。可以继续补写任何章节；旧任务最多明确失败并要求重试，不能因为它启动得更早、返回得更晚，就把缺少新章节的角色状态重新变成正式资料。

当前边界：

1. 已有纯规则测试覆盖“同步范围内后来插入章节必须判定来源集合变化”。真实 PostgreSQL 锁等待和死锁顺序仍需要 `A4N_TEST_DATABASE_URL` 才能做集成验证。
2. 当前集合校验针对角色时间线，因为它会跨章节累积。其他资料若以后也根据一个章节范围计算累计状态，应复用“完整集合 + 行版本”的 terminal 校验，而不是只记录已选来源 ID。

三十八、场景分析保持本章事实快照，不建立第二条跨章时间线（2026-08-09）

继续追踪场景 `entry_state / exit_state / entity_states` 后确认：场景出场记录是某一章正文的完整局部快照，创作上下文只在目标章之前选择最近一次快照；它不像角色属性事件那样把每章增量依次重放。因此前章改写不应机械删除所有后续场景记录，但场景抽取也不能暗中依赖前章派生状态，否则实现会重新制造一条没有明确回放规则的隐藏时间线。

现在的规则是：

1. 场景同步请求中的已有场景档案只提供名称、别名、类型、重要性、基础描述、视觉、布局、氛围和首次适用章节，用于识别同一正式场景；不再把派生的 `current_state_json` 或全局 `last_seen_chapter` 输入模型。
2. 本章 `occurrences`、进入/离开状态和场景内实体状态只能依据本章正文、当前正文锚点及本章已确认的场景候选抽取。正文没有明确给出的状态允许为空，不能拿前章状态补成新的正式事实。
3. 第 K 章正文变化时，现有统一清理仍立即删除第 K 章自己的场景出场、转场和实体状态，并刷新场景档案投影。若该章原本是目标章之前最近一次出场，后续创作上下文会自然回退到更早的真实出场；若第 K+1 章存在自己的正文快照，则继续以第 K+1 章事实为准。
4. 章节生成和优化仍可读取目标章之前最近一次场景出场作为创作历史；“资料抽取不能继承旧派生状态”和“创作时可以参考已成立的前文状态”是两个不同职责。
5. 因此场景资料不复制角色的跨章节 `needs_analysis` 和级联清理规则，也不新增场景 revision、累计事件表或补偿队列。以后只有出现必须按章节应用场景增量、且本章正文无法独立形成快照的真实需求时，才重新设计时间线。

从用户创作方式看，用户先写第 10 章再补第 3 章时，第 10 章中明确写出的场景结果仍是第 10 章事实；系统不会因为补写第 3 章就删除所有后章场景资料，也不会在重新分析第 10 章时把第 3 章旧派生状态偷偷填进正文没有写明的字段。

三十九、整项目场景同步校验完整章节集合，并进入统一资料状态（2026-08-09）

场景资料页提供“同步全部场景档案”的真实用户入口。此前任务启动时虽然记录了全部章节指纹，但每章落库只校验当前目标章；用户在长任务期间补写新章节、删除章节，或改回已经处理过的章节后，旧任务仍可能继续显示“全部同步成功”。同时，写作台的场景资料状态只认整章分析 checkpoint，用户单独同步成功后仍可能看到“需分析”。

现在的规则是：

1. 场景同步只选择未删除且有正文的章节。空章节、生成占位和已删除正文不会被包装成可分析来源，也不会让“同步全部”对不存在的事实调用模型。
2. workflow 启动时继续记录本次全部来源章节的 ID、章节号、标题、正文 hash、`updated_at` 和 `analysis_data`。全部章节处理及场景 RAG 同步完成后，系统重新按同一选择规则读取来源集合并比较完整指纹。
3. 同步期间新增有效章节、删除章节、正文或标题变化、重复保存导致版本变化，以及分析数据变化，都会使整项目任务明确失败并要求重新同步，不能再把缺章或旧来源结果报告成成功。单章写入仍保留事务内目标章行锁和来源版本校验。
4. 写作台 `material_sync.scenes` 会读取现有 `scene_profile_sync` workflow。只有运行指纹包含当前章节版本、且运行发生在该章最近一次正文清理之后，才参与状态投影；运行中、完成或失败分别显示对应状态。
5. 场景资料页单独同步和整章分析内部触发的场景同步使用同一个 workflow 证据。正文再次保存后，新 `chapter_content_sync` 的运行身份会使旧场景同步自动失去证明资格，不新增场景状态表或人工同步标记。

从用户角度看，“同步全部成功”现在表示任务确实覆盖了它结束时仍然有效的全部正文；“场景资料已完成”也不再要求用户必须通过整章分析这一条入口，只要当前正文对应的正式场景同步确实完成即可。

当前边界：

1. 整项目同步仍按章节逐步提交，某个后续章节失败时不会回滚已经基于当前正文成功写入的前面章节；workflow 会显式失败，用户重试时按当前来源创建新的运行。只有出现必须全书原子切换场景资料的真实需求时，才值得承担长事务或版本化发布的成本。
2. 当前没有独立的全项目物品同步用户入口；物品发现的 `chapter_number=None` 只保留为内部能力和测试合同。本轮不为没有实际入口的批处理竞态增加通用框架。

四十、场景批量同步按章节承认局部完成，并在 RAG 前后复核来源（2026-08-09）

继续核对“同步全部场景档案”的部分失败语义后发现：整项目 workflow 允许逐章正式提交，但写作台此前只读取整个 workflow 的最终状态。只要后续某章失败、任务停止，或结束时发现项目新增了正文，已经写入并保存 final checkpoint 的前面章节也会一起显示为“失败”，与数据库中的真实资料不一致。

现在的规则是：

1. 每章场景资料是否完成，优先由该章当前正文对应的 `scene_profile_sync.chapter.N.final` checkpoint 证明。checkpoint 同时校验章节 ID、章节号、标题、正文 hash、`updated_at`、`analysis_data` 和完成状态，不能用其他正文版本的旧 checkpoint 冒充。
2. 整项目任务后续失败时，已经完成 checkpoint 的章节继续显示“已完成”；尚未完成的章节才根据当前 workflow 显示运行中或失败。这样既保留部分提交的真实结果，也不会把未处理章节伪装成成功。
3. 正文再次保存后，新 `chapter_content_sync` 仍会使更早的场景 workflow 失去证明资格，并清理该章场景记录。局部完成规则不会绕过正文版本失效边界。
4. 完整章节集合现在在场景 RAG 同步开始前和结束后各校验一次。RAG 开始前已经发生的插章、删章或正文变化不会继续进入外部索引；RAG 期间发生的变化仍会在结束时明确使 workflow 失败。
5. 可同步章节继续统一来自现有 `character_sync_chapters` 共享入口；该入口已经排除已删除和空正文。本轮删除场景选择器里的重复过滤，不再让不同资料类型各维护一套“有效正文”定义。
6. 写作台角色发现入口始终携带当前章节号；当前没有用户可见的“全项目角色发现”操作。因此不为 `chapter_number=None` 的内部合同增加一套没有实际入口的批处理来源框架。当前章只有章纲或空占位时，现有共享章节门禁会直接提示没有有效正文。

从用户角度看，用户同步十章场景时，即使第八章失败，已经成功落库的第一至第七章仍会如实显示完成；用户可以继续创作或针对失败范围重试，不必因为一个总任务失败而猜测前面资料是否还存在。同时，用户可在 AI 工作期间继续补写或改写正文，旧任务只能失败，不能把过期来源报告成全部成功。

当前边界：

1. 场景 RAG 是外部存储写入，不与 PostgreSQL 场景事务组成跨系统原子提交。当前复用 RAG 既有的记录来源前后校验、正文变更清理，以及本轮完整集合前后校验；只有真实出现并发旧写覆盖新清理的问题时，再考虑按项目串行化 RAG 操作或版本化索引，不预先增加锁服务或补偿队列。
2. 每章 final checkpoint 表示正式场景记录已经提交，不表示整项目 workflow 的所有后续工作都成功。整项目错误仍保留在 workflow 和任务提示中，章节资料状态只回答“这一章当前版本的场景资料是否已经写入”。

四十一、独立批量角色同步进入统一资料状态，AI 只读取已保存正文（2026-08-09）

写作台角色工作台的“同步全部角色”会直接写入正式角色时间线，但此前章节资料状态只认整章分析 workflow；用户已经完成独立同步，界面仍可能显示“需分析”。同时，编辑器中的未保存正文只存在于前端，角色发现和同步若继续请求后端，会读取数据库里的旧正文。

现在的规则是：

1. 独立批量角色同步启动一个属于目标章节的 `character_profile_batch_sync` 父 workflow。它记录目标章 ID、章节号、标题、正文 hash、摘要、分析数据、`updated_at`，以及用户点击时实际确认同步的角色 ID 集合。
2. 角色 ID 在指纹中稳定排序；运行期间后来新建的角色不加入这一次任务，也不把已经确认的批次改成一个不断变化的目标。用户需要同步新角色时再次明确运行即可。
3. 全部角色成功或按现有断点规则跳过时，父 workflow 完成；任一角色失败时父 workflow 失败，取消时记录取消终态。已经成功写入的角色时间线继续保留，任务结果仍如实返回成功、跳过和失败明细。
4. `material_sync.characters` 会在整章分析和独立批量同步之间选择较新的当前来源证据。独立同步成功后立即显示完成；若较早章节后来产生新的正文同步运行，现有 run ID 顺序规则会再次把目标章角色资料降为 `needs_analysis`。
5. 当前章节存在未保存正文时，角色发现、发现请求预览、同步全部和同步请求预览全部禁用并明确提示先保存。刷新、手工新建、编辑和删除正式角色资料仍可使用，不能因为 AI 来源暂时不稳定而冻结用户维护资料。
6. 批量任务无论成功、部分失败还是取消，写作台都会重新读取章节资料状态；即使角色弹窗已经关闭，也只根据后端 workflow 证据刷新，不在前端伪造“已完成”状态。

本轮没有增加角色批次表、候选角色状态、资料 revision 或自动重跑队列。父 workflow 只回答一次明确用户操作是否基于当前正文完成；角色时间线、正文同步运行和章节资料投影继续分别承担正式数据、失效证据和用户可见状态。

四十二、章节场景生成只允许当前已保存来源正式落库（2026-08-09）

章节场景生成会直接写入正式 `chapter_scene`。此前写作台即使只有未保存修改、空占位正文或仍在生成的正文，也可能继续请求后端；模型运行期间若章节、章纲或已有场景发生变化，旧结果还会覆盖用户刚刚确认的新资料。

现在的规则是：

1. 写作台统一判断当前章节 AI 来源是否可用：有未保存正文时要求先保存，正文仍在生成时要求等待，没有已落库正文时明确禁止请求。角色发现、角色同步、章节场景生成及其请求预览共用这一用户可见门禁。
2. Host/API 侧的章节场景共享校验同样要求章节具有已保存正文且不处于生成中，不能依赖前端按钮来保护正式写入边界。
3. 手工创建、编辑、删除角色资料，以及手工编辑、删除、排序章节场景继续开放。AI 来源暂时不可用不能冻结用户维护正式资料。
4. 模型调用前保存完整来源：当前章节记录、实际选中的章纲记录和该章全部章节场景。保存模型结果时，不只比较目标场景，而是按模型真正看到的完整集合复核。
5. 正式写入在同一数据库事务内依次锁定并重读章节、章纲和全部场景；任一来源变化都返回 `chapter_scene_generation_source_changed`，旧任务明确失败，不更新也不插入场景。
6. 两个生成任务即使同时基于同一旧场景集合开始，先完成的任务写入后会改变正式集合；后完成的任务不能继续覆盖前一个结果。用户也可以在 AI 运行时继续保存正文或调整场景，旧任务只会失效，不要求冻结创作。

本轮没有增加章节 revision 表、临时场景候选、补偿队列或第二套章节场景状态。正文、章纲和正式场景记录仍是唯一来源，事务内完整集合比较只负责判断本次模型结果是否还能落库。

当前边界：

1. 本环境未配置 `A4N_TEST_DATABASE_URL`，已完成纯规则测试、编译和 SQLite 可执行路径检查，但 PostgreSQL 下真实锁等待与并发提交顺序仍需在隔离测试库验证。
2. 更高层的分部/章节大纲生成仍需继续逐个核对：这些入口同样会在模型返回后写正式规划，下一步应确认用户在任务期间修改蓝图、正文或目标大纲时，旧结果不会覆盖新的正式资料。

四十三、正式大纲生成只提交仍基于当前创作资料的结果（2026-08-09）

分部和章节大纲是用户后续写作会直接依赖的正式规划。此前各入口会先读取蓝图、正文和已有大纲，等待模型返回后再直接插入或更新；用户在此期间修改资料时，旧任务仍可能覆盖刚确认的新内容。单条重生成还存在“先读目标、后读上下文”的窗口，模型可能使用旧目标参数，却在写入时覆盖已经更新的同一条记录。

现在的规则是：

1. 每次模型调用前保留本次正式写入所依据的完整来源：与大纲有关的项目创作字段和导入分析来源、实际蓝图投影、正式分部集合、正式章纲集合及其自动来源、有效正文章节的 ID、章节号、标题、摘要、完整正文 hash、分析数据和 `updated_at`。正文只给提示词提供摘要或节选时，写入门禁仍绑定完整正文，不能因修改发生在节选之外而继续提交旧结果。
2. 正式写入统一在事务内按“正文行 → 项目行 → 蓝图/角色/关系 → 分部 → 章纲及来源”的顺序锁定并重读资料。当前来源与准备阶段不完全相同时，返回 `outline_generation_source_changed`，不插入、不更新，也不先删除任何已有正式大纲。
3. `GenerateParts`、全部分部重生成、最后一部重生成、分部续写、指定分部重生成、按分部生成章纲、批量按分部生成、按数量追加章纲、单章章纲重生成和节拍映射，最终都经过同一个来源复核边界；不能由某个较少使用的入口绕过。
4. 指定分部、指定章纲、章节生成的目标分部和节拍映射分部，都从同一份生成上下文中解析，不再先单独读取一份可能过期的目标。更新写入还会确认目标完整记录确实属于准备阶段快照，避免旧目标覆盖新目标。
5. 逐部、逐章生成成功写入后，只把任务自己刚提交的正式记录加入下一步预期，并同步更新下一次请求使用的上下文。这样前一步自己的写入不会被误判为外部变化；用户或其他任务的变化仍会让后续旧结果明确失败。
6. 用户在 AI 运行期间仍可继续修改正文、蓝图、角色关系、分部或章纲。系统不冻结创作，也不建立“暂定蓝图”、大纲 revision、候选大纲表或补偿队列；正式资料仍只有一份，事务内比较只决定这次旧模型结果还能不能写入。

从用户创作方式看，用户可以启动十章章纲生成后立即回去重写正文、调整人物关系，或手工改好某一章章纲。已经基于旧资料运行的模型最多失败并提示重试，不能因为返回更晚就重新覆盖用户的新决定；同一任务按顺序生成的前几章若已经成功提交，后续请求可以继续把这些正式结果作为当前上下文使用。

当前边界：

1. PostgreSQL 行锁可以保护已经存在的来源行；集合完整复核、项目行锁和唯一约束共同保护正常业务入口中的新增记录。没有隔离的 `A4N_TEST_DATABASE_URL` 时，不能声称已经验证所有多 worker 下的 phantom insert 和真实锁等待顺序。
2. 本轮只解决“模型运行期间来源变化时能否正式落库”。用户主动修改上游资料后，已经存在的大纲是否要在界面显示为“需重新规划”，应继续依据真实用户需求设计可见状态，不能借本次写入门禁再制造一套隐藏 revision。

四十四、物品保持章节分析归属，蓝图只提交仍基于当前正式资料的结果（2026-08-09）

继续核对资料同步入口后确认：当前产品没有独立的“同步全部物品档案”或“同步本章物品”用户操作，物品发现只作为章节分析的一部分运行。因此 `material_sync.objects` 继续由当前正文对应的章节分析 checkpoint 证明完成是自洽的；为一个没有真实入口的能力新增物品 workflow、批次状态表或全项目来源框架，只会制造第二套状态。

蓝图生成和蓝图优化不同：它们会直接替换用户后续大纲和正文依赖的正式蓝图、蓝图角色及关系。模型运行期间，用户仍可能修改这些正式资料；旧任务不能因为启动更早、返回更晚而覆盖用户的新决定。

现在的规则是：

1. 蓝图生成在模型阶段开始前记录当前正式蓝图、蓝图角色、蓝图关系及版本，同时记录它最终会同步的项目创作字段。蓝图优化记录同一组蓝图来源，但不把项目主表作为写入目标。
2. 正式写入前在同一事务中重新锁定并读取来源。蓝图内容、版本、角色集合或关系集合发生变化时返回 `blueprint_source_changed`；蓝图生成会覆盖的项目字段发生变化时返回 `blueprint_project_source_changed`。失败发生在创建版本、替换正式蓝图或同步项目字段之前。
3. 蓝图生成统一按“项目 → 蓝图 → 蓝图角色 → 蓝图关系”的顺序锁定。蓝图版本恢复也先锁项目，再修改蓝图及角色关系，与正式大纲生成保持一致，避免不同正式规划入口形成反向锁序。
4. 项目来源门禁只比较蓝图生成实际读取或覆盖的创作字段。`current_chapter`、项目头像和后台进度等无关字段变化不会让旧任务失败，用户可以在 AI 运行期间继续写作和推进项目。
5. 蓝图优化不写项目主表，因此只复核并锁定正式蓝图、角色和关系，不额外扩大冲突范围。手工维护正式资料继续开放；只有 AI 将结果写入正式资料时才要求来源仍然新鲜。
6. 系统不新增“暂定蓝图”、候选蓝图表、项目 revision 或自动重跑队列。正式蓝图始终只有一份；任务启动时间只用于判断模型结果是否仍可提交，不会生成一份依赖时间存在的第二事实源。

从用户创作方式看，用户可以启动蓝图生成后继续写正文、更新当前章节或头像，这些无关变化不应阻塞结果；也可以在等待期间重新确认蓝图角色、关系或项目规划字段，此时旧任务必须明确失败并要求按当前资料重试，不能静默覆盖用户刚完成的修改。

当前边界：

1. 已完成纯规则测试、聚焦编译和现有蓝图测试；本环境没有配置 `A4N_TEST_DATABASE_URL`，PostgreSQL 下真实行锁等待、并发插入和完整锁顺序仍需在隔离测试库验证。
2. 当前没有物品独立同步入口，因此不为 `object_discovery` 的内部全项目能力增加用户不可见的同步状态。以后只有产品真的提供独立物品同步操作时，才需要像角色或场景一样定义它自己的来源指纹、部分完成语义和资料状态投影。

四十五、用户删除或修改正式档案后，旧发现任务不能把资料复活（2026-08-09）

继续沿着“AI 运行期间用户维护正式资料”的实际操作检查角色、物品和场景发现后，三条路径并不完全相同：角色发现只创建本次真正不存在的角色；对模型启动时已存在的角色，它只按原档案 ID 绑定证据。用户在等待期间删除该角色后，旧 ID 无法再通过档案归属校验，任务会失败，不会按名称重新创建。因此角色路径不需要再增加一套通用资料 revision。

物品发现此前会在模型返回后按规范化名称直接 upsert。用户若删除模型启动时看到的物品，旧任务会把同名物品重新创建；用户若刚修改或清空字段，旧任务也可能继续补回旧来源下的内容。场景同步虽然显式 ID 被删除时通常会失败，但模型允许为场景返回空 ID，并且场景、角色、物品上下文只在准备阶段校验，仍存在按旧上下文重建场景或写入失效实体引用的风险。

现在的规则是：

1. 物品发现请求上下文保留模型启动时看到的正式物品档案集合。正式 upsert 前在同一事务中先锁来源章节，再锁当前项目的物品档案并复核来源；档案被删除、身份字段变化或用户拥有的正式描述变化时返回 `object_discovery_profile_source_changed`，旧任务不创建、不更新，也不写 generation run。
2. 物品来源门禁不是整行时间戳比较。`first_seen_chapter`、`last_seen_chapter`、证据和 `updated_at` 属于不同章节分析可以安全合并的派生事实；这些字段变化不会让另一章的旧任务无谓失败。档案 ID、归属、名称、规范化名称、别名和类型始终参与比较；用户拥有的用途、外观、材质、位置和图片种子也参与比较。
3. 场景同步把模型实际看到的三组正式上下文收敛成同一份来源合同：场景身份与基础描述、目标章时点的角色状态，以及物品名称、类型、外观、材质和位置。提示词和 terminal 校验复用同一组投影字段，不能各维护一套近似合同。
4. 场景正式写入在锁定目标章节后，依次锁定场景、角色和物品档案，重新按目标章节计算可见资料上下文。任一档案删除、相关字段修改、角色时点状态变化或可见集合变化时返回 `scene_profile_sync_context_changed`，不会 upsert 场景、替换本章出场记录或写 generation run。
5. 场景来源合同继续排除 `current_state_json` 和全局 `last_seen_chapter` 等跨章派生投影。用户先同步第 10 章、再补第 3 章时，第 10 章产生的未来状态不会仅因更新时间变化就阻止第 3 章提交；真正改变第 3 章模型输入的资料才会使旧任务失效。
6. 物品和场景删除事务现在都先锁定目标档案，再清理图片主素材、generation target、出场、转场和实体状态。若 AI 已进入正式提交，删除会等待其事务完成后继续，并最终以用户删除为准；若删除先完成，旧 AI 任务重读来源时会明确失败。不会再出现“删除先清了一半下游数据，却在最后删档案时才等待 AI”的交错窗口。
7. 本轮没有增加档案墓碑表、项目 revision、通用资料锁服务或自动重跑队列。正式档案仍是唯一事实源，短事务行锁只覆盖最终复核和写入，不冻结模型运行期间的创作操作。

从用户角度看，用户可以在物品或场景分析等待期间继续整理资料：删除就是删除，旧任务不能把它复活；手工确认的新描述也不能被旧上下文补回。同时，用户可以跳写多个章节并让不同分析任务追加同一物品的出现范围和证据，系统不会因为这些可交换的派生更新把所有任务串成一条不必要的队列。

当前边界：

1. PostgreSQL 已有查询合同测试确认正式资料行使用 `FOR UPDATE`，但本环境仍未配置隔离的 `A4N_TEST_DATABASE_URL`，尚未实测两个真实连接下“删除等待 AI / AI 等待删除”的完整时序。
2. 在“任务开始时档案不存在、最终提交检查后用户又瞬间创建并删除同名档案”的极窄 ABA 窗口中，没有持久墓碑就无法证明中间动作发生过。当前唯一约束、按名称重读和用户最终删除优先已经覆盖正常入口；只有真实出现这种冲突并需要记住删除意图时，才值得引入项目级资料变更序号或墓碑，而不是预先为所有档案建立 revision 系统。

四十六、场景 RAG 只能缓存当前正式资料，不能复活已删除或已修改的场景（2026-08-09）

场景档案、出场和转场会进入通用 RAG 检索。此前删除场景只清理 PostgreSQL 记录和下游图片，向量库中的 `SceneProfile`、`SceneOccurrence`、`SceneTransition` 会一直保留到用户下一次执行完整 RAG 同步。章节正式场景上下文虽然直接读取数据库，不会使用这些残留，但通用检索仍可能返回已经删除的场景；并发中的旧 RAG 同步也可能在数据库删除完成后晚到写回。

现在的规则是：

1. 场景删除事务在锁定目标档案后，同时收集将被级联删除的出场 ID 和转场 ID。数据库提交成功后，编排层使用正式场景、出场和转场的规范 chunk ID，一次性精确删除这些 RAG 记录；不会清空其他场景，也不要求全项目重建。
2. 场景 RAG chunk ID 的生成统一由同一组 helper 负责，写入和删除不再各自拼接字符串，避免 ID 合同分叉。RAG 删除失败会作为提交后警告明确返回，不能把“数据库已删、向量仍在”报告成完整成功；但该失败不会中断用户已经确认的下游图片清理，若两项清理都失败会一起报告。
3. 通用增强检索在向量搜索完成后重新读取当前场景档案、出场和转场，并复用正式 RAG 文本构造器计算当前内容 hash。只有 chunk ID 仍存在且向量中的 `content_hash` 与当前数据库资料一致，场景结果才允许进入最终检索结果。
4. 因此，场景被删除、手工修改、重命名，或旧同步晚到写回时，旧向量即使暂时仍存于索引，也不会再成为创作上下文。下一次场景或完整 RAG 同步负责补写当前记录并清理存储残留；正式资料始终以 PostgreSQL 为准。
5. 章节生成当前只从 RAG 读取有完整章节来源版本的正文类记录，场景创作上下文继续直接读取数据库。本轮不把场景 RAG 变成第二份状态，也不为删除建立墓碑、revision、补偿队列或后台自动重跑。

从用户创作方式看，用户可以在 AI 或 RAG 同步运行期间继续删除、重命名或整理场景。删除就是删除，手工修改后的正式内容就是当前内容；旧索引最多造成一次显式清理失败或暂时少返回结果，不能继续向后续创作提供已经被用户否定的资料。

当前边界：

1. PostgreSQL 删除与外部向量库清理不是跨系统原子事务。当前通过“提交后精确删除 + 检索终端按正式内容 hash 过滤”保证错误数据不可见；只有真实需要自动恢复索引完整性时，才增加可重试的 RAG 清理任务，而不是把外部索引升级为事实源。
2. 通用检索目前会为项目当前场景资料重建 hash 集合。该路径优先保证资料正确性；只有实际测量显示大型项目检索延迟受此影响时，再改为按候选 ID 批量读取或维护可验证版本字段。
3. 本轮 `cargo check -p a4n-runtime`、`a4n-db` 库编译、删除锁测试、精确 chunk ID 测试、场景检索 freshness 测试、双清理错误合并测试和 `git diff --check` 均已通过。当前仍未配置 `A4N_TEST_DATABASE_URL`，没有实测 PostgreSQL 双连接下“场景同步晚到写 RAG / 用户同时删除”的完整时序。

四十七、手工场景维护立即更新检索副本，正式提交与外部同步采用双结果（2026-08-09）

继续从用户实际操作核对后确认，写作台右栏的“资料检索”是用户会直接使用的创作工具，不只是后台缓存。此前用户手工新建或编辑正式场景后，章节生成会立即从 PostgreSQL 读到新资料，但资料检索要等下一次场景同步或全量 RAG 同步才会补上；旧结果虽然已被 freshness 过滤，不会误导创作，新资料却可能暂时查不到。

现在的规则是：

1. 手工新建或编辑场景档案成功落库后，复用现有场景 RAG 普通同步，重新核对场景档案、出场和转场三类规范记录。未变化记录按现有 content hash 直接跳过，只为实际变化的记录重新计算和写入向量；场景重命名时，引用该名称的出场和转场文本也会一起更新。
2. 场景 RAG 同步开始前和结束后都读取正式场景资料并使用同一套 canonical 文本计算 hash。同步期间若另一处又修改、创建或删除场景，当前同步返回“正式资料已变化”的警告，不能把基于混合时点完成的索引报告成当前完成；检索终端仍会过滤已经写入的旧内容。
3. 手工创建、编辑和删除的 API 明确区分“正式数据库提交结果”和“提交后的外部副作用”。数据库写入成功后，即使 RAG 或下游图片清理失败，也返回已经保存/删除的正式结果以及 `warnings`，不再把整个操作伪装成失败。
4. 前端收到带警告的成功结果后仍会刷新正式场景列表、关闭已完成的编辑操作，并明确提示“档案已创建/更新/删除，但资料索引或图片清理失败”。用户不会因为一次外部服务错误重复创建档案，也不会在界面继续看到已经删除的旧记录。
5. 警告明确指向项目操作中的“同步资料索引”作为恢复入口。当前不增加场景专用重试表、outbox、后台补偿队列或 per-record 索引状态；RAG 仍是可重建副本，正式资料状态仍由 PostgreSQL 决定。
6. `material_sync.scenes` 继续回答“当前正文对应的场景分析/独立场景同步是否完成”，不因为用户手工创建、修改或删除正式场景而改写成 `needs_analysis`。手工维护是用户的正式决定，不应被状态投影误解成需要 AI 重建刚刚删除或修正的资料。

从用户创作方式看，用户可以在写完第 10 章后回头补第 3 章，也可以随时手工整理地点名称、空间规则和章节范围。正式资料保存后立即参与章节上下文并尽量同步到资料检索；外部索引暂时失败时，系统准确告诉用户“资料已保存、索引待恢复”，而不是让用户猜这次保存到底有没有生效。

当前边界：

1. PostgreSQL 与向量库仍不是跨系统原子事务。同步前后 hash 核对、提交后警告和检索终端 freshness 共同保证旧内容不可用；只有实际需要无人值守自动恢复时，才增加持久重试任务。
2. 手工保存目前复用整组场景 RAG 普通同步，而不是新增单条场景同步协议。它会读取项目全部场景记录，但只为变化内容生成 embedding；只有性能测量证明大型项目保存延迟不可接受时，再缩小为受影响档案、出场和转场的定向同步。
3. API 合同生成、Web API parity、排除既有测试类型错误后的 462 个前端源文件检查和 Vite 生产构建已通过。最终 Rust 全链检查当前被工作区已有的无关错误阻塞：`project/chapters.rs` 导出了已在 `readiness.rs` 中删除的 `validate_chapter_generation_readiness_record_with_brief`；本轮没有越界修改该问题。场景删除警告测试和本轮较早的 `cargo check -p a4n-runtime` 已通过，但新增的同步前后 hash 测试需在该无关编译错误修复后补跑。

四十八、通用资料检索只返回当前正式资料，旧索引不能挤占有效结果（2026-08-09）

继续审计写作台“资料检索”后确认，场景并不是唯一会残留旧向量的正式资料。分部与章节大纲、正式蓝图及其元数据和世界观、蓝图角色、主角档案、角色状态与属性事件、角色关系、伏笔，都可能在用户手工修改或删除后等待下一次完整 RAG 同步。此前增强检索只校验章节来源版本和场景 hash，其他旧记录仍可能被用户看到，并且可能占满首轮 top-k，使后面的当前资料没有机会进入结果。

现在的规则是：

1. 每次实际执行增强检索时，复用完整 RAG 同步已经使用的 canonical 文本构造器，从 PostgreSQL 正式资料构造当前非章节 chunk ID 与 `content_hash` 集合。检索 freshness 和索引写入不再各维护一套近似文本规则。
2. 当前集合覆盖分部/章节大纲、蓝图正文/元数据/世界观、蓝图角色、主角档案、角色状态、属性事件、关系、伏笔以及场景档案/出场/转场。章节正文及其摘要和分析记录继续使用现有 `source_chapter_id + 正文 hash + updated_at` 来源版本合同。
3. 查询时不会为了得到非章节 hash 构造章节 RAG 记录，因此不会触发章节语义分块或额外 embedding。当前非章节集合在一次增强检索中只构造一次，并沿 runtime facade 传入统一搜索执行层。
4. 每一轮向量候选补取后，先过滤失效章节，再要求所有非章节结果的规范 chunk ID 仍存在，且向量 metadata 中的 `content_hash` 与当前正式资料一致。已删除、已修改但尚未重建索引、或 metadata 损坏的记录都会被丢弃。
5. freshness 过滤位于有界扩量补取循环内部。若首轮候选被旧蓝图、旧角色或已删除资料占满，系统会继续扩大候选范围，直到找到足够的当前资料、存储已无更多结果，或达到既有补取上限；旧记录不能再通过占位间接让当前资料消失。
6. 原先增强检索结束后单独重读场景并二次过滤的路径已经收口到同一套非章节规则。场景同步前后 hash 核对仍保留，用于判断外部索引同步期间正式资料是否变化；检索与同步各自回答自己的问题，不再重复建立场景特例。
7. 本轮没有增加资料 revision、删除墓碑、per-record 索引状态、outbox 或自动补偿队列。RAG 仍是可重建副本；资料发生变化但新向量尚未写入时，系统宁可暂时少返回，也不会返回已经被用户否定的旧内容。

从用户创作方式看，用户可以跳写章节、回头重做世界观、删掉角色设定或调整关系，不需要先等待全量索引同步。下一次资料检索会按当次读取到的正式资料判断哪些缓存仍可使用；旧缓存最多继续占用向量库存储，不能继续进入创作上下文。涉及 AI 正式写入的长任务仍使用各自的终端来源复核，检索快照不会替代正式写入门禁。

当前边界：

1. PostgreSQL 与向量库仍不是跨系统原子事务，当前保证的是“正式资料决定结果是否可见”，不是物理索引立刻无残留。只有实际需要无人值守恢复存储完整性时，才增加可重试清理任务。
2. 每次增强检索会读取项目当前全部非章节 RAG 正式资料并构造 canonical hash。先保证正确性；只有大型项目的真实延迟数据证明这里成为瓶颈时，再按请求 data type 或候选 ID 缩小读取范围，不能先引入一套难以同步的缓存版本表。
3. 非章节 hash 过滤测试、旧候选占满首轮后的补取测试、12 条增强检索测试、20 条章节生成 RAG 测试、runtime 窄 facade 测试和 `cargo check -p a4n-runtime` 已通过。`cargo fmt --all -- --check` 目前只被工作区已有的 `crates/a4n-orchestrator/src/project.rs` import 顺序问题阻塞，本轮修改文件均已符合 rustfmt。

四十九、手工修改世界观直接形成正式版本，数据库提交与检索同步分别报告（2026-08-09）

继续核对用户在世界观页的真实操作后确认：此前手工保存只修改当前蓝图的 `world_setting` 和更新时间，不推进 `current_version`，也不创建可恢复的正式版本。结果是 AI 生成或优化会留下版本历史，用户亲自确认的修改反而没有同等证据；资料检索也要等下一次全量同步才能补上新世界观。这与“用户决定优先、正式资料只有一份、时间变化由正式版本表达”的设计直接冲突。

现在的规则是：

1. 用户保存世界观时，系统先验证项目编辑权限和非空输入，再在一个 PostgreSQL 事务内按“项目 → 蓝图 → 蓝图角色 → 蓝图关系”的顺序锁定当前正式资料。用户不需要在 AI 运行期间停止编辑；谁先进入最终提交谁先完成，后提交的蓝图 AI 任务仍由既有来源指纹复核决定能否落库。
2. 手工世界观修改不再原地覆盖同一个版本。事务从当前 `current_version` 开始寻找尚未占用的下一个正式版本，同时更新世界观、`current_version` 和 `updated_at`，并插入 `change_description = 手工修改世界观`、`created_by = user:{user_id}` 的版本记录。
3. 版本快照使用蓝图优化路径共用的完整构造器，包含标题、类型、风格、基调、目标读者、一句话摘要、完整梗概、世界观、分部与章节规划、头像、蓝图角色和关系。手工修改生成的版本可以走现有恢复入口，不会因为缺少头像或角色关系字段而成为不可恢复的半快照。
4. 恢复旧版本后再修改时，不会机械使用 `旧版本 + 0.1` 并重复已有版本号，而是继续跳过历史中已经存在的版本。例如恢复 `1.1`，历史仍有 `1.2` 时，下一次手工修改创建 `1.3`。版本号表达正式历史身份，不依赖用户当前查看的是哪一个时间点。
5. 数据库事务提交后，只同步本次真正受影响的 `Blueprint`、`BlueprintMetadata` 和 `WorldSetting` 三类 RAG 记录，不触发章节、角色、场景等全项目资料重算。未变化记录继续按现有内容 hash 跳过，不新增单条世界观索引协议。
6. 蓝图 RAG 同步开始前和结束后都会读取当前正式蓝图。同步期间若另一处再次修改蓝图，本次同步返回“正式资料已变化”的警告，不能把混合时点的外部索引报告成当前完成；通用检索已有的 canonical `chunk_id + content_hash` freshness 过滤继续保证旧向量不可见。
7. API 返回明确的双结果：`world_setting` 和 `current_version` 表示 PostgreSQL 已经正式保存，`warnings` 表示提交后的检索副本同步是否失败。RAG 失败不会把已经提交的世界观伪装成“保存失败”，前端仍退出编辑并刷新正式蓝图，同时提示“世界观已保存；资料检索索引更新失败”，避免用户重复保存并制造错误判断。
8. `UpdateWorldSettingResult` 已收口到 `a4n-api-contract`，前端使用生成类型，不在 runtime 和 TypeScript 各维护一份近似合同。世界观版本、数据库事实和 API 结果各只有一个 owning layer。

从用户创作方式看，用户可以启动蓝图优化后继续手工修改世界观：如果用户先保存，旧 AI 结果会因正式蓝图来源变化而拒绝提交；如果 AI 已经先提交，用户随后保存只覆盖自己正在确认的世界观，并把 AI 已提交的其他蓝图字段带入新的完整版本。用户的明确决定不会比模型生成结果更弱，也不需要一份“暂定蓝图”来解释先后时间。

当前边界：

1. 本轮只完成用户界面中证据最明确的手工世界观路径。手工分部/章节大纲、蓝图角色关系及其他正式资料入口是否同样创建版本、同步哪些 RAG 类型、如何表达下游失效，仍需按各自真实创作操作继续审计，不能先扩展成通用 revision 框架。
2. PostgreSQL 与向量库仍不是跨系统原子事务。当前采用提交后普通同步、明确警告和检索 freshness；只有实际需要无人值守恢复时，才增加持久重试任务或 outbox，不预建补偿系统。
3. 版本快照、RAG 来源变化、提交后警告、前端部分成功提示、Host API 边界、Web API parity、TypeScript 检查及 runtime/Tauri/server 编译均已通过。runtime 全库测试中本轮目标测试通过，整体为 493 条通过、16 条失败：其中 8 条数据库复制测试因缺少 `A4N_TEST_DATABASE_URL` 失败，另外 8 条是工作区已有的投影断言或结构收敛测试失效，均不在本轮文件中。真实“保存 → 创建版本 → 恢复 → 跳过已占用版本”的 PostgreSQL 集成测试已加入，但当前环境缺少测试库变量，因此本轮不能声称已执行真实数据库恢复链。

五十、手工大纲维护接管正式规划，数据库提交与检索同步分别报告（2026-08-09）

继续按用户真实的大纲维护方式检查后确认，当前界面提供三个手工入口：编辑章节大纲、删除最近章节大纲、删除最近分部大纲。用户会在 AI 生成期间继续修正或删掉这些正式规划，因此这些操作不能只修改一行数据，也不能让旧 AI 来源标记、正文软关联或资料检索索引各自处于不同状态。

现在的规则是：

1. 手工编辑章纲在一个 PostgreSQL 事务内完成。事务先锁定项目行并复核 `lifecycle_gate`，再按稳定顺序锁定项目正文和目标章纲；来源标记清理、章纲字段更新和 `chapter.outline_id` 软关联修复一起提交或一起回滚。项目行是同一项目正式业务写入的串行边界，锁序与项目重置的“项目 → 子资料”清理方向一致。
2. 用户保存章纲即表示接管这条正式规划。事务会清除该章纲的自动分析来源；模型运行期间已经生成但尚未提交的旧结果，仍必须通过既有完整来源复核，不能在用户保存后重新恢复或覆盖这条章纲。
3. 删除最近章节大纲和删除最近分部大纲继续复用现有正式删除事务及章节派生资料清理，不增加“已删除候选”、墓碑或大纲 revision。用户删除后的 PostgreSQL 当前记录就是唯一事实。
4. 三个手工操作在数据库正式提交后，统一复用现有 `Outline` 和 `PartOutline` 两类 RAG 全量同步入口。未变化记录按 canonical content hash 跳过；分部删除造成的章纲级联删除也由同一次同步清理旧向量，不新增单条大纲同步协议。
5. 大纲 RAG 同步开始前和结束后都会读取当前正式章纲与分部集合。章纲按 `(chapter_number, id)`、分部按 `(part_number, id)` 稳定排序后比较；同步期间若用户或另一个任务再次修改、创建或删除大纲，本次同步返回“正式资料已变化”的警告，不能把混合时点的索引报告成当前完成。
6. API 返回明确的双结果：章纲编辑返回已正式保存的 `outline` 和 `warnings`，两类删除返回 `warnings`。RAG 失败不会把已经提交的数据库操作伪装成失败；前端仍退出编辑、刷新正式列表，并以信息提示说明“已保存/删除，但资料检索索引更新失败”，避免用户重复操作。
7. `ChapterOutlineSummary`、章纲更新结果和删除结果收口到 `a4n-api-contract`，前端使用生成类型。数据库事实、runtime 编排和 Host/TypeScript 合同不再各维护一份近似返回结构。

从用户创作方式看，用户可以启动分部或章纲生成后继续手工修改、删除已有规划。用户先提交时，旧 AI 结果会因正式来源变化而拒绝覆盖；AI 已经先提交时，用户随后保存或删除就是新的正式决定。时间只决定哪个正式提交先发生，不需要“暂定蓝图”或第二份大纲事实来解释过程。

当前边界：

1. 当前产品没有手工编辑分部大纲入口，因此本轮只覆盖实际存在的三个维护操作；以后真正增加分部编辑时，应直接复用同一事务和大纲 RAG 双结果，不预建通用资料同步框架。
2. PostgreSQL 与向量库仍不是跨系统原子事务。当前依靠提交后同步、来源前后复核、明确警告和通用检索 freshness 保证旧索引不可用；只有出现需要无人值守自动恢复的真实需求时，才增加持久重试任务或 outbox。
3. 手工操作复用整组大纲普通同步，优先保证删除级联和分部/章纲索引一致。只有大型项目的实际保存延迟证明这里成为瓶颈时，再设计受影响记录的定向同步，不能先维护第二套 chunk 选择规则。
4. 本轮大纲来源复核测试、提交后警告测试、runtime/Tauri/server 编译、TypeScript、前端生产构建、API 合同边界、Web API parity、rustfmt 和 `git diff --check` 均已通过。现有“手工章纲接管后旧回顾分析不得覆盖”的 PostgreSQL 集成测试仍依赖 `A4N_TEST_DATABASE_URL`；当前环境未配置，因此不能声称已实测真实数据库锁等待与事务回滚时序。

五十一、手工物体档案以数据库提交为准，下游图片清理失败不能伪装成保存失败（2026-08-09）

继续检查用户会直接操作的正式资料后确认，物体档案与场景档案的同步边界不同。物体档案当前不进入 RAG，它由章节生成、场景同步和视频上下文直接从 PostgreSQL 读取，因此不应为了形式统一再增加一条物体 RAG 链路。真正存在的用户问题是：编辑或删除物体档案时，数据库先完成正式提交，随后才清理用户选择删除的下游素材图；图片清理失败却会让整个 API 返回失败，用户会误以为档案没有保存或删除并重复操作。

现在的规则是：

1. 创建、编辑和删除物体档案统一返回“正式档案结果 + `warnings`”双结果。创建当前没有提交后副作用，因此警告为空；统一合同让前端不需要根据创建或编辑维护两套成功语义。
2. 编辑仍先完成正式物体档案更新，再按用户选择清理下游图片。图片清理失败只进入 `warnings`，不会推翻已经提交的档案；返回档案在清理尝试后重新读取素材图数量，界面看到的是当前正式投影。
3. 删除仍以物体档案数据库事务提交为完成边界。提交后的图片清理失败返回警告，前端仍刷新列表、关闭已删除档案详情，并明确提示“物体档案已删除，但下游图片清理失败”，不会让用户再次删除一个已经不存在的档案。
4. 物体档案没有新增 RAG、revision、墓碑、同步状态或补偿队列。章节生成、场景同步和视频上下文继续直接读取当前正式数据库记录；已有 AI 物品发现与场景同步来源复核继续阻止旧任务覆盖或复活用户的新决定。

从用户创作方式看，用户会先整理道具、线索和环境物件，再决定旧素材图是保留还是随档案一起清理。档案文字是后续创作直接依赖的正式事实，素材图是可独立失败的派生产物；系统必须准确告诉用户哪一部分已经完成，而不是用一个笼统的“保存失败”掩盖数据库真实状态。

当前边界：

1. 多张图片按现有删除入口逐张处理；某张失败时，之前已删除的图片不会回滚，警告会促使界面重新读取当前数量。只有真实出现需要批量全成全败的产品需求时，才调整图片删除协议，不能把外部文件清理和物体档案写入强行包装成伪原子事务。
2. 物体档案不在当前 RAG 类型集合中，这是现有创作上下文设计的事实，不是遗漏。以后只有资料检索或其他真实用户入口需要检索物体档案时，才定义它的 canonical chunk 和 freshness 规则。

五十二、手工角色资料提交后立即更新检索副本，时间线操作不再被外部索引失败伪装成失败（2026-08-09）

继续按角色详情页和写作台的真实操作核对后确认，用户现在可以手工创建、删除角色档案，新增或修改角色属性，确认隐性属性修改，执行已达到阈值的属性删除，并把角色时间线回滚到指定章节。这些操作都会改变后续创作要读取的正式角色状态；此前部分入口只提交 PostgreSQL，部分入口把提交后的 RAG 失败继续作为整个操作失败返回，用户无法判断自己的决定是否已经生效。

现在的规则是：

1. 手工创建角色档案成功落库后，立即按该角色的 chunk 前缀同步身份、外貌、背景、人格、基础属性、当前状态、角色弧光和声音指纹等现有规范维度。缺失维度会由同一次同步清理旧向量，不新增另一套单字段索引协议。
2. 手工新增属性、修改属性、执行属性删除以及确认隐性属性修改，仍由 PostgreSQL 事务同时更新角色当前状态并写入属性事件。提交后分别同步本次属性事件和角色档案本身；前者保存“发生了什么”，后者保存“角色现在是什么状态”，两者不能互相替代。
3. 属性事件写入向量后会重新读取正式事件和所属角色身份。若用户在同步期间回滚时间线、删除角色，或角色身份已经变化，本次同步返回“正式资料已变化”的警告，不能把已经失效的事件报告成当前完成。角色档案同步本身也在同步前后重新读取完整正式档案；通用检索继续按 canonical chunk ID 和 content hash 过滤旧副本。
4. 删除角色时，角色档案及其事件、状态索引、快照、行为、删除标记、立绘引用等数据库记录仍在正式事务中一起处理。事务提交后，角色档案 RAG、角色状态 RAG、属性事件 RAG 三类清理都会独立尝试；其中一类失败不会阻止另外两类，所有外部失败只进入 `warnings`。
5. 角色时间线回滚以数据库恢复后的角色状态为正式结果。提交后独立清理被回滚的状态索引 RAG 和属性事件 RAG，再同步恢复后的角色档案当前状态；任一清理失败不会阻止其余动作，也不会把已经完成的回滚伪装成失败。
6. API 统一返回正式操作结果和 `warnings`。前端收到警告时仍关闭已完成的表单、刷新角色列表或详情，并提示“正式资料已保存/删除/回滚，但资料检索索引更新失败”，避免用户重复创建、重复删除或误以为时间线没有回滚。
7. 原先为了区分持久化和 RAG 错误而存在的角色属性/记录生命周期错误包装已经删除。持久化失败直接返回错误；提交后的索引问题直接作为警告数据返回，不再维护一套只服务于错误搬运的中间结果结构。

从用户创作方式看，角色并不是从第一章到最后一章一次性定稿。用户可能先建立一个简略人物，在补写前章时增加背景，在后章确认性格变化，随后又回滚错误的时间线。每一次明确保存或回滚都立即成为唯一正式事实；正在运行或稍后完成的旧索引操作最多造成当前资料暂时检索不到，不能让已经删除或回滚的旧角色状态重新进入创作上下文。

当前边界：

1. PostgreSQL 与向量库仍不是跨系统原子事务。当前用提交后同步、独立清理、同步前后来源复核、明确警告和检索 freshness 保证用户不会看到被自己否定的旧资料；只有出现无人值守自动恢复的真实需求时，才考虑持久重试任务，不预建角色 revision、墓碑、per-record 索引状态或补偿队列。
2. 当前产品没有独立编辑角色姓名、外貌、背景等档案字段的手工入口；创建表单和属性时间线是现有真实维护入口。本轮没有为了假设中的未来编辑器增加通用角色更新 API，等实际入口出现时直接复用同一角色档案同步和双结果语义。
3. 两条角色 RAG 来源变化测试、提交后 warning 测试、runtime/Tauri/server 编译、TypeScript 检查、前端生产构建、API 合同与 Web API parity、相关 Rust 文件格式化以及 `git diff --check` 已通过。

五十三、恢复蓝图版本是新的正式决定，五类蓝图资料同步且不暗中重写其他创作层（2026-08-09）

继续检查蓝图版本面板的真实操作后确认，用户恢复旧版本时，数据库会在一个事务里同时替换蓝图正文、元数据、世界观、蓝图角色和蓝图关系，并同步项目标题、目标章节数和状态。此前 API 在事务提交后直接返回恢复后的蓝图，资料检索仍可能保留恢复前的五类向量；用户看到“已恢复”后立即检索资料时，当前正式内容可能暂时缺失，也无法知道索引是否更新成功。

现在的规则是：

1. 蓝图版本恢复的 PostgreSQL 事务继续作为正式完成边界。事务内恢复当前蓝图、角色快照和关系快照，并更新项目投影；任一正式写入失败都会整体回滚，不产生半份恢复结果。
2. 事务提交后同步五类确实发生变化的蓝图资料：`Blueprint`、`BlueprintMetadata`、`WorldSetting`、`Character` 和 `Relationship`。复用现有 canonical 记录构造器、content hash 和按 data type 清理，不新增“恢复专用向量格式”。
3. 蓝图正文、元数据、世界观三类同步会全部尝试；蓝图角色和关系两类也会全部尝试。某一类向量服务失败不会阻止其他类型尽量收敛，最终错误统一进入恢复结果的 `warnings`。
4. 整次同步开始前和五类同步结束后都会读取完整正式蓝图、蓝图角色和关系集合。角色与关系按数据库 ID 稳定排序后比较，避免查询返回顺序不同造成假警告；若另一次蓝图生成、优化、世界观修改或版本恢复在同步期间提交，本次操作返回“正式资料已变化”的警告，不能把跨两个版本拼出的混合索引报告成当前完成。
5. 恢复 API 改为返回 `blueprint + warnings`。前端即使收到索引警告，也会把版本恢复视为已经完成，刷新蓝图和版本列表，并明确提示“蓝图已恢复，但资料检索索引更新失败”，避免用户重复恢复或误判数据库状态。
6. 恢复蓝图只恢复版本快照明确拥有的蓝图规划层，不会暗中删除或倒带用户后来确认的正文、章节大纲、主角动态时间线、场景档案和物体档案。这些是各自独立的正式决定；如果以后需要级联重审，必须先提供用户可见的影响预览和明确选择，不能用后台同步偷偷覆盖。

从用户创作方式看，恢复旧蓝图通常不是“把整个项目时光倒流”，而是重新选择一个总体构思。用户可能希望保留已经写好的正文和后来整理的角色动态，只让故事总纲、设定角色和关系回到某个版本。系统现在准确恢复蓝图层并更新它自己的检索副本，同时尊重其他创作层已经形成的正式事实。

当前边界：

1. 蓝图层与既有正文、大纲或动态资料之间可能在语义上出现冲突，但系统不能替用户决定删除哪一方。当前先保证所有来源都是真实、当前、可追溯的正式资料；是否增加“恢复影响分析/选择性重审”应由实际用户需求驱动，不能预建通用依赖失效框架。
2. PostgreSQL 与向量库仍不是跨系统原子事务。恢复后的旧向量即使物理清理暂时失败，也会被通用检索 freshness 过滤；只有真实需要无人值守自动恢复时，才增加持久重试机制。
3. 蓝图角色/关系稳定来源与变化拒绝测试、共用 warning 测试、runtime/Tauri/server 编译、TypeScript、前端生产构建、API 合同与 Web API parity、相关 Rust 文件格式化以及 `git diff --check` 已通过。

五十四、确认反推候选才写入正式资料，项目状态和检索副本失败不能推翻确认结果（2026-08-09）

继续沿导入页“生成反推结果 → 用户审阅 → 确认应用”的真实操作检查后确认，反推结果在确认前只是 workflow checkpoint 中的候选；用户确认后，蓝图、章节大纲或分部大纲会在 PostgreSQL 事务中成为正式资料。此前事务提交后仍会继续推进项目状态，状态推进失败会让整个确认接口返回失败；三类正式资料也没有立即更新 RAG。用户因此可能看到“确认失败”并重复确认，但数据库中的资料其实已经写入。

现在的规则是：

1. 候选确认事务继续负责唯一的正式写入边界。它从已完成且身份、目标、输出指纹均匹配的 workflow checkpoint 读取模型结果，校验自动上下文来源仍然新鲜，再一次事务写入对应正式资料和候选确认状态；调用方不能上传另一份 JSON 替换候选。
2. 事务提交后，项目状态只作为正式资料的进度投影继续推进。状态读取、推进或事件发布失败时，确认结果仍返回 `confirmed/already_confirmed + applied + warnings`，不会把已经提交的蓝图或大纲伪装成失败。
3. 新确认和已确认重试都会按候选的可信目标重新执行提交后收敛。`reverse_outline` 与 `reverse_part_outline` 复用现有大纲同步，一次核对章节大纲和分部大纲；`reverse_blueprint` 复用蓝图版本恢复的五类同步，更新蓝图正文、元数据、世界观、蓝图角色和关系。
4. 反推蓝图确认还会在同一数据库事务内从蓝图角色新增或补全 `protagonist_profile`，且只填充原本为空的字段，不覆盖用户已经拥有的角色事实。提交后因此会继续逐个复用现有角色档案 RAG 同步；每个档案都在同步前后复核正式来源，用户同时修改或删除角色时，旧同步只能返回 warning，不能宣称旧资料仍是当前内容。
5. 蓝图、大纲和角色档案的索引同步彼此作为提交后副作用报告。某一类失败不会推翻数据库确认，也不会阻止其他类型尽量收敛；所有错误统一提示可在项目操作中重新同步资料索引。
6. 已确认候选重试不会再次写入正式资料或创建重复版本，只读取 checkpoint 中保存的 `apply_result`，再次尝试项目状态推进和 RAG 同步。这条幂等路径就是状态或索引暂时失败后的恢复入口，不增加确认补偿表或后台队列。
7. 前端收到 warning 时仍把候选显示为已确认、刷新正式资料并结束忙碌状态，只用信息提示说明“正式资料已写入，但项目状态或资料索引待恢复”；不会再显示“确认失败”诱导用户重复操作。

从用户创作方式看，用户可能先导入已有正文，让 AI 反推结构，再手工决定哪些结果进入当前项目；确认之后也可能马上修改角色、世界观或大纲。系统必须把“用户已经确认的正式决定”和“状态栏、向量索引是否已经跟上”分开表达。时间决定哪个正式提交在先，旧 AI/RAG 操作只能校验当前来源并报告落后，不能覆盖或复活用户后来形成的事实。

当前边界：

1. PostgreSQL、项目状态事件和向量库仍不是跨系统原子事务。当前依靠正式事务、提交后 warning、幂等重试、同步来源复核和检索 freshness 保证错误资料不可见；只有出现无人值守自动恢复的真实需求时，才考虑 outbox 或持久重试任务。
2. 反推蓝图数据库结果当前没有返回“本次新增或补全的 profile_id”集合，因此提交后读取项目现有角色档案并逐个使用已有按档案前缀同步。未变化记录由现有 content hash 跳过；只有实际性能数据证明大型角色项目确认延迟不可接受时，才把变更 ID 纳入正式应用结果，不能先复制角色身份匹配规则。
3. 本轮 14 条候选确认测试、3 条 Runtime 反推测试、7 条前端候选合同测试、runtime/Tauri/server 编译、TypeScript 与前端生产构建、Web API parity、全工作区 rustfmt 检查和 `git diff --check` 均已通过。

五十五、蓝图任务启动不等于创作完成，终态确认后按当前正式资料收敛检索副本（2026-08-10）

继续检查三条真实蓝图操作后确认，灵感页会等待 generation 终态并核对正式结果，但此前没有同步蓝图 RAG；项目概览和项目操作中的“优化蓝图”则只等到后端返回任务句柄，就立即提示“蓝图已优化”并读取旧资料。用户看到的完成状态因此可能早于模型执行、正式提交和索引更新，任务随后失败时界面仍会误报成功。

现在的规则是：

1. 蓝图生成或优化仍由现有 generation worker 完成正式提交。蓝图正文、元数据、世界观、蓝图角色、关系以及生成时新增或补全的角色档案继续以 PostgreSQL 当前记录为唯一事实；本轮不改 generation terminal 协议，也不把 RAG 写入正式事务。
2. 新增窄入口 `sync_blueprint_materials(projectId)`。它先验证项目编辑权限，再复用蓝图版本恢复的现有同步逻辑更新 `Blueprint`、`BlueprintMetadata`、`WorldSetting`、`Character` 和 `Relationship`，随后读取项目当前角色档案并逐个复用已有主角档案同步。反推蓝图确认也改为调用这一共用函数，不再维护第二份蓝图与角色档案同步循环。
3. 三条前端流程都必须先等到 generation terminal，再用 `result_ref` 的类型、蓝图 ID、项目 ID 和正式版本核对当前数据库蓝图。任务句柄只表示“已受理”，不能触发成功提示；终态失败或正式结果不一致时不会显示“已优化”。
4. 正式结果核对成功后，同步的是调用时数据库中的当前资料，而不是任务启动时或模型返回时保存的一份副本。用户若在 AI 完成后又修改蓝图或角色，索引操作读取并同步新的正式决定；同步期间来源再次变化时，现有 freshness 复核返回 warning，旧同步不能宣称自己代表当前资料。
5. 数据库提交结果与提交后的索引副作用继续采用双结果。RAG 某一类失败会进入 `warnings`；连同步命令本身都因网络、权限上下文或运行配置无法调用时，前端也只提示“蓝图已生成/优化，但资料检索索引待恢复”，不能把已经完成的正式提交重新显示成生成失败。
6. 三条流程在同步尝试后重新读取或刷新正式资料。项目概览不再读取任务启动前的旧蓝图；项目操作中的优化会等真正完成后再刷新项目；灵感页继续显示经过正式 `result_ref` 校验的蓝图。
7. 本轮没有新增暂定蓝图、候选蓝图表、蓝图 revision 状态、索引状态表、outbox 或补偿队列。用户离开页面后若自动同步没有执行，正式资料仍然正确，旧向量会被通用检索 freshness 过滤，项目操作中的“同步资料索引”仍是明确恢复入口。

从用户创作方式看，用户可以启动蓝图优化后切去整理角色、继续写正文，甚至再次修改蓝图。系统现在只在任务真正提交并能对应到正式蓝图时报告完成；随后索引的是用户当前保留的资料。先完成的 AI 结果不会因为索引晚到而覆盖用户后来的决定，索引暂时失败也不会诱导用户重复生成或重复优化。

当前边界：

1. 蓝图资料同步目前由仍在页面中的前端在终态后触发。若用户离开页面且任务在离开后完成，可能错过这次自动同步；正式数据库结果和检索 freshness 仍保证错误资料不可见，用户可执行项目级全量同步恢复。只有真实出现无人值守自动收敛需求时，才考虑持久重试或 outbox。
2. 当前入口会同步项目全部角色档案，未变化记录由 content hash 跳过。只有大型角色项目的实际延迟证明这一步成为瓶颈时，才把本次新增或补全的 profile ID 纳入 generation 正式结果，不能提前复制角色匹配和变更判定逻辑。
3. 新增前端正式结果/部分成功测试、API command descriptor 测试、Runtime 反推 warning 测试、runtime/Tauri/server 编译、前端生产构建以及 Web API parity 已通过。

五十六、AI 大纲任务终态后按当前正式规划收敛资料索引，所有生成入口统一报告部分成功（2026-08-10）

继续审计大纲页后确认，大纲生成没有蓝图页曾经出现的“只拿到任务句柄就提示成功”问题：generation terminal 只会在分部或章纲正式写入完成后发布。但此前 AI 写入完成后不会同步 RAG，主页面的 4 条生成路径和高级工具中的 6 条生成路径也只刷新列表并固定提示成功。用户随后进行资料检索时，新规划可能暂时缺失；索引服务失败时，界面又无法区分“正式大纲已经完成”和“检索副本尚未跟上”。

现在的规则是：

1. 新增窄入口 `sync_outline_materials(projectId)`。它先验证项目编辑权限，再直接复用手工大纲维护已经使用的 `sync_outline_rag_records`，一次同步当前 PostgreSQL 中全部章节大纲与分部大纲；没有增加生成专用 chunk、单条同步协议或第二套大纲选择规则。
2. 所有大纲 AI 操作继续先等待 canonical generation terminal。只有正式分部或章纲写入成功后，共用 `useOutlineGeneration` 才进入“正在同步资料索引”阶段；任务启动、模型开始输出或返回任务句柄都不能触发同步和成功提示。
3. 同步逻辑放在所有页面操作共用的生成 Hook 中，因此同时覆盖生成/追加分部、按数量生成章纲、重生成单章、重生成最后一部，以及高级工具中的节拍映射、为指定分部生成章纲、批量生成、重生成指定分部、重生成全部分部和续作下一部。页面不再存在绕过同步的 AI 大纲入口。
4. 同步读取的是调用时数据库中的当前正式大纲，不保存任务启动时或模型返回时的资料副本。用户在 AI 运行期间或刚完成后继续编辑、删除、恢复规划时，索引会尽量收敛到用户当前保留的结果；同步期间来源再次变化会由现有前后集合核对返回 warning，通用检索 freshness 继续过滤已经被用户否定的旧向量。
5. 共用 Hook 返回 `warnings`，主页面和高级工具的全部 10 条操作都使用“正式成功 + 提交后警告”的提示。内部 RAG 某一步失败、正式资料在同步期间变化，或连 Host 同步命令本身都因网络和运行配置无法调用时，界面仍显示“大纲已生成/重生成”，同时说明资料索引待恢复，不能把已经提交的规划伪装成生成失败。
6. 反推章节大纲和分部大纲确认也复用同一个大纲同步 warning 入口，不再自己拼装另一套错误转换。蓝图资料同步的前端封装同时补齐了相同的命令调用失败降级，兑现上一节已经确定的双结果语义。
7. Host 合同已接通 Runtime、Tauri、Web server、API manifest 和生成的 TypeScript runtime-config 策略。`sync_outline_materials` 是项目上下文中的立即、可安全重试命令，返回现有 `OutlineMutationResult`；没有为这次同步增加通用 revision、墓碑、索引状态表、补偿队列或同步框架。

从用户创作方式看，大纲不是必须线性定稿后才能继续写作的前置表单。用户可能先生成三部，再手工删除最后一部；可能让 AI 批量生成章纲，同时回头重写某一章；也可能在任务完成后马上续作下一部。系统现在以每一次 PostgreSQL 正式提交为准，AI 完成只说明它自己的正式写入已经成功，随后索引的是用户此刻仍然保留的规划。时间决定正式提交的先后，不需要“暂定蓝图”或“暂定大纲”解释过程。

当前边界：

1. 本轮没有给大纲 terminal 伪造单一 `result_ref`。一次操作可能创建或替换多条分部和章纲，而当前 terminal 已保证只在正式操作成功后完成；只有以后出现跨页面恢复并必须逐条证明结果身份的真实需求时，才设计项目级大纲结果引用。
2. 自动同步仍由等待任务终态的页面流程触发。用户离开页面后若没有继续等待，可能错过这次自动收敛；正式数据库和检索 freshness 仍保证旧资料不可见，项目级“同步资料索引”可以恢复。只有无人值守收敛成为真实需求时，才增加持久任务，不预建 outbox。
3. 6 条前端资料同步测试、9 条 API manifest 测试、前端生产构建、API 合同检查、generation 合同检查、Web API parity 和目标 Rust 文件 rustfmt 检查已通过。`cargo check -p a4n-runtime -p a4n-tauri -p a4n-server` 当前被工作区已有的蓝图输入字段不一致阻塞：`NovelBlueprintUpsertInput` 调用方仍读取已不存在的 `now`，`InsertBlueprintVersionInput` 的调用方仍使用 `created_at` 而当前结构字段为 `now`；本轮没有越界修改这些无关并行改动。

五十七、复制、分支和导入先成立新项目，再从新项目当前正式资料重建检索副本（2026-08-10）

继续检查用户会怎样复用已有创作后确认，项目复制、创建分支、完整 JSON 导入和项目族导入都会创建新的项目 ID。此前这些操作只复制或导入 PostgreSQL 正式资料，不为新项目建立 RAG；源项目向量又绑定源项目 ID，不能直接作为新项目的检索资料。用户打开副本继续写作时，资料检索因此可能为空，直到主动执行一次“同步资料索引”。

现在的规则是：

1. 项目复制、分支和导入仍以 PostgreSQL 创建新项目成功作为正式完成边界。界面会先提示“已复制/已创建分支/已导入”并刷新项目列表，后续索引失败不能把已经存在的新项目重新报告成创建失败。
2. 正式创建完成后，前端复用现有 `ragIngestAll` 为新文本项目执行普通全量同步。同步读取新项目此刻实际拥有的蓝图、世界观、大纲、章节、角色、关系和场景资料，不复制源项目向量，也不假设文本副本包含源项目全部角色或场景档案。
3. 完整 JSON 导入直接同步返回的新文本项目；项目族包按既有包合同只选择其中唯一的文本根项目。漫画、视频和 GALGame 派生项目继续引用各自项目族中的文本根资料，不为每个派生项目重复建立一份文本 RAG。视频画布包没有文本正式资料，不触发这条同步。
4. 桌面本地 embedding 继续由前端分批计算，Web/Server 模式继续由后端 embedding；两种运行方式统一走同一个现有 API。没有把同步塞进复制或导入后端事务，因为后端无法替桌面本地模型计算向量，也不能让外部向量服务决定 PostgreSQL 事务是否成功。
5. 本地 embedding 上传前会重新读取新项目当前 canonical 资料，比较 prepare 时的内容 hash，并复核来源仍然新鲜。用户若在索引计算期间已经修改资料，旧上传会被拒绝并提示重新同步，不能覆盖或复活用户的新决定；通用检索 freshness 仍会过滤不再匹配正式资料的旧向量。
6. 索引同步使用现有进度和停止入口。同步失败、用户停止或 embedding 配置不可用时，只提示“正式资料已保存，资料索引待恢复”，并明确可从项目操作重新同步；不会自动重试创建、复制、分支或导入。
7. 新建的空白自由创作/AI 辅助创作文本项目不额外执行空索引任务，因为此时没有需要搬运的正式资料。两种创作入口的区别仍只是用户从哪里开始创作，不产生两套资料事实或同步规则。

从用户创作方式看，复制和分支不是把一个不可变快照永久封存，而是从已有内容开启另一条可以马上修改的新创作线；导入则是把外部已有作品接回当前系统。新项目一旦创建就拥有自己的正式事实，后续索引只能追随这个新项目当前保留的内容。用户不需要等待索引成功才能继续创作，旧源项目的向量也不能因为复制发生得更早就取得事实优先级。

当前边界：

1. 自动同步仍是创建操作后的前台收敛。如果用户在正式创建后立即关闭应用，可能错过本次索引；项目级“同步资料索引”是现有恢复入口。只有真实出现大量无人值守导入并要求自动恢复时，才考虑持久任务或 outbox。
2. 当前项目族合同只允许一个文本根项目，因此只同步一个根项目。以后若产品真的允许一个包中包含多个独立文本根项目，再按返回的正式项目集合逐个同步，当前不预建批处理框架。
3. 新增的部分成功测试连同大纲、世界观和反推候选 warning 回归共 11 条通过；前端生产构建、API/generation 合同、Web API parity 和目标文件 `git diff --check` 均已通过。

五十八、场景档案的提交后警告使用信息提示，不能用红色错误否定正式保存（2026-08-10）

场景档案创建、修改和删除已经返回“正式数据库结果 + `warnings`”，但前端在只有 RAG 更新或下游图片清理警告时仍使用红色错误 toast。用户会自然理解为保存或删除失败，并可能重复操作。

现在创建、修改和删除场景档案仍正常刷新并展示 PostgreSQL 当前结果；`warnings` 非空时使用信息提示，明确说明正式操作已经完成以及哪些索引或清理副作用待恢复。只有正式数据库操作本身失败才使用错误提示。本轮没有增加场景 revision、索引状态字段或静默兜底。

五十九、正文先保存，派生资料同步状态不能否定用户已经写下的章节（2026-08-10）

继续检查用户最频繁的写作动作后确认，写作桌首次保存、修改已有章节、AI 生成正文和章节页外部导入都复用同一套章节正式写入。用户可以先写第七章、回头补第二章，也可以导入旧稿后继续改写；正文顺序不是系统事务顺序。后端已经允许非连续章节，并在正文提交后创建可恢复的 `chapter_content_sync` workflow，负责清理旧分析、角色状态、场景等派生资料，重新处理正文、同步章节 RAG 和刷新项目进度。

这条后端链路已经具备非线性创作需要的关键门禁：

1. PostgreSQL 正文保存先完成，派生同步失败不会回滚用户刚写下的正文。失败状态、错误信息、workflow run ID 和是否可恢复会投影到当前章节摘要。
2. 每次正文修改都会形成新的内容指纹和同步 workflow。旧同步在清理、重新处理或写入 RAG 前都会确认自己仍对应当前正文；用户再次修改后，旧任务只能被 supersede，不能把旧分析、角色状态或旧章节向量重新写回当前创作线。
3. 用户可以从章节顶部重试失败的派生同步。重试继续使用当前 workflow 及其清理计划，不要求重新保存正文，也不增加正文 revision、墓碑或第二份章节事实。

当前修正的是前端对这条正式边界的表达：

1. `importChapter` 不再返回 `unknown`，而是返回后端实际的 `ChapterData`。章节页外部导入可以立即判断派生同步是完成、进行中还是失败，而不是固定提示全部成功后再让用户从列表猜测。
2. 外部导入、写作桌手工保存和 AI 正文生成都把“正文已经保存，但派生资料同步失败”作为信息提示；只有正文正式写入本身失败才使用红色错误。失败章节仍在顶部保留明显状态和“重试资料同步”入口。
3. 写作桌首次保存会保留 `importChapter` 返回的正式章节作为结果，即使随后刷新列表暂时没有返回该行，也不会丢失本次保存后的同步状态或把编辑器重新解释成未保存。
4. 章节结构化分析已经写入 PostgreSQL、但伏笔/RAG/物体/角色/场景等派生同步失败时，同样使用“分析已保存，继续同步”的信息提示，避免用户重复调用模型生成另一份分析。

从用户角度看，正文是创作行为本身，分析、角色状态、场景档案和检索索引是围绕正文形成的可恢复资料。资料系统可以暂时落后，但不能用一个红色“保存失败”让用户怀疑自己的文字是否存在，更不能诱导用户重复保存或重复生成。章节摘要中的 workflow 状态只是派生资料跟进情况，不是第二份正文状态。

当前边界：

1. 初次章节结构化分析在分析已保存、后续派生同步失败时，交互式命令已经直接返回“正式章节 + warnings”；严格导入和后台恢复入口仍把 warning 提升为错误。模型失败、checkpoint 未写成、用户取消或正文来源变化不会被伪装成部分成功。
2. 项目重置仍是下一处需要单独处理的破坏性边界：数据库重置、RAG 清理和 lifecycle gate 完成由后台接续保证，目前一次清理失败仍可能让界面显示笼统的“重置失败”。它涉及项目在清理完成前是否允许继续写作，不能只改 toast。
3. 章节、新项目、大纲和反推 warning 回归共 13 条通过；前端生产构建和目标文件 `git diff --check` 已通过。

六十、项目重置按正式提交阶段报告，重置收尾期间只读而不能继续写入（2026-08-10）

继续检查项目重置后确认，它不是一次普通的“删除后刷新”操作，而是三个有明确先后的阶段：先提交 PostgreSQL 正式资料重置，再清理项目 RAG，最后把持久化的 `lifecycle_gate` 从 `resetting` 恢复为 `active`。此前任一后续阶段失败都会让 API 返回普通错误，界面因此显示“重置失败”；但数据库可能已经删除章节和规划，后台 continuation 也可能已经接管。用户若据此重复重置或继续编辑，界面表达就会与真实项目状态冲突。

现在的规则是：

1. 重置 API 返回 `completed | pending`、`database_committed`、可选删除统计和 `warnings`。`pending + database_committed=false` 只说明请求和 gate 已经被系统接管，不宣称资料已经删除；`pending + database_committed=true` 明确说明 PostgreSQL 正式资料已经重置，只剩索引清理或 gate 收尾；`completed` 才表示三个阶段都完成。
2. generation 任务排空失败、数据库暂时不可用、RAG 清理失败或 gate 完成失败时，只要 `resetting` 已经持久化并安排后台接续，API 就返回 `pending`，不再用普通错误诱导用户重复操作。只有尚未形成不可逆进度、并且 gate 已安全恢复为 `active` 的失败才继续返回错误。
3. PostgreSQL 已提交后，RAG 清理失败会保留本次真实删除统计并作为 warning 返回；RAG 已清理但 gate 完成失败时，同样报告“正式资料和索引已完成、项目仍在收尾”。后台在同一进程内记住数据库已经提交，后续重试只继续 RAG/gate，不在每秒重做一次数据库重置；Host 重启后则从持久 gate 恢复一次幂等重置再继续收尾。标准文本、Galgame 和自由创作视频项目的数据库事务都只提交正式资料，不再由某一种项目提前把 gate 恢复为 `active`。
4. 项目状态事件发布发生在数据库提交之后。事件总线失败现在只记录 warning，不能推翻已经提交的正式重置，也不能让调用方把已删除资料误解成仍然存在。
5. `ProjectSummary` 直接暴露现有 `lifecycle_gate`，没有新增第二套重置状态表。项目列表会显示“重置收尾中/删除中”；项目详情、写作桌和 Galgame 工作区显示只读提示，并在 gate 恢复后自动刷新或重建工作区内容。
6. 共用项目权限边界现在同时检查角色和项目 gate。Viewer 读取继续允许；Editor、Manager、Owner 发起的普通资料写入在目标项目或其文本根项目不是 `active` 时统一拒绝。因此用户可以查看重置进度和旧页面，但不能在后台重置随后会删除的新章节、章纲、角色或媒体资料上继续形成新的正式提交。破坏性重置自身不走普通写 gate，而由 `begin_project_gate` 直接校验真实 owner，避免重试请求被自己的 `resetting` 状态挡住。
7. 前端只在 `database_committed=true` 时立即清空正文、章纲和工作区派生状态；数据库尚未提交时保留当前内容供只读核对。页面轮询正式项目摘要，gate 恢复为 `active` 后再统一清空/刷新，并提示可以继续创作。重复点击重置只会得到“已经在后台执行”，不会再次启动一轮重置。
8. Host 启动时不再同步阻塞等待所有 pending destructive operation 完成。它先中断上次进程遗留的 generation attempt，再为持久化的 deleting/resetting/disabling gate 安排现有后台 continuation；应用可以正常启动并把项目显示为只读收尾状态，不需要新增 outbox、重置阶段表或通用同步框架。

从用户创作方式看，重置是一项明确否定当前生成资料的决定，但清理外部索引可能比数据库提交慢。系统现在准确区分“尚未正式删除”“正式资料已删除但仍在清理”和“全部完成”。用户不需要猜一次红色错误到底有没有删掉正文，也不会在后台重置期间继续写入随后被删除的新内容。

当前边界：

1. 共用权限检查会阻止 gate 持久化之后发起的新写请求。极窄的并发窗口仍然存在：某个请求可能在 gate 切换前已经通过权限检查、但尚未进入自己的数据库写事务。彻底消除这一窗口需要所有正式写事务在同一事务内锁定并复核项目 gate，或引入数据库级统一写门禁；应结合真实 PostgreSQL 并发测试逐步收口，不能用页面禁用代替后端规则。
2. 当前没有持久化“数据库阶段已完成”这一额外状态。首次请求能准确返回 `database_committed`；Host 重启或另一客户端只看到既有 `resetting` gate 时，系统保守报告 pending，不猜测资料是否已经删除，待 gate 恢复后再刷新正式事实。
3. lifecycle gate 单元测试、相关前端回归、TypeScript 检查、前端生产构建、API/generation 合同、Web API parity、`a4n-runtime/a4n-tauri` 编译和目标文件差异检查已通过。自由创作视频项目新增了“数据库提交后 gate 仍为 `resetting`”的 PostgreSQL 回归断言，代码已完成编译；当前环境缺少 `A4N_TEST_DATABASE_URL`，因此不能声称已执行真实数据库断言。多标签页并发写入与重置时序也仍需在配置隔离测试库后补跑。

六十一、章节分析部分成功必须走正式结果合同（2026-08-10）

上一节确认了用户不应因为派生资料落后而重复生成结构化分析；继续沿调用链检查后发现，仅靠前端在错误后重新读取章节仍有两个问题：客户端必须猜测错误属于模型阶段还是同步阶段，Web 和 Tauri 的返回语义也不一致。这里不引入新的同步状态表，而是让本轮结果直接表达已经成立的事实。

现在的规则是：

1. 章节分析写入 PostgreSQL 后立即写入现有 `chapter_analysis.analysis_stored` checkpoint。只有该 checkpoint 成功、当前正文来源快照仍匹配、workflow 仍可恢复时，交互式 `generate_chapter_analysis` 才返回 `ChapterAnalysisMutationResult { chapter, warnings }`。
2. warning 只描述伏笔、RAG、物体、角色、场景或项目状态等后续派生同步未完成；返回的 `chapter` 仍由现有 `ChapterSummary` 和数据库同步状态投影生成。用户因此可以继续编辑，也可以从已有“继续同步”入口恢复，不会再次调用模型覆盖已保存分析。
3. 模型调用、分析持久化、checkpoint 写入、用户取消、正文来源变化和终态写入失败仍是真错误。导入分析和后台 workflow 恢复复用严格入口，不能把交互式 warning 静默当成整批导入成功。
4. 前端成功路径读取 `warnings` 显示信息提示；异常 fallback 只使用持久化的 `analysis_sync_can_resume`，不再依赖错误字符串前缀。生成成功进度文案只承诺“结构化分析已保存”，不宣称所有派生资料已经完成。

这与非线性创作方式一致：用户一次模型分析得到的结构化结果是当前正文的正式派生事实，资料索引和档案投影只是可恢复的跟进工作。系统必须把“已保存”和“尚未同步”同时告诉用户，而不是用一个布尔成功/失败覆盖两个不同事实。

本轮边界：

1. `resume_chapter_analysis_sync` 仍保持严格返回，因为它本身就是用户明确点击的恢复动作；如果恢复再次失败，持久化状态和错误会保留，用户可以继续重试。
2. 目前只把章节分析生成入口改为交互式结果合同，没有抽象通用 mutation envelope；等另一条真实工作流需要同样语义时再复用，不预建全局结果框架。
3. `a4n-orchestrator/a4n-runtime/a4n-tauri/a4n-server` 编译、章节分析 3 条 application 单测与 13 条 workflow 合同测试、前端生产构建、155 条 Vitest、API/generation 合同、Web parity、目标 Rust 格式和 `git diff --check` 已通过。真实 PostgreSQL 集成测试仍需 `A4N_TEST_DATABASE_URL`；`a4n-runtime` 全库测试目标本次只完成编译检查，过滤测试在链接阶段超过默认超时，不能把它报告为已执行通过。

六十二、正文与正式大纲写入在事务内服从项目重置门禁（2026-08-10）

上一轮项目重置已经在权限边界阻止 `resetting/deleting` 项目的新写请求，但仍存在一个真实并发窗口：请求可能先通过权限检查，随后另一标签页启动重置，旧请求才进入正式数据库事务。对于正文或大纲，这会产生两类用户无法接受的结果：界面提示保存成功后内容又被本次重置删除，或数据库重置已经提交后，迟到的插入重新留下章节和规划资料。

现在的规则是：

1. 项目写入门禁只保留现有 `novel_project.lifecycle_gate` 一份事实。新增的共享纯规则只判断项目是否仍为 `active`，不建立写锁表、revision、重置阶段表或第二套同步状态。
2. 写作桌手工正文编辑、外部章节导入和新章节写入都在正式事务中先锁定项目行并复核 gate，再锁定目标章节或项目章节集合。gate 不是 `active` 时，正文、章节资料清理计划和 workflow checkpoint 都不写入。事务外为了定位 `project_id` 进行的普通读取不是正式锁，不改变该锁序。
3. AI 正文生成的正式提交统一采用“项目行 → 章节集合/目标章节 → 章纲行”锁序。任务可以在重置前启动、模型也可以稍后返回，但 `resetting/deleting` 已经成立时，旧正文不能成为正式章节；生成期间章纲发生变化时仍由现有来源快照拒绝旧结果。
4. 手工章纲更新、分部同步/更新/删除、章节大纲同步，以及导入分析产生的回顾性章纲写入，都在已有事务项目锁后执行同一 gate 规则。正式大纲生成的所有入口继续共用 `lock_outline_generation_sources`，因此不需要逐个页面补判断。
5. 导入分析蓝图候选和分部候选的“确认”也是正式创作决定。确认事务锁定正文和项目后会复核 gate，不能因为用户在重置前打开了候选页，就在重置收尾期间继续把候选写回正式资料。
6. 并发先后由项目行锁给出明确含义：若普通写事务先取得锁并提交，随后取得锁的重置会把它作为重置前资料正常清除；若重置先把 gate 持久化，迟到写事务等待后会读到非 active 状态并明确失败。页面按钮禁用只是提示，数据库事务才是最终边界。
7. 这些失败继续使用现有 `InvalidState` 合同，Host 和前端会收到“项目正在重置或删除，完成前暂不可编辑”。没有为这次修复新增 Host 命令、前端状态或通用 mutation envelope。

从用户创作方式看，多标签页并不罕见：用户可能在写作桌保存第十章，同时在项目列表确认重置；也可能等待批量章纲生成时决定清空项目重新开始。系统现在不会让较早通过权限检查、但更晚进入事务的请求绕过用户最新的重置决定。时间只决定两个正式事务的提交顺序，不生成“重置前草稿”或“暂定大纲”。

当前边界：

1. 本节记录的是正文和正式大纲的第一批收口。后续审计已经继续覆盖角色、物品、场景、世界观、蓝图、媒体、分析、导入审核、优化、立绘、画布和灵感对话，详见下一节；不能再把本节旧边界理解为当前实现状态。
2. 已增加一条 PostgreSQL 数据库回归，覆盖手工正文编辑、外部导入和 AI 正文提交在 `resetting` 时均不写入；当前环境缺少 `A4N_TEST_DATABASE_URL`，测试目标已编译，但真实数据库断言未执行。共享 gate 纯规则测试已执行通过。
3. `cargo check -p a4n-db -p a4n-orchestrator -p a4n-runtime`、目标 Rust 格式和目标文件 `git diff --check` 已通过。真实双连接下“普通写事务先获得项目锁 / 重置 gate 先提交”的两种等待顺序，仍应在隔离 PostgreSQL 测试库配置后补跑。

六十三、正式资料写入统一项目优先锁序，分析、画布和会话不再在重置后复活（2026-08-10）

继续沿项目重置真正会清理的数据库表反查写入入口后确认，仅在 Runtime 权限层禁用按钮还不够。用户可能在多个标签页同时等待分析、生成立绘、应用优化补丁或操作视频画布；这些请求都可能在通过权限检查后才进入数据库。要让非线性创作与项目设计自洽，系统必须在每一次正式提交时重新回答同一个问题：这份资料是否仍属于用户当前保留的项目事实。

现在的规则是：

1. 同一项目的正式业务写入统一采用“项目行锁 + `lifecycle_gate` → 来源或目标子资料行 → 正式写入”的顺序。派生项目写入会把目标项目和文本根项目按 ID 稳定排序后一并锁定并复核 gate，避免根项目已经重置时继续向漫画/视频等派生项目登记旧媒体。项目重置也先锁项目行再清理子资料，因此普通写入与重置只有明确的先后，不再出现章节、档案或画布行先锁、随后反向等待项目行的等待环。事务外为了找到 `project_id` 的普通 hint 读取不构成业务锁，取得项目锁后必须重读并校验真正目标。
2. 角色属性、角色发现与同步、物品发现、场景档案与同步、世界观、蓝图生成/优化/恢复、正式大纲、正文、媒体资产、生成图片/视频、章节分析、样式标签、伏笔、章节场景、导入分析进度和导入审核都在自己的正式事务内复核同一 gate。分析结果仍先写当前章节的 PostgreSQL 正式记录，角色、物品、场景、伏笔和 RAG 作为可恢复的派生收敛分别跟进；不会因为后续同步失败产生另一份分析事实。
3. 内容优化只在创建新会话和真正应用正文补丁时形成新的项目资料。创建会话先锁项目再核对章节归属；应用补丁先锁项目、再锁当前章节，并比较补丁生成时正文与事务内当前正文。用户在模型运行期间已经改稿时，旧补丁明确返回 `optimization_chapter_source_changed`，不能覆盖新正文。
4. 角色立绘的 AI 生成、手工上传和主图切换都先锁项目，再锁角色档案或立绘行。图片文件可能已经在事务外生成或上传，但 gate 拒绝数据库登记时会沿用现有文件清理路径；不能因为模型或文件操作较早开始，就在重置完成后重新留下立绘记录。
5. 视频画布的默认画布创建、画布保存、文本资料、自由创作生成意图、节点产物/观察结果、成片时间线和媒体登记都服从同一 gate。用户打开已有画布仍是只读操作；只有确实需要创建默认画布时才进入写事务。重置先成立时，迟到的生成结果不能重新绑定已清理媒体，也不能把节点状态改回“已完成”。
6. 灵感历史读取不再隐式创建空对话。没有历史时直接返回空列表；第一轮用户/助手正式回复在 generation 终态事务内锁定项目、复核 gate，再创建对话和两条消息。这样重置期间查看只读页面不会写数据库，迟到模型回复也不能复活已删除对话。
7. 删除类操作仍按可交换操作处理：用户删除与项目重置都把同一记录变成不存在时，不额外增加 gate、墓碑或删除 revision。需要门禁的是可能插入、覆盖、切换主记录或重新建立引用的操作。PostgreSQL 提交与提交后的 RAG、文件清理等外部副作用继续分别报告，不用一个“同步成功”布尔值否定已经成立的正式事实。
8. 本轮继续复用现有事务、项目行锁、来源快照和 `InvalidState` 合同，没有新增“暂定蓝图”、通用 revision、重置阶段表、写锁表、outbox 或第二套同步状态。时间只决定哪个正式事务先取得项目锁，不产生一份依赖时间命名的临时创作事实。

从用户创作方式看，用户可以先写后章再补前章，可以在 AI 分析期间修改正文，也可以等待图片或视频生成时决定重置项目。系统不要求用户冻结整个创作过程；它只在结果准备成为正式资料的最后一步检查当前项目和当前来源。先提交的普通写入会被随后重置正常清理，先成立的重置会拒绝迟到结果，这正好对应用户最后一次已经提交的明确决定。

1. 新增回归覆盖优化旧补丁、优化会话、角色立绘、画布正式资料、灵感对话以及根项目重置时派生媒体写入的拒绝；`cargo test -p a4n-db --no-run` 已证明全部测试目标可编译，纯 gate 规则测试已实际通过。当前环境仍未配置 `A4N_TEST_DATABASE_URL`，因此不能声称这些 PostgreSQL 断言已真实执行。

六十四、章节视频时间线是正式剪辑资料，写入继续服从项目优先锁序（2026-08-10）

继续审查新接入的章节视频时间线后确认，时间线不是只供界面排序的临时状态。创建时间线、提交 AI 插入片段、按当前原生规划收敛时间线和移动插入片段，都会正式写入提示词、时间线项、链表指针、revision 与操作事件；项目重置和媒体工作流重置又会删除这些记录。此前这些入口只锁时间线，可能在另一标签页已经成立项目重置后仍短暂提交成功，随后又被重置清除。

现在的规则是：

1. 获取或创建章节视频时间线在自己的数据库事务中先按既有规则锁定目标项目和文本根项目、复核两边 `lifecycle_gate`，再执行幂等插入和正式读取。重置先成立时，即使调用名是 `ensure`，也不能重新创建一条马上会被清理的时间线。
2. 提交插入片段、同步原生时间线和移动插入片段先只读时间线取得项目提示，再按“目标项目/文本根项目 → 时间线”重新加锁；加锁后复核时间线仍属于同一项目。这样既服从项目重置锁序，也保留现有 timeline revision 对同一时间线编辑冲突的精确判断。
3. 时间线历史和快照读取仍是只读操作，不要求项目保持 `active`。删除插入片段继续视为与项目重置可交换的删除操作，不机械增加 gate；若删除先提交，重置随后清理整条时间线，若重置先删除时间线，迟到删除得到不存在，不会复活资料。
4. 本轮没有新增项目 revision、时间线同步状态、墓碑或补偿任务。项目 gate 只回答“当前还能否形成新正式资料”，timeline revision 只回答“用户是否基于当前排序进行编辑”，两者职责保持分离。

从用户创作方式看，用户可能一边等待插入镜头生成，一边决定重置视频资料，也可能在另一个页面重新生成原生片段规划。系统现在只允许在项目仍可编辑、且时间线 revision 仍匹配时提交；模型先启动或草稿先生成都不取得事实优先级。

1. 已新增 PostgreSQL 回归，覆盖时间线创建和原生时间线收敛在项目 `resetting` 时被拒绝；`cargo test -p a4n-db --no-run` 已通过，但当前环境没有 `A4N_TEST_DATABASE_URL`，因此这条数据库断言尚未真实执行。
2. `cargo check -p a4n-db`、目标纯单测和 `git diff --check` 已通过。真实双连接下项目重置与时间线提交的等待顺序仍需在隔离 PostgreSQL 测试库中执行。

六十五、来源同步预览会冻结正式快照，应用和脱离必须与根文本修改串行（2026-08-10）

继续检查根文本与视频、漫画、Galgame 派生项目之间的现有来源同步后确认，冲突类型和用户决策模型已经能够表达保留本地、采用来源、重建提示词、重新绑定锚点、创建替换版本、局部重生成和脱离来源。真正缺失的是事务边界：所谓“预览”会创建不可变源快照、同步运行和冲突记录，应用会修改生成意图、提示词、锚点、Galgame 场景及派生项目当前快照，但此前这些事务没有先锁定项目族。

现在的规则是：

1. 来源同步预览不是普通只读查询。事务先按 ID 稳定顺序锁定派生项目和文本根项目，并复核两边 `lifecycle_gate`，随后才从根项目当前正文、分析、档案、蓝图版本和章纲构建同一份目标快照，再计算差异并写入 run/conflict。这样一次预览不会跨越另一标签页的正文提交或项目重置，拼出来自两个时刻的混合快照。
2. 来源同步应用先用 run 做普通定位，再锁定派生项目和文本根项目，之后锁定并重读 run。run 的项目族和起止快照身份若在等待期间变化会被明确拒绝；同一派生项目的两个标签页不能同时把两组冲突决策写入生成意图、锚点或场景。
3. 项目锁成立后仍保留现有来源复核：派生项目必须仍绑定 run 期望的起点/目标快照，不能已经脱离；根项目按当前章节范围重新计算的版本哈希必须仍等于预览保存的目标快照。项目 gate 解决“当前能否写”，快照哈希解决“写入依据是否仍然有效”，二者不能互相替代。
4. “脱离来源同步”改为在事务内按项目 ID 重读并锁定当前派生项目和根项目，再更新 `source_sync_status=detached`；不再把权限检查阶段读取的旧项目模型直接保存。应用决策中的 detach 继续复用同一已锁定事务内的窄更新。
5. `source_sync_status` 继续只表达派生项目与根文本的关系状态，source snapshot 继续保存一次不可变来源事实，sync run/conflict/decision 继续保存一次预览与用户处理过程。没有新增“暂定蓝图”、项目 revision、第二套当前来源、全局同步状态或后台补偿框架。

从用户创作方式看，用户可能一边修改根文本，一边在视频工作台打开来源同步对话框，也可能在两个标签页对同一批冲突作出不同选择。系统现在以项目锁确定哪次正式操作在先：先完成的根文本修改会进入随后构建的完整快照；先完成的同步应用会基于它已经核验的快照提交。等待期间失效的旧预览只会明确过期，不会覆盖用户后来形成的正文或派生资料。

当前边界：

1. 新增 PostgreSQL 回归覆盖根项目 `resetting` 时拒绝创建来源同步预览、应用既有 run 和脱离来源；测试目标已经编译。当前环境没有 `A4N_TEST_DATABASE_URL`，不能声称数据库断言已实际执行。
2. `cargo check -p a4n-db -p a4n-orchestrator`、`cargo test -p a4n-db --no-run`、目标来源同步纯单测和 `git diff --check` 已通过。真实双连接下根正文写入、项目重置、两个同步应用之间的等待顺序仍需隔离 PostgreSQL 测试库验证。

六十六、独立新建不依赖旧资料，派生创建、复制和分支必须冻结来源项目（2026-08-10）

继续沿“从现有作品开始另一条创作线”的真实操作检查后确认，不能只因为结果拥有新项目 ID，就把所有创建操作都视为与来源无关。空白项目和外部包导入的事实来自用户输入；派生项目、项目副本和文本分支则会读取当前项目的蓝图、大纲、正文、快照、画布、生成意图、媒体和引用图。如果调用前读到一个 `original`，事务内却不锁来源，复制结果可能混合用户复制期间先后提交的不同版本，或者在项目重置已经成立后保存一份用户刚否定的旧资料。

现在的规则是：

1. 创建漫画、视频或 Galgame 派生项目继续先锁根文本项目，再复核根项目 `lifecycle_gate`，随后在同一事务中构建不可变源快照、创建派生项目和派生关系。重置先成立时不能从待清理资料创建新派生项目；派生创建先提交时，后续根项目修改或重置仍通过现有 `source_sync_status=root_updated` 提醒其来源已经变化。
2. 独立创建源文本快照的窄数据库入口也在事务内锁定并复核根项目，避免公开入口绕过同一规则。内部 `create_source_snapshot_in_record` 继续由已经锁定根项目的派生创建或来源同步事务调用，不增加第二套快照生成协议。
3. 文本复制和文本分支在事务内按项目 ID 重读并锁定当前来源项目，再根据锁后的状态、蓝图、大纲和正文进行复制；调用前权限检查读取的 `original` 只用于定位，不能继续充当正式复制来源。
4. 派生项目复制会同时锁定派生项目和文本根项目；自由视频复制锁定自身项目。三类复制都从锁后的当前项目模型开始复制本地生成意图、画布、媒体和引用图，复制期间普通写入与重置只能等待，不能产生跨两个时刻的混合副本。
5. 媒体文件仍沿用现有“数据库复制事务 + 调用方失败清理”边界。gate 在任何文件复制前检查；若后续数据库或文件复制失败，现有 rollback 会清理本次已经复制的文件。本轮没有为了复制创建跨文件系统事务、copy revision、临时项目状态或补偿队列。
6. 空白自由创作/AI 辅助创作项目和外部项目包导入继续不锁一个不存在的“旧项目”，因为它们的正式来源就是本次输入。规则按数据依赖区分，而不是按结果是否为新项目机械分类。

从用户创作方式看，“复制”通常意味着在某个确定版本上开始另一条创作线，而不是把复制按钮点击期间不断变化的数据库拼成一份结果。系统现在让正式事务顺序决定版本：复制先锁定并提交，随后修改只影响原项目；修改或重置先提交，复制读取新结果或明确拒绝。无需引入依赖点击时间命名的暂定副本。

当前边界：

1. 新增 PostgreSQL 回归覆盖根项目 `resetting` 时拒绝显式源快照、派生项目创建、文本复制和文本分支；来源同步回归同时覆盖预览、应用与脱离。测试目标已编译，当前环境缺少 `A4N_TEST_DATABASE_URL`，数据库断言尚未实际执行。
2. `cargo check -p a4n-db -p a4n-orchestrator`、`cargo test -p a4n-db --no-run`、目标复制/来源同步纯单测和 `git diff --check` 已通过。派生/自由视频媒体复制与项目重置的真实等待顺序仍需隔离 PostgreSQL 测试库验证。

六十七、项目族包与视频画布包必须来自同一个正式资料快照（2026-08-10）

继续沿用户“导出当前作品留档、迁移或交给其他设备继续创作”的操作检查后确认，项目族导出此前先读取根项目和派生项目选择，再分二十余次读取正文结构、源快照、生成意图、媒体、Galgame、时间线和来源同步记录；视频画布也先单独读取项目，再分十余次读取画布、生成规格、图片、视频、媒体资产和成片时间线。PostgreSQL 默认 `READ COMMITTED` 会让每条查询看到各自开始时的已提交状态，因此用户在导出期间继续写作、调整画布或生成媒体时，一个包可能拼接多个提交时刻。

现在的规则是：

1. 项目族包新增唯一高层读取入口，在一次只读 `REPEATABLE READ` 事务中完成根项目/派生项目选择以及全部正式行读取。根项目、派生项目、它们引用的源快照和所有下游资料都来自事务第一次读取建立的同一数据库快照。
2. 视频画布包同样在一次只读 `REPEATABLE READ` 事务中读取项目模型和全部画布、生成、媒体及时间线记录。包名、项目标题与包内资料不再分别来自两个时刻。
3. 快照开始时会检查所有被导出的项目仍处于 `active`。项目或任一派生项目已经进入 `resetting/deleting` 等过渡态时明确拒绝导出，不能把一次尚未完成的重置过程当成可迁移作品。
4. 原来可分别调用的“只选择项目”“只读取导出行”入口收回数据库模块内部，Orchestrator 只能取得已经配对的 `(selection/project, rows)` 快照结果，不能再无意间恢复分段读取旁路。
5. 普通编辑不需要为导出停笔，也不需要取得项目写锁。导出快照先成立时，随后提交的正文、画布或媒体留给下一次导出；编辑先提交时，本次导出会完整包含新结果。时间决定快照边界，但不会生成一份叫“暂定导出状态”的第二事实。
6. 数据库快照完成后，Host 继续按快照中的媒体路径读取全部文件字节，再开始生成 zip。任一文件已经被清理或不可读时，现有逻辑会让整次导出失败，不会静默跳过文件或输出缺件包；全部文件已读入内存后，即使原路径随后被清理，包仍使用本次已经取得的字节。
7. 本轮没有增加 export revision、导出锁表、临时项目状态、文件系统事务、outbox 或补偿框架。数据库原生一致快照已经解决多查询混合问题，媒体缺失继续作为显式失败处理。

从用户创作方式看，导出不是要求用户先把整个非线性创作过程“定稿”，而是截取按下导出时已经正式保存的一张照片。用户可以在另一标签页继续写下一章或调整镜头；这些后来提交的资料应整体进入下一张照片，而不是有一半混进当前包。系统因此冻结的是一次读取视图，不是冻结用户的创作活动。

当前边界：

1. 新增双连接 PostgreSQL 回归：导出事务已经读取项目并等待后续表时，另一连接新提交的章节不能进入同一个项目族包；另有项目族根项目和视频画布项目在 `resetting` 时拒绝导出的回归。测试目标已编译，但当前环境仍缺少 `A4N_TEST_DATABASE_URL`，因此这些数据库断言尚未实际执行。
2. `cargo check -p a4n-db -p a4n-orchestrator -p a4n-runtime`、`cargo test -p a4n-db --no-run` 以及两条 Runtime transfer owner 回归已通过；本轮目标 Rust 文件的 `rustfmt --check` 通过。全工作区 `cargo fmt --all -- --check` 仍被本轮范围外的 API 合同和视频提示词文件既有格式差异阻塞。
3. 当前媒体输出按持久化路径作为不可变生成结果使用；重置与文件清理交错时要么读到本次快照引用的完整旧字节，要么显式失败。只有以后真的允许原路径原地覆盖，或产品要求“即使同时重置也必须保证导出成功”，才需要增加文件内容哈希复核或临时文件快照，当前不预建。

六十八、无标题正文也必须能够成为非线性资料生长的起点（2026-08-10）

重新按用户定义的目标核对创建入口和章节分析后确认，顶层创建代码已经只保留 AI 辅助创作、自由创作和视频画布三项，项目导入是独立恢复操作，正文导入与分析位于文本项目内部。真正存在的用户阻塞是：导入章节界面明确允许标题为空，但章节分析请求和回顾性章纲生成却要求章节预先有标题。用户只有正文初稿、尚未决定章节名时，会在最需要“分析后逐步补资料”的场景被拒绝。

现在的规则是：

1. 章节模型提供唯一的展示标题规则：优先使用去除首尾空白后的用户标题；标题缺失或为空时使用中性的“第 N 章”。该标签只用于模型上下文、资料归纳和界面可读性，不会反向写入章节标题，也不会伪造用户已经完成命名。
2. 章节分析四阶段请求及稳定上下文都使用这条规则。用户可以只保存正文就执行分析，角色、场景、物体、伏笔和章节摘要不再被“必须先命名”这一无业务依据的门禁阻塞。
3. 分析完成后的回顾性章纲同样允许无标题章节，以“第 N 章”作为中性标题；已有用户章纲仍保持优先，不会被自动分析覆盖。分部大纲和蓝图归纳所使用的章节摘要也接受无标题章节，并避免生成“第3章《第3章》”这样的重复标签。
4. 创建模式文案同步明确真实边界：AI 辅助创作从 idea 进入灵感、蓝图、大纲和正文链路；自由创作可以从已有设定、大纲、正文或空白章节开始，并按需要调用 AI。设计文档不再把导入分析描述为第四种创作模式。
5. 本轮没有增加“无标题状态”、自动标题候选、暂定章纲或第二套章节事实。以后若产品需要 AI 起名，应作为用户可确认的单独建议，而不能借分析动作静默改写正文标题。

从用户创作方式看，章节名通常不是开始写作或开始整理资料的必要条件。有人先写完场景再命名，有人直到分部结构稳定后才统一调整标题；系统应允许正文先成为事实，再从正文长出局部资料，而不是要求用户为了通过流程先填写一个并不认可的名字。

当前边界：

1. `a4n-core` 的标题回退单测已实际通过；章节分析请求和回顾性章纲各新增无标题回归。Orchestrator 目标测试在 60 秒后端单测上限内仍停留在工作区重编译，不能声称已执行通过。
2. `cargo check -p a4n-orchestrator` 被本轮范围外的 `a4n-db` shooting script 模块引用缺失阻断：当前工作树的 `a4n-db/src/shooting_script/*` 仍引用不存在的 `a4n_core::shooting_script`。本轮没有顺手修改这条并行工作区问题。
3. 下一项仍需继续处理的是重新分析的替换时序：当前流程会在模型返回前先清理旧的角色时间线、场景、锚点和伏笔派生记录。需要把它调整为新分析已经成功产生后再进入可恢复替换，避免模型失败让用户现有可用资料先消失；这属于资料更新语义本身，不再转去扩展通用并发设施。

六十九、重新分析先生成新结果，再替换旧派生资料（2026-08-10）

继续沿着“写完一章再分析”的真实操作检查后确认，重新分析原先会先清理本章已有的角色时间线、场景记录、文本锚点和伏笔派生资料，然后才调用模型。模型超时、返回无效结构或被用户取消时，新结果尚未产生，旧资料却已经先消失；用户只是想尝试更新分析，不应因此失去当前仍可使用的创作资料。

现在的规则是：

1. 重新分析先在资料同步锁内校验当前正文、记录正文来源快照并创建本次分析工作流，不再执行任何预清理。来源快照继续使用现有章节 ID、项目、章节号、标题、完整正文 hash 和 `updated_at`，不增加分析 revision 表或替换状态。
2. 四阶段模型调用、结构校验、来源片段实体化和最终分析组装全部成功后，才进入旧派生资料替换。模型调用或结果校验在此前任一步失败、取消时，本章已有角色时间线、场景、锚点、伏笔和已保存分析保持不变。
3. 开始清理前在数据库事务内重新锁定章节并匹配模型开始时的正文快照。用户在等待模型期间修改了正文或标题时，本次旧结果会在清理前被拒绝，不能先删除新正文对应的资料，也不能把旧分析挂到新正文上。
4. 本次替换清理继续复用现有章节资料同步工作流，但明确标记为不重建当前章节 RAG。该清理只是为同一正文替换分析派生资料，不会反向把刚生成的分析工作流判定为已被“正文变化”淘汰。
5. 清理流程会重新计算样式标签并更新章节时间，因此清理完成后重新读取当前章节，再通过现有分析工作流归属校验和数据库 compare-and-set 保存新分析。真正的正文或标题并发变化仍会让保存显式失败；仅由本次派生刷新造成的 `updated_at` 变化不会误伤新结果。
6. 新分析正式保存后，才继续同步回顾性章纲、伏笔、章节 RAG、物体、角色和场景资料。已有用户章纲仍不被自动覆盖；分部大纲和蓝图仍没有进入章节分析的自动写入链，继续由用户主动决定何时归纳或生成。
7. 本轮没有增加“暂存分析”、双份正式资料、替换锁表或补偿队列。模型生成成功是允许开始替换的边界，正文快照和现有可恢复清理工作流负责处理随后阶段的并发与失败。

从用户创作方式看，重新分析是一种试算：用户可能只是调整提示词、切换模型，或想看看这一章能否提取出更好的资料。在新结果尚未证明可用前，旧资料就是当前唯一可依赖的创作上下文；系统必须先拿到可用的新结果，再动旧资料，而不能把“点击重试”变成一次先删后赌的操作。

当前边界：

1. `cargo check -p a4n-orchestrator --lib` 已通过，相关 Rust 文件格式化和 `git diff --check` 已通过；此前半完成接口造成的旧符号和旧清理签名已经全部收敛。
2. 新增纯规则回归，分别确认分析替换清理不会淘汰本次生成结果，以及清理刷新样式标签和 `updated_at` 后分析来源仍有效、正文变化后立即失效。Orchestrator 测试目标在 60 秒单测上限内仍停留在测试二进制编译，不能声称这两条测试已经实际运行通过。
3. PostgreSQL 事务与 Host 外部清理仍不是一个跨系统原子事务。模型失败已经不会触发任何清理；模型成功后若外部清理失败，现有章节资料同步工作流会保留可恢复任务。只有实际出现无法通过现有恢复入口收敛的数据完整性问题时，才考虑更重的 outbox 或补偿机制。

七十、章节分析恢复复用原断点，不让用户为已完成的模型调用再次付费（2026-08-10）

继续检查“新分析已经生成，但替换或保存阶段失败”后的真实恢复操作时确认，系统虽然已经保存四个模型阶段的调用级 checkpoint，旧恢复入口却会创建新的 analysis revision。新 run 无法读取旧 run 的 checkpoint，用户点击恢复后仍会重新调用模型；章节投影又只有在分析已经落库时才开放“继续同步”，尚未保存的新结果会被界面说成“请重新分析”。这让技术上已有的可恢复结果在产品上等同于不存在。

现在的规则是：

1. 失败、取消或中断的章节分析继续使用原 workflow run ID 恢复，不再创建新的 analysis revision。事实抽取、摘要、角色状态和伏笔阶段继续走现有请求指纹；请求仍与当前正式资料一致时直接复用 checkpoint，只有实际提示词输入变化时才重新调用受影响的模型阶段。
2. 如果失败发生在模型成功后的章节资料替换阶段，恢复入口会先继续同一正文对应、且明确标记为“分析替换”的章节资料同步任务。真正的正文保存同步仍会淘汰旧分析；分析替换同步不会被误认成正文变化，也不会让用户手工寻找并依次恢复两个内部任务。
3. 原分析 run 恢复为 running 后，仍通过最新 run 归属、正文指纹和 compare-and-set 门禁保存结果。用户在失败后修改了正文、标题或启动了更新的分析时，旧断点不能因为可恢复就越过当前正式资料。
4. 已经保存结构化分析的失败继续进入原有派生同步路径，只补回顾性章纲、伏笔、RAG、物体、角色和场景等未完成阶段；尚未保存结构化分析的失败则先从模型/替换断点继续。两个入口最终汇入同一正式资料写入和同步规则，不维护两套分析事实。
5. 章节投影不再把“分析尚未落库”解释成不可恢复。终态失败、取消或中断且 run 允许恢复时，界面都会开放继续操作；同时新增一个只读投影字段区分本次 run 是否已经保存分析结果。
6. 写作台据此显示准确动作：结果尚未保存时显示“继续分析”，即使章节还没有任何 `analysis_data` 也能从断点恢复；结果已经保存但派生资料未完成时才显示“继续同步”和同步请求预览。旧分析仍显示在界面、但新一轮重分析尚未保存时，也不会拿旧分析的派生请求冒充新 run 的恢复预览。
7. 本轮没有增加模型结果暂存表、恢复专用 API、checkpoint 复制或跨 run 搬运。原 workflow ID 和原调用级 checkpoint 已经足够表达用户需要的恢复语义；新投影字段只描述当前状态，不成为第二来源。

从用户创作方式看，章节分析可能因为网络波动、模型结构错误、取消操作或后续资料同步失败而中断。用户关心的是“已经完成的工作能否接着做”，而不是内部失败发生在哪一层。只要正文和相关模型输入没有变化，继续操作就应复用已经付费取得的结果；用户主动修改资料后，再按新输入重算才是合理成本。

当前边界：

1. `cargo check -p a4n-orchestrator -p a4n-runtime`、`npx tsc --noEmit`、前端生产构建、Web API parity、相关 Rust 文件格式化和 `git diff --check` 已通过。
2. 新增 Runtime 纯规则回归，确认分析尚未保存时失败 run 仍可恢复，并且 running 状态不会重复显示恢复按钮。目标测试和 `cargo check --tests` 在 60 秒后端测试上限内均停留在测试目标编译，不能声称该测试已实际运行通过。
3. checkpoint 只在请求指纹完全一致时复用。角色、世界观或其他正式上下文改变导致提示词变化时，相关模型阶段会按当前资料重新生成；这是避免旧上下文污染新分析的正确失效，不应为了节省调用而强行复用。

七十一、章节分析必须告诉用户具体处理了哪些资料（2026-08-10）

继续核对章节分析完成后的真实界面后确认，现有状态面板只能显示物品、角色、场景等步骤“已完成/失败”，用户无法判断本章到底新增了什么、关联了哪些已有资料，也无法区分“模型没有识别到条目”和“资料同步结果没有展示”。后台其实已经在工作流 checkpoint 中保存了物品发现、角色发现和角色状态同步结果；缺口主要是结果没有进入章节只读投影，场景阶段则在拿到完整返回值后把它丢弃了。

现在的规则是：

1. 章节分析继续使用现有 workflow checkpoint 作为运行证据，不增加资料变更日志表、候选表或第二套同步事实。只有与当前正文、当前分析结果和当前 workflow run 指纹一致的已完成 checkpoint 才能参与展示。
2. 物品更新直接复用发现结果中的 `created` 和 `updated`；角色更新复用发现结果中的 `created`、`existing` 以及角色时间线结果中的 `synced`；场景阶段把原本已经返回的 `profiles` 结果一并保存到章节分析 checkpoint，不再只记录 `completed=true`。
3. 新建角色的发现结果补回名称和别名。此前 `created` 只有 ID，不仅无法向用户说明新增了谁，后续按发现结果选择角色同步时也不能稳定取得新角色名称；现在创建与已存在分支具有可读取的身份信息。
4. Runtime 将这些有效 checkpoint 投影为 `material_updates`，只包含资料类型、动作和名称。正文被修改、分析 run 被替换或正文保存同步已经淘汰旧分析时，既有指纹规则会让旧更新项自动消失，不需要额外清理状态。
5. 写作台“当前正文的资料更新”面板在步骤状态之外显示本次分析的具体结果，例如“新增物品”“补充已有物品”“新增角色”“关联已有角色”“同步角色状态”和“关联场景”。结果较多时只展示前八项和剩余数量，完整正式资料仍在各自资料页维护。
6. 面板明确说明：用户手工资料不会被静默覆盖；分部大纲和蓝图不属于逐章自动更新范围，只在用户主动操作时生成或更新。这个说明描述现有写入规则，不引入新的确认流程。
7. 本轮没有尝试构造字段级 before/after diff。物品和场景静态资料仍按现有规则只补空缺、追加章节范围和证据；角色时间线继续按事件来源保护用户或历史值。只有以后用户确实需要逐字段审阅 AI 建议时，才应基于真实字段来源设计确认能力，而不是把一次章节分析扩展成通用冲突系统。

从用户创作方式看，分析按钮不是一个看不见内部结果的后台维护动作。用户写完一章后需要立即知道“这一章让哪些资料长出来了”，然后决定是继续写、打开资料页修正，还是主动归纳分部大纲或蓝图。状态说明同步是否完成，具体更新项说明系统实际做了什么；二者都来自同一次正式工作流，不会形成第二份作品事实。

当前边界：

1. 新增纯规则回归覆盖物品、角色和场景 checkpoint 的具体更新投影，并确认正文变化后旧结果不可见。当前工作区的 Galgame 合同重构存在 41 个与本轮无关的编译错误，`cargo check -p a4n-orchestrator -p a4n-runtime` 无法完成，因此不能声称该 Rust 测试已经实际运行。
2. `npx tsc --noEmit`、前端生产构建和目标文件 `git diff --check` 已通过。Web API parity 在 API 合同生成检查处被工作区已有的 `frontend/src/api/generated/host.ts` 过期阻断，本轮没有覆盖用户正在进行的合同生成改动。
3. 旧章节分析 checkpoint 没有保存场景结果或新建角色名称时，界面仍只显示步骤状态；下一次重新分析或恢复到实际执行该阶段后会产生完整更新项。本轮不迁移历史 checkpoint，也不伪造未知结果。

七十二、上层归纳必须允许从已有设定或大纲进入，并由用户明确确认更新（2026-08-10）

继续按三类真实用户入口核对后确认，章节分析已经能够让正文逐章长出角色、场景、物品、伏笔和章纲，但蓝图与分部大纲的主动聚合仍有三处不自洽：入口隐藏在“导入 → 辅助工具 → 结构反推”；项目没有正文时整个上下文读取会直接拒绝，即使用户已经填写项目简介、角色、场景、物品或正式章纲；确认分部候选又完全拒绝更新已有分部，而蓝图确认会更新正式顶层字段，却没有把这种行为清楚告诉用户。

现在的规则是：

1. 项目详情入口改为“导入/归纳”，归纳面板提升到页面首部并改用用户能理解的“项目资料归纳”表述。生成阶段只形成持久化候选，不修改正式资料；确认按钮会再次说明本次蓝图、章纲或分部大纲的具体写入语义。
2. 上下文门禁按目标资料判断，不再机械要求所有归纳都必须有正文。章节大纲仍需要正文；分部大纲可以从正式章纲、正文或已有分部进入；蓝图可以从项目简介、正式章纲、分部大纲、已有蓝图、角色、关系、物品、场景或伏笔进入。这样“已经立项但尚未写正文”的自由创作项目也能主动补全上层结构。
3. 蓝图归纳上下文补入项目简介、正式章纲、物品档案、场景档案和已有角色关系；原有正文摘要、抽样正文、分部大纲、角色、伏笔和正式蓝图继续保留。提示词明确把正式资料作为更新基线，不能因为抽样正文没有再次出现就否定用户已经确认的事实。候选 freshness hash 自动覆盖这些新增来源，确认前资料发生变化时旧候选会过期。
4. 蓝图确认仍是用户主动更新正式蓝图的操作，而不是章节分析的自动副作用。导入分析候选和项目资料归纳候选现在共用正式蓝图字段差异规则；两条路径都按落库后的真实记录返回变化字段，并且 `total_chapters` 都不能小于项目当前已存在的最高章节。角色和关系继续只新增或补空，不删除候选未返回的资料，也不覆盖已有非空冲突字段。
5. 导入分析分部候选和项目资料归纳分部候选共用同一个正式写入函数：按 `part_number` 更新候选覆盖的正式分部、插入缺失分部、复用未变化分部，并保留候选没有覆盖的其他分部。系统先验证确认后的完整分部集合不存在范围重叠，再重新绑定现有章纲的 `part_id`；两条入口不再各自维护一套分部覆盖规则。
6. 章节大纲归纳继续保护手工章纲：缺失时新增，已有自动分析章纲可以刷新，与没有自动来源标记的正式章纲冲突时明确拒绝。蓝图和分部大纲不会进入逐章分析自动写入链，也没有新增“暂定蓝图”、临时分部表或第二套正式事实。
7. 本轮复用现有 import-reverse workflow、checkpoint、候选确认事务和项目锁，没有再建立一套“资料归纳系统”。原内部名称继续承担兼容性，用户界面和进度文案统一解释为“归纳候选 → 用户确认 → 正式资料”。

从用户创作方式看，这补齐了三个入口之间真正缺失的一段：有 idea 的用户仍可走灵感到蓝图的标准链路；已有设定或章纲、尚无正文的用户可以直接从当前正式资料归纳蓝图或分部；已有正文的用户可以逐章分析，再在自己认为资料足够时主动向上聚合。系统不要求正文必须先存在，也不让章节分析替用户决定何时改蓝图。

当前验证：

1. `cargo check -p a4n-db --lib` 通过；蓝图章节规划 4 条纯规则测试和分部重划 2 条纯规则测试实际通过。PostgreSQL 集成回归已补充蓝图主动更新、已写章节下限、分部更新和章纲重绑，但当前没有 `A4N_TEST_DATABASE_URL`，不能声称数据库断言已执行。
2. 项目归纳候选前端合同 8 条 Vitest 通过，当前前端资源使用 `npx vite build` 构建通过，目标文件 `git diff --check` 和 Rust 目标文件 `rustfmt --check` 通过。
3. 全量 `cargo check -p a4n-orchestrator --lib` 仍被工作区现有 13 个 Galgame 导出/可见性错误阻断；全量 `npx tsc --noEmit` 仍被 `GalgameTab.tsx` 3 个既有类型错误阻断。本轮没有修改这些并行合同问题，也没有把 Vite 转译成功冒充全量类型检查通过。

七十三、已有设定可以直接建立和修改初始角色档案，不能伪造章节事件（2026-08-10）

继续沿“已经立项但尚未写正文”的自由创作入口检查后确认，角色资料此前仍有两个断点：项目详情只能等待正文分析产生角色，新增手工入口后又只能创建、不能修改；现有属性管理要求填写章节号，因此若拿它代替初始档案编辑，就会把用户立项时已经存在的设定伪装成“第 1 章发生的变化”。

现在的规则是：

1. 项目详情角色页可以直接新建角色，姓名是唯一必填项；性别、年龄、性格、背景和外观可以只填写用户当前已经确定的部分。角色不再必须从蓝图或正文分析中产生。
2. 尚未进入章节时间线的角色可以打开详情并编辑初始档案。保存直接更新正式 `base_attributes` 和对应当前投影，不创建章节属性事件，也不把“已有设定”伪装成正文事实。
3. 编辑表单只展示常用基础字段，但保存会保留已有的角色类型、动机、其他扩展属性和社会关系；用户没有看到的字段不能因为一次局部编辑被清空。用户主动清空本次可编辑字段时，该字段从初始档案移除，其他资料保持不变。
4. 初始档案一旦已有属性事件、行为、删除标记、快照、状态索引或已同步章节，直接重写会被明确拒绝。此时基础设定与章节变化已经形成时间关系，应通过角色详情记录章节后的变化；系统不会为了让表单“能保存”而偷偷指定一个假章节，也不会原地改基线后留下旧快照。
5. 用户确认修改后，系统解除旧角色发现 generation run 对这条正式档案的所有权，但保留 generation run 本身作为历史运行证据。后续章节分析可以补充其他空白和真实变化，不能再把发现时的基础值当成仍由 AI 拥有。
6. 角色同步模型开始后、正式提交前，会重新锁定角色并比较模型读取时的姓名、基础属性、当前状态和同步断点。用户在等待期间修改了初始档案或角色状态时，旧 AI 结果在清理时间线之前就被拒绝，不能覆盖用户较新的正式决定。
7. 正文生成同时存在蓝图角色种子和尚未同步的正式角色档案时，详细角色参考优先采用用户当前确认的初始档案；蓝图中仍可提供角色类型、弧光等未被档案补充的规划字段。这样蓝图负责播种，正式角色档案负责用户后续确认，不会把旧蓝图字段和新角色设定并列成两个同等事实。
8. 角色档案数据库提交后继续同步现有角色 RAG。索引失败只作为警告返回，前端仍刷新已经正式保存的档案；数据库事实与可重建检索副本不会被一个笼统的“保存失败”混为一谈。

从用户创作方式看，立项资料通常是逐步填写的：用户可能先知道角色姓名和职业，过几天才确定年龄或背景。在正文开始前，这些修改都是同一份初始设定的完善；正文开始后，角色变化才需要按章节进入时间线。项目以是否已经存在真实时间线区分两者，不以“AI 辅助/自由创作”模式建立两套角色数据。

当前边界：

1. 本轮没有实现角色改名。姓名同时参与蓝图角色、关系、正文锚点、立绘和生成记录的身份匹配，局部改一列会制造悬空引用；需要改名时必须先设计一次可核对的身份迁移，不能把它塞进普通档案表单。
2. 已有时间线后的“纠正初始设定并重放后续事件”仍未开放。当前明确拒绝不安全的原地改基线；只有用户真实需要这一操作时，再复用现有时间线清理、重放和来源复核实现显式重建，不预建第二套角色版本。
3. `a4n-api-contract` 生成器检查、命令目录排序测试、`a4n-db` 目标编译和两条来源门禁单测已通过；角色表单 3 条 Vitest 和前端生产构建已通过。当前全量 Rust 检查被并行 Manga 类型文件缺少 serde derive 导入阻断，全量 TypeScript 被并行 Manga 生成合同缺失阻断，本轮没有覆盖这些范围外改动。

七十四、手工场景和物品允许从稀疏设定开始，正文证据只能由正文产生（2026-08-10）

继续检查“已有零散设定、尚未写正文”的入口后确认，场景和物品虽然已有手工创建表单，但此前要求外观、用途、空间、氛围、证据和图片描述等字段一次填满，并用默认类型、重要性和第 1 章范围补齐缺失值。用户只有名称和一两句想法时仍无法保存，系统还会把默认值展示成用户已经确定或正文已经证明的事实。

现在的规则是：

1. 手工创建场景和物品时，名称是唯一必须填写的描述字段。类型、重要性可以保持“未确定”，外观、用途、空间布局、氛围、规则、图片描述和证据都允许为空，后续由用户编辑或章节分析逐步补充。
2. 放宽只作用于用户手工草稿边界。AI 物品发现和场景同步仍在各自解析层要求完整结构、有效枚举和正文证据；不能因为手工录入允许稀疏值，就把模型缺字段或无证据输出当成成功。
3. 数据库存储仍需要一个章节范围占位时，该内部值不作为正文事实展示。没有正文证据的手工档案在界面显示“出场章节待正文确认”，不会显示“第 1 章出现”来冒充用户写过的内容。
4. 第一次章节分析取得真实正文证据后，用实际最早/最晚章节替换无证据的手工占位范围；已有真实证据的档案继续按最早和最晚章节增量合并。占位只服务旧 schema 约束，不成为第二来源。
5. 自动分析继续只补空、追加章节范围和证据，不覆盖用户已经填写的非空描述。名称匹配到已有手工档案时更新同一条正式资料，不另建“AI 版本”或候选档案。
6. 图片生成入口继续依据生成所需字段做自己的显式校验。允许稀疏资料先保存不等于允许缺少视觉描述时返回假成功；资料录入完整度和具体下游能力门禁各自回答不同问题。

从用户创作方式看，场景和物品往往先以名称存在，例如“废弃钟楼”“母亲留下的钥匙”，具体外观、用途和出现章节要到正文推进后才会确定。项目应先保存用户真正知道的部分，再让正文分析补充被作品证明的事实，而不是为了满足表结构迫使用户提前编造完整档案。

当前边界：

1. 类型和重要性的“未确定”继续使用现有可空/空值表达，没有增加 draft 状态、完整度表或字段候选表。以后只有真实下游需要统一完整度判断时，才从具体必需字段计算，不能维护一份容易失真的完成百分比。
2. 物品和场景的稀疏输入前端回归、首次正文证据替换占位范围的数据库回归、`a4n-db` 与 `a4n-orchestrator` 目标编译以及目标 `git diff --check` 已在实现时通过；后续并行 Manga 合同迁移造成的全量检查阻断不改变这些目标规则，但最终合并前仍需在工作区稳定后重跑全链验证。

七十五、初始关系属于正式角色档案，时间线开始后只能记录变化（2026-08-10）

继续沿“已经立项、尚未写正文”的入口检查后确认，角色页虽然已经能够建立初始档案，关系页却仍然只是只读图。用户已有“旧友”“师徒”“隶属某组织”等关系设定时只能等待正文分析识别，或者进入需要章节号的属性事件入口；前者阻断已有设定录入，后者又会把立项事实伪造成某章才发生的变化。

现在的规则是：

1. 关系页可以新增、编辑和删除初始关系，写入角色正式档案 `current_state.social_attributes`，不增加关系表、关系候选表或新的关系 API，也不创建虚假的章节事件。
2. 关系对象既可以是已有角色，也可以是用户输入的组织、阵营或其他社会对象。系统拒绝自指关系和同一角色下的同名重复关系，关系对象本身在编辑时保持不变；需要改对象时显式删除后重建，避免一次“改名”留下旧键。
3. 初始关系只在所属角色尚未进入章节时间线时可直接修改。角色已有同步章节或其他时间线记录后，关系页明确提示用户到角色详情按真实章节记录关系变化，不能为了保留编辑按钮而原地重写基线。
4. 字符串关系可以通过当前文本表单维护；已经存在的对象、数组等结构化关系保持只读，不能被一个简单描述框压平成字符串并丢失结构。
5. 每次保存携带用户打开表单时读取的完整 `expected_current_state`。AI 分析、其他标签页或另一位协作者先更新正式角色资料后，旧表单会明确过期并要求刷新，不能用一项关系修改覆盖同期产生的其他角色字段。
6. 关系保存继续复用初始角色档案的项目锁、时间线门禁、用户来源接管和 RAG 重建逻辑。数据库提交成功而可重建索引失败时仍返回警告，不把已保存的正式关系说成保存失败。
7. 蓝图关系和角色当前关系没有机械双写。`blueprint_relationship` 负责长期关系规划和演化弧线，`social_attributes` 负责角色当前正式事实；用户在关系页修改当前事实不会暗中改写未来规划，也不会制造第二份当前关系。

从用户创作方式看，关系和角色年龄、背景一样，常常在立项时只知道一部分，写作推进后才发生变化。正文前是在完善同一份初始事实，正文后才是时间线事件；系统必须以真实创作时间边界区分两者，而不是以“自由创作/AI 辅助”建立两套关系数据。

当前边界：

1. 本轮不实现已进入时间线后的关系基线纠正与事件重放，也不实现跨角色自动生成对称关系。“甲把乙视为旧友”不必然等于“乙也把甲视为旧友”，只有用户确实需要双向联动时再设计显式操作。
2. 关系图仍展示角色档案中的当前社会关系；蓝图关系继续在蓝图规划入口维护。后续生成链必须明确消费语义，不能再把两者都泛称为“角色关系”。
3. 角色表单 4 条目标 Vitest、全量 TypeScript、前端生产构建、`a4n-api-contract` 目标编译、初始档案时间线/CAS 2 条数据库单测和目标文件 `git diff --check` 已通过。Web API parity 仍被整个生成文件过期阻断，本轮没有用 `--write` 覆盖并行合同迁移；实际页面新增、编辑、删除和旧表单过期仍需浏览器复核。

七十六、正式创作资料必须进入大纲与正文生成，蓝图关系只能作为规划（2026-08-10）

继续追踪资料下游后确认，允许用户维护角色、场景和物品还不够：常规大纲生成此前主要读取蓝图角色和蓝图关系，没有自然读取自由创作用户的正式角色档案、当前关系、物品、场景和伏笔；正文生成又把蓝图关系直接标成“角色关系”。结果是用户已经录入的资料在生成时消失，或者未来关系规划与当前事实被模型当成两份冲突事实。

现在的规则是：

1. 分部大纲和章节大纲的稳定上下文新增 `formal_materials`，统一携带正式角色档案、当前社会关系、物品、场景和未解决伏笔。它是现有正式表的请求级投影，不持久化为蓝图，也不形成“暂定蓝图”。
2. 上下文明确定义资料优先级：`formal_materials` 是当前正式事实，发生冲突时优先；蓝图 `characters` 和 `relationships` 只描述长期定位、角色弧光和关系演化，不代表这些状态在当前章节已经发生。
3. 没有正式蓝图的项目只要已有任一正式角色、物品、场景或伏笔，也可以生成大纲，不再机械要求先写项目简介或正文。该上下文继续标记 `blueprint_available=false`，模型只能基于已有资料规划，不能假装全书蓝图已经由系统确认。
4. 正式资料同时进入完整、聚焦和最小压缩上下文。上下文因 token 预算降级时不能只留下蓝图标题、却把用户当前角色和物品全部丢掉。
5. 大纲写入前的来源锁扩展到正式角色、物品、场景和伏笔；保存前重新加载的上下文会比较这些投影。用户在模型生成期间修改正式资料时，旧大纲结果不能越过来源变化门禁写入。
6. 正文关键参考拆成“正式角色当前资料”“蓝图角色规划”和“蓝图关系规划”。蓝图关系每条都带有规划标记，并明确说明长期走向不代表当前章节已发生；角色当前关系继续来自正式角色状态和章节时间线。
7. 只有初始档案的自由创作角色即使没有对应蓝图角色，也会进入正文关键参考。已有时间线的角色继续使用目标章节之前的状态，不能把较后章节的当前投影倒灌到前面的非线性补写章节。
8. 稀疏物品和场景在正文上下文中至少保留用户确认的名称；空字段不再渲染成“外观: ；状态: ”，只有基础描述的场景也不会被遗漏。没有正文证据的内部章节范围占位不进入大纲投影，避免把 schema 占位冒充作品事实。
9. 本轮复用现有大纲上下文账本、来源指纹、项目锁和正式资料查询，没有增加资料同步服务、统一素材 DTO 或另一套缓存。正式表仍是唯一事实来源，生成上下文只是当次请求的可重建投影。

从用户创作方式看，已有设定用户通常先建立少量角色、地点和关键物品，再让 AI 帮忙规划接下来的分部或章节；已有正文用户则通过逐章分析让这些资料逐步增长。两类用户都不应被迫先补一份蓝图，生成也不能忽略已经确认的事实。蓝图存在时负责“想往哪里走”，正式资料负责“现在是什么”，二者只有这种职责分工才自洽。

当前验证：

1. `cargo check -p a4n-orchestrator --lib` 通过。
2. 大纲正式资料投影 4 条上下文合同测试通过；章节正文准备 19 条规则测试通过；章节前置上下文 9 条测试通过，其中覆盖稀疏物品、稀疏场景、当前关系和蓝图关系规划标记。
3. 目标 Rust 文件格式化和目标文件 `git diff --check` 通过。尚未实际调用模型检查生成文本，也未完成浏览器端到端验证；这些仍是整个 Goal 完成前的验证项，而不是本轮规则测试可以替代的证据。
4. `a4n-runtime` 和 `a4n-server --no-default-features` 的扩大编译被工作区现有 ExportChapter 私有导入错误阻断；该错误不在本轮资料同步链路中，未为取得绿色结果而修改并行导出重构。

七十七、角色资料冲突必须保留用户值并继续同步（2026-08-10）

继续检查“章节分析只补充、不覆盖用户资料”的实际失败路径后确认：角色属性门禁虽然已经能够识别用户或历史来源拥有的字段，但此前一旦模型尝试修改这类字段，整个角色同步事务会失败。章节分析随后把该角色记为失败，用户点击“继续同步”仍会遇到同一个冲突；与此同时，同一角色本来可以正常写入的行为记录、其他空白属性和状态索引也被一起放弃。保护用户资料不应等于让资料同步永久卡死。

现在的规则是：

1. 用户或历史来源拥有的角色属性仍然不可被 AI 修改或删除；底层将这种情况表达为明确的“受保护属性”结果，不再与数据库错误、来源过期或合同错误混为一类。
2. 角色同步事务只对这一种可预期的所有权冲突执行“保留并继续”。属性新增/修改、删除候选和隐性属性复审都遵守同一规则；数据库失败、正文来源变化、角色并发修改和无效模型结构仍然显式失败，不能被当作普通冲突吞掉。
3. 被保护的字段不产生 AI 属性事件或删除标记。后续快照和角色当前状态继续从实际落库事件重建，因此不会把模型尝试过、但未被接受的值写进正式投影。
4. 同一角色的其他合法属性事件、行为记录、状态索引和快照继续提交。一个关系字段冲突不会再阻断整名角色，也不会使整章分析陷入无法恢复的重复失败。
5. 每个被保留的字段记录章节号、属性分类、键和模型尝试的操作，进入角色同步 generation run 与章节分析 checkpoint。写作台“当前正文的资料更新”会显示“保留用户角色资料”，并指出具体角色及关系/显性/隐性属性，不再只给出一个模糊的同步成功状态。
6. 本轮复用现有角色事件来源、事务写入步骤、工作流 checkpoint 和章节资料更新投影，没有增加字段候选表、冲突版本表或第二套角色档案。只有用户确实需要逐字段查看模型建议值并选择接受时，才设计正式的审阅交互。

从用户创作方式看，用户可能先明确“林夏与沈默是旧友”，再让章节分析补充林夏的行为、位置和其他关系。模型即使对“旧友”作出不同判断，也只能报告“已保留用户资料”；它不能覆盖用户设定，更不能因为这一处冲突让本章其他可靠资料全部失去。
